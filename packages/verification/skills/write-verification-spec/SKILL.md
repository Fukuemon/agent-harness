# write-verification-spec

撮る仕組み（録画のライブラリ、それを呼ぶ薄い層、配置先と名前の決まり）は、利用者の `context/testing/evidence.md` の Capture Tools が持つ。  
このスキルは、spec を書いて撮るときの判断だけを持つ。コードの層と待ち方は、利用者の `context/testing.md` と、テストのコードの書き方の取り決めに従う。

## 始める前に読むもの

- `context/testing/evidence.md` の Capture Tools、Capture Environment、Login and Test Data。spec の配置先、見本の spec、撮るコマンド、ログインとテストデータの作り方が書いてある。要る値が書かれていなければ利用者に尋ね、context に書いてもらう。
- 既にあるエビデンスの spec のうち、同じアクターか同じ画面のものを 1 本

新しい spec は、context にある見本の spec を写して始める。見本がなければ、既にあるエビデンスの spec を写す。どちらもなければ、利用者と見本を決めて context に書いてもらう。

## 観点から写すもの

pull request のエビデンスは、スキル attach-evidence で設計した観点から書く。観点は、スキル design-test-cases の EARS の要件の条件と期待結果である。推測で足さない。

- 1 つの観点を 1 つの test にする。テストの名前は、利用者のテストの名前の付け方に従い、条件と期待結果から作る。
- 動画の置き場と名前は、スキル capture-browser-evidence の「置き場所と名前」に従う。test の名前は、本文の表の「確認の方法」に書く。
- 字幕は、観点の操作を `step` に、確認する結果を `check` に出す。文は観点の条件と期待結果から作り、画面の文言はそのまま書く。
- 字幕に出すアクターは、ログインする利用者の名前と役割にする。

## シナリオから写すもの

推測で埋めない。分からなければ利用者に尋ねる。

- 手順の文: シナリオの「前提」「もし」「かつ」「ならば」の文。言い換えずに字幕にし、リンクとコードスパンの書式だけを外す。
- シナリオの識別子、要求の issue、アクター、番号、シナリオ名: 配置先のフォルダの名前になる。名前の決まりは、`context/testing/evidence.md` の Verification Scenarios にある。
- 例の列と値: シナリオアウトラインの例の表の値。実施の結果を記録する場所に書く値の形も、Verification Scenarios にある。ファイル名になるので、文言を変えない。
- 改修前と違ってよい差: シナリオの備考。要求ごとに 1 つのファイルに写し、その要求の spec から読む。そのスクリーンショットだけの差は `check` に、どのスクリーンショットにも映りうる差はシナリオ全体に渡す。備考にない差が撮れたら、spec に書かずに利用者に示す。

## spec を書く

- シナリオの文ごとに、`step` か `check` を呼んでから操作する。
  - 前提、もし、操作の続きの「かつ」は `step`。字幕を出し、動画の時刻を残す。
  - ならば、判定の続きの「かつ」は `check`。出し終えた時点の画面をスクリーンショットにする。
  - 操作の間に見る判定の文は、操作の前の `step` の 2 行目以降に出す。字幕は次に変えるまで残る。
- シナリオにない操作（表を横に送る、隠れた要素を見せるためにカーソルをずらす）は、前に「(撮影のため、…)」の字幕を出してから行う。録画に映らない値（カーソルの形、API のバージョン）も、この字幕に出す。
- ログインとデータの確認は、録画の外の準備の段階で行う。録画は、前提の画面を開いてから、前提の字幕で始める。
  - 字幕の文をページの storage に置く仕組みでは、最初の `step` より前に画面を開く。何も開いていない画面では失敗する。
- ほかのシナリオの前提を変える操作（登録、保存）は、撮った後に戻す。戻す処理は `try/finally` に置く。登録まで求めないシナリオでは、確定で開くダイアログを「キャンセル」で閉じる。

### 改修前と比べるとき

振る舞いを変えない改修（置き換え、リファクタリング）を確認する要求だけ、改修前の URL を渡して両方を撮る。新しい機能の要求では、1 つのバージョンだけを撮る。

- 改修前のバージョンを、改修後と同じ指し方で操作する。改修前はテスト用の識別子を持たない画面がある。両方のコードを読み、両方にある指し方（ボタンの名前、アイコンの class、要素名）を、セレクタをまとめる場所に置く。
- 改修前と改修後で、`check` を同じ順に同じ数だけ呼ぶ。比較の画像は、`check` の順に組にする。
- 改修前のバージョンだけで起きる読み込みの失敗は、画面を開く操作の中で読み直す。spec には書かない。

## 書いた spec を撮って直す

1. `context/testing.md` にあるテストのコードの lint と型のチェックを流す。
2. 1 本だけ流す。改修前と比べるなら、改修後だけに絞る。
3. 配置先の `frames/` のスクリーンショットで、操作の位置と字幕が合っているかを見て、spec を直す。
4. 改修前と比べるなら、改修前も撮り、比較の画像で、判定の場面が同じ操作の後になっているかを見る。改修前だけ表示の位置がずれたら、「(撮影のため、…)」の字幕を出して位置を戻す。
5. 検証のシナリオのときは、エビデンスの一覧（置き場は `context/testing/evidence.md` の Verification Scenarios にある）に、足した spec とシナリオの対応を書く。撮影のための操作も書く。

撮る環境の選び方、確認の方法、シナリオと食い違ったときの扱いは、スキル run-verification-scenarios にある。本文への入れ方は、スキル attach-evidence にある。
