# attach-evidence

エビデンスを付ける変更、元のファイルの置き場、公開してよい範囲、撮影の手段は、利用者の `context/testing/evidence.md` が持つ。  
セクションの形は、写された pull request の雛形の「検証とエビデンス」にある。  
このスキルは、観点を決める、撮る、本文に入れる、入ったことを確認するときの判断だけを持つ。

## 始める前に読むもの

- `context/testing/evidence.md` の Evidence Scope、Storage and Visibility、Attachment のセクション。要る値が書かれていなければ、利用者に尋ねて context に書いてもらう。
- 対応する issue の完了の条件と検証の観点、pull request の差分
- 添付の仕方は、`context/project.yml` の `hosting` の値に合う 1 つだけを読む。
  - `github`: [references/github.md](references/github.md)
  - `gitlab`: [references/gitlab.md](references/gitlab.md)

## 観点を設計する

観点は、スキル design-test-cases で設計する。推測で足さない。

- 書くのは、本文の「観点の設計」の details に入れる 3 つだけにする。処理の流れ、主要な仕様、観点の表（対象外の観点と理由を含む）。設計の文書の骨組みのほかのセクションは埋めない。
- 観点は、design-test-cases の EARS の要件にする。
- 1 本の動画には 1 つの観点だけを撮る。表の 1 行が 1 つの観点で、レビューする人が観点と動画を 1 対 1 で読み合わせられる。
- 検証のシナリオ（前提、もし、かつ、ならば の文）があれば、観点はシナリオに従う。
- issue に検証の観点があれば、その行を観点の出発点にする。どちらもなければ、issue の完了の条件の項目ごとに 1 つの観点にする。
- 撮る観点の一覧を、撮る前に利用者に見せる。

## 撮る

エビデンスは、観点ごとの spec で撮る。spec の書き方はスキル write-verification-spec に、流し方と撮った後の確認はスキル run-verification-scenarios に従う。  
spec を書くほどではない 1 回きりの再現は、スキル capture-browser-evidence で撮る。

撮る画面は、変更の種類で選ぶ。それぞれの起動の仕方と URL は、`context/testing/evidence.md` の Capture Environment にある。

| 変更 | 開くもの |
| --- | --- |
| 検証のシナリオがある | 検証環境か、ローカルで起動したアプリの画面 |
| 画面の操作から API までを通す、API だけ | ローカルで起動したアプリの画面。API だけの変更は、その API を呼ぶ画面の操作で撮る |
| 画面の UI と見た目 | コンポーネントのカタログ |
| 画面の仕様とモック | モックのファイル |

- 既にある spec で撮れる観点は、spec を流し直すだけにする。なければ、機能の spec に test を足す。
- spec をコミットしてから撮る。字幕に撮ったコミットを出す仕組みなら、未コミットの変更が字幕に残る。
- 対話でブラウザを操作するツールでは、エビデンスを撮らない。録画のフレームが落ちることがあり、撮り直すときに同じ操作を再現できない。spec を書く前に、画面の操作の位置を確認するのには使ってよい。
- 録画が H.264 の mp4 でなければ、capture-browser-evidence の変換のスクリプトで変換する。

## 出す前に確認する

次のチェックリストを応答に写し、全部を満たすまで撮り直す。  
コンタクトシートの作り方は、run-verification-scenarios の「確認する」にある。

```
- [ ] 判定のスクリーンショット（`frames/`）を開き、字幕と画面が合っている
- [ ] 録画の全体をコンタクトシートで見て、判定の外に失敗の通知、想定外のダイアログ、空白の画面がない
- [ ] 録画に映らない結果（API のレスポンス、DB の値、ブラウザのダイアログ）は、テキストの証跡を表の同じ行に書いた
- [ ] 撮ったコミットに未コミットの変更がなく、撮った後にコードを変えていない
- [ ] ログインの値、トークン、公開してよい範囲の外のデータが映っていない
- [ ] 1 つのファイルが、ホスティングサービスの上限以下
```

## 本文に書く

形は、pull request の雛形の「検証とエビデンス」に合わせる。

- セクションの先頭の 1 行に、撮った条件を書く。撮った環境（ローカルか検証環境か、カタログか、モックか）、ブラウザのエンジン、viewport、撮ったコミット。
- 機能が複数あるときは、機能ごとに小見出しと表を分ける。
- 観点は「条件」と「期待結果」の 2 列に分け、1 つのセルに要件の文を入れない。
  - 条件だけを縦に読めると、観点の抜けと重なりを見つけやすい。
  - 期待結果と「結果」を隣に並べると、比べやすい。
- 「確認の方法」には、spec のファイル名と test の名前を書く。パスは「エビデンスの spec」の details に書く。パスを表に書くと、列の幅が条件と期待結果の列を狭める。
- 「結果」は、通った、通らなかった、未実施のどれかにする。未実施は理由を書く。撮らなかった観点も、行を消さない。
- 「エビデンス」には、動画と判定のスクリーンショットを並べる。スクリーンショットの代替テキストは、判定の文にする。
- 改修前と比べるときは、「エビデンス」の列を「改修前」と「改修後」の 2 列にし、同じ行に並べる。
- 録画に映らない結果は、同じ行の「結果」に値を書く（`200 が返った`、`破棄の確認: 0 回`）。
- 「観点の設計」の details に設計の 3 つを、「エビデンスの spec」の details に spec のパスを、撮ったコミットの SHA の blob link で書く。コードはリポジトリにあるので貼らない。手元のファイルの置き場所は書かない。
- 自動のテスト、lint、CI の結果は「確認したこと」に書き、このセクションに書かない。

表の例は次のとおり。

```md
| # | 条件（WHEN / IF） | 期待結果（SHALL） | 確認の方法 | 結果 | エビデンス |
| --- | --- | --- | --- | --- | --- |
| 1 | 一覧の画面で「作成」を押したとき | 作成のダイアログが開く | `create-dialog.spec.ts` の `create-dialog-open` | 通った | [create-dialog-open](<URL>) ![作成のダイアログが開く](<URL>) |
| 2 | 何も入れずにダイアログの「閉じる」を押したとき | 破棄の確認を出さずにダイアログが閉じ、一覧に戻る | `create-dialog.spec.ts` の `create-dialog-close` | 通った。破棄の確認: 0 回 | [create-dialog-close](<URL>) ![ダイアログが閉じ、一覧に戻る](<URL>) |
```

## 本文に入れる

- 元のファイルは、`context/project.yml` の `verification.evidence_dir`（書かれていなければ `.ai-out/evidence`）の下の `<番号>/` に置く。`<番号>` は本文に入れる pull request の番号にし、作る前に撮るときは issue の番号にする。
- 本文を下書きのファイルに書き、エビデンスの参照を、リポジトリのルートからの相対パスの `![<名前>](./<path>)` にする。
- 入れ方は、`hosting` の references に従う。作った後に足すときは、今の本文を取り、入れ済みの URL を残したまま、足すファイルの参照だけを書く。
- 本文が参照しないファイルを渡さない。渡すファイルは全部、表から参照する。
- issue に入れるのは、不具合の再現と改修前の動きのように、pull request より先に示すものだけにする。

コメントは、次のときだけ使う。

- 撮り直したとき。本文のエビデンスを今の差分のものに差し替え、撮り直した理由と差し替えた観点をコメントで知らせる。本文の編集は、レビューする人に通知されない。
- 本文が上限を超えるとき。表とスクリーンショットは本文に残し、`<details>` の中身からコメントへ移す。上限は、`hosting` の references にある。

## 入ったことを確認する

- 本文を API で取り、上げた先の URL の数が、本文に入れたファイルの数の合計と合うことを確認する。数え方は `hosting` の references にある。
- 書き換わらずに残った `](./` の参照がない。
- pull request の画面にログインして開き、再生できることを確認する。

## コメントの動画を本文に移す

過去の pull request のコメントに付けた動画は、上げ直さずに、URL を本文の表へ移す。手順は `hosting` の references にある。

- 条件と期待結果はコメントの観点の文を分けて写し、結果は本文の「確認したこと」から写す。

## 終えたら

- 元のファイルの置き場のうち、自分が作ったものを消す。
- 利用者に、撮った観点と本数、本文に入れたファイルの数と確認した数、撮らなかった観点を伝える。
