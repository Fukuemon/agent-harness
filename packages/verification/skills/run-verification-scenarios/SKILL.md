# run-verification-scenarios

撮るコマンドと環境変数は、利用者の `context/testing/evidence.md` が持つ。決まっていない値は、利用者に尋ねる。  
配置先と名前は、スキル capture-browser-evidence の「置き場所と名前」に従う。  
このスキルは、撮るときと確認するときの判断だけを持つ。

## 始める前に読むもの

- `context/testing/evidence.md` の Capture Environment と Login and Test Data。撮るコマンド、環境変数、改修前と比べるときの起動の仕方、テストデータを作る手順
- エビデンスの一覧（要求ごとの README など。置き場は `context/testing/evidence.md` の Verification Scenarios にある）。撮るシナリオ、spec を置かないシナリオ、撮影のための操作

pull request のエビデンスは、ローカルで起動したアプリで撮る。「利用者に確認すること」のうち、環境と検証環境のログインの値は尋ねない。改修前と比べるかと、テストデータだけを確認する。  
pull request のエビデンスでは、実施日でフォルダを分けない。改修前と改修後を別の日に撮っても、同じ配置先にそろう。

## 利用者に確認すること

推測で埋めない。

1. 要求と、撮るシナリオ（全部か、絞るか）
2. 環境（ローカルか検証環境か）と、改修前と比べるか
   - 比べないとき: 撮る環境の URL だけを渡し、1 つのバージョンを撮る。
   - 比べるとき、画面だけの改修: 改修後と改修前の画面を別のポートで起動できれば、1 回で両方を撮る。起動するブランチを確認する。起動の仕方が context になければ、次の項目の手順で 1 回ずつ撮る。
   - 比べるとき、API も変わる改修と検証環境: 改修前と改修後の環境で 1 回ずつ流し、2 回目に 1 回目の実施日を渡して同じ配置先にそろえる。今どのバージョンがデプロイされているかを、アプリの画面で確認する。
3. テストデータを作ってあるか。作っていなければ、context にある手順で先に作る。
4. 検証環境のログインの値と環境のファイルがあるか。値は環境のファイル以外のファイル、コミット、issue、pull request に書かない。

## 撮る

1. テストデータが撮る日に依存するなら（今日の作業など）、その日に作り直す。
2. 1 つのシナリオを 1 本だけ流し、スクリーンショットで操作の位置と字幕が合うことを見てから、残りを流す。検証環境で初めて撮るときは、アクターごとに 1 本ずつ試す。
3. 残りを流す。出力をファイルに書きながら、バックグラウンドで流す。

- 録画は 1 本ずつ撮る。同じマシンでほかの撮影と同時に流すと、同じ配置先を書き合い、録画の速さも変わる。流す前に、ほかのテストの実行がないかを確認する。
- 時間切れで落ちた 1 本は、テストの名前で絞って流し直す。
- ログインの状態を保存したアカウントを、並列の worker で共有しない。
- 撮影のためにデータを作る spec は、検証環境の共有のデータを一時的に変える。検証環境で撮る前に、利用者に伝える。
- 認証コードを求められたら、利用者に、Login and Test Data にあるファイルへコードを書いてもらう。spec はそのファイルを待つ。

## 確認する

撮った spec ごとに、配置先のフォルダで次を見る。見た結果は利用者に報告する。シナリオの OK と NG は、人が動画を見て決める。spec が通ったかは、事実として報告と本文に書く。

1. README の表で、例の行ごとに mp4 がそろっているか
2. `frames/` のスクリーンショットで、字幕と画面が合っているか
3. 改修前と比べたときは、比較の画像で、縮尺、位置、画面が揃っているか。揃っていなければ、spec の待ちか操作の位置を直して撮り直す。直し方はスキル write-verification-spec にある。
4. 録画の全体を 1 秒ごとの一覧で見て、失敗の通知、想定外のダイアログ、空白の画面がないか

   ```sh
   ffmpeg -i <mp4> -vf "fps=1,scale=480:-1,tile=6x6" -frames:v 1 <作業の出力の置き場>/<名前>-sheet.png
   ```

5. 改修前と比べたときは、違う動きがシナリオの備考で違ってよいとされているか。書かれていなければ、利用者に示す。

比較の画像が多いときは、サブエージェントに見せて、ずれている画像だけを挙げさせる。

## シナリオと食い違ったら

spec で無理に合わせない。利用者に、食い違った場面、スクリーンショット、直し方の案を示す。

- 期待の文が録画で判定できない: 期待の文を、画面で見分けられる結果に直す案を出す。
- 改修前も同じ不具合: 範囲外の不具合として起票するかを利用者に尋ねる。撮影では、字幕を付けて回避する。
- 改修前と改修後の差がシナリオに書かれていない: 備考に「違ってよい」と足す案を出す。

シナリオを直すときは、`context/testing/evidence.md` の Verification Scenarios にある、実施の結果を記録する場所の決まりに従い、そこへ転記した文も同じ文に直す。

## pull request の本文に入れる

- pull request のエビデンスは、スキル attach-evidence に従って本文の「検証とエビデンス」に入れる。入れるのは、動画と `frames/` の判定のスクリーンショットだけにする。撮る仕組みが書く README と撮った記録は、確認するのに使い、入れない。
- 検証のシナリオの、添付する正式なエビデンスは、検証環境で撮ったものにする。ローカルで撮ったものは、検証環境で実施する前の確認に使い、添付するかは担当者が決める。
- シナリオごとの配置先の mp4 を、Verification Scenarios にある、実施の結果を記録する場所に添付する。本文への入れ方は、スキル attach-evidence に従う。
- 添付した後に、記録する場所へ担当者、実施日、OK か NG かを書くのは人が行う。

## 終えたら

利用者に、次を伝える。

- 撮った環境、バージョン、シナリオと本数、通った本数と流し直した本数
- 確認した結果（揃っていない比較の画像、失敗の通知、シナリオと食い違った点）
- エビデンスの置き場と、本文に入れた pull request の URL
