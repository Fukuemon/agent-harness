# 撮る仕組みで間違えやすい点

撮影の手段の具体（コマンド、設定のキー、依存の入れ方）は、利用者の `context/testing/evidence.md` が持つ。ここには、どの手段でも間違えやすい点だけを書く。

## 依存を足さない

撮るために、対象のリポジトリの依存を足さない。対象のリポジトリに入っているテストのツールを使う。

- スクリプトを対象のリポジトリの外に置くと、モジュールはスクリプトの位置から解決される。作業ディレクトリを変えても解決先は変わらないので、解決先を環境変数で渡す。
- ブラウザのアプリの設定に依存する事象（タブで開くかウインドウで開くか）は、テストのツールのエンジンでは測れない。証跡に、測っていない項目として書く。

## 録画の癖

- 録画はページ（タブ）ごとに分かれる。同じコンテキストで開いたタブは、それぞれ別のファイルになる。
- 録画は、ブラウザのコンテキストを閉じたときに確定する。ファイルの名前は、閉じた後で変える。
- viewport と録画のサイズを揃える。録画のサイズを指定しないと、小さく縮めて録画するツールがある。

## 字幕とカーソルを重ねて撮る

観点ごとに撮る spec を書くときは、字幕とカーソルを重ねる仕組みを使う。利用者の context に仕組みがなければ、このスキルの `references/` の下の雛形を写す。

- 前提と操作の文を `step`、その時点の画面で判定できる文を `check` で字幕に出す。`check` は字幕を出し終えた時点の画面を `frames/` に撮る。
- 字幕の 1 段目はどの証跡か（例: 観点 / 条件 / 改修の前後）とカーソルの凡例、2 段目は手順の文にする。手順の文は、検証の手順書の文をそのまま写す。
- 撮った環境と、デプロイされたバージョンを字幕の 1 段目に入れる。改修の前後を撮ったとき、どのバージョンを撮ったかが字幕と README から分かる。バージョンを返さない構成では、どのブランチを撮ったかを別に書く。
- 操作の間に見る判定の文は、操作の前に `step` で出す。字幕は次に変えるまで残る。
- 検証の手順にない操作を撮影のために足すとき（地図を拡大する、画面の外へ出た対象まで動かすなど）は、その前に「(撮影のため、…)」の字幕を出す。手順と見分けられるようにする。
- 検証用のページは、`file:` か `data:` の URL で開く。文書を差し替える API は、読み込みのたびに実行するスクリプトを流し直さないので、字幕とカーソルが消える。
- README は、撮るたびに撮った記録から書き直す。人が書き足すと、次に撮ったときに消える。確認した結果は別のファイルか、添付する本文に書く。

### ログインを録画の外で済ませる

録画しないコンテキストでログインとデータの確認を行い、その後のログインの状態を録画のコンテキストに入れる。

- 保存できるログインの状態は、cookie と `localStorage` だけのことが多い。`sessionStorage` は、タブを開いたときに一度だけ入れ直す。読み込みのたびに入れると、画面が書き換えた値を戻してしまう。
- ログインの後に別のポートや別のホストへ移る構成では、移った先でログインの状態を取る。`localStorage` と `sessionStorage` は origin ごとに分かれる。

### 速さを決める

- 人が読む間は、字幕を変えるたびに止める時間で作る。マウスの移動は、移動を刻む段数を増やして見える速さにする。
- 全部の操作を一律に遅くする設定は使わない。待ちの timeout を使い切ることがある。既存のテストを撮るときだけ使う。
- 並べて撮るのは、データを変えない spec だけにする。撮る中でデータを作る spec は、同じ画面を撮るほかの録画に映り込む。

## 既存のテストを撮る

テストの本体と既存の設定は変えない。撮るための設定を証跡の置き場所に作り、テストのツールに渡す。

- 継承元の設定のうち、テストのディレクトリと全体の前処理のような相対パスは、設定ファイルの位置が変わると解決できない。撮るための設定で上書きする。
- worker は 1 つ、再試行は 0 にし、viewport と録画のサイズを上書きする。

### 遅くすると挙動が変わる

連続したクリックは等倍では一瞬で終わるため、撮るときは 1 操作ごとに 500 から 700 ms 遅くする。遅くしたときだけ失敗するテストは、前提がタイミングに依存している。録画の設定より先に、テストを調べる。

- ダブルクリックで確定する操作では、1 回目のクリックが入力に数えられるかが間隔で変わる。境界を突く検証では、どちらに転んでも結論が変わらない数を渡す。
- 等倍と撮る速度の両方で、同じ条件で 2 回以上通してから証跡にする。

### 録画をレポートから取り出す

録画のディレクトリ名は、テスト名を途中で切ることがある。テストのツールの JSON のレポートには、完全なテスト名と動画のパスが入る。  
JSON のレポートから録画に名前を付けて写すスクリプトが、このスキルの `scripts/` にある。

```bash
uv run --no-project python {このスキルのディレクトリ}/scripts/collect-playwright-videos.py <report.json> <置き場所>/<検証名>/<条件> --prefix <条件>
```

- 出力は `<出力先>/webm/<条件>-<spec のファイル名>-<連番>-<describe 名>-<テスト名>.webm`。describe 名が末尾の丸括弧に画面名を持つときは、括弧の中だけを使う。
- 終了コード 0: 全部のテストの録画を取り出した。
- 終了コード 1: 録画のないテストがあった。標準エラーの一覧を見て、設定の録画の指定と、テストが実行されたかを確認する。

## ローカルのサーバの間違い

テストのツールが既に起動しているサーバを使い回す設定だと、別のブランチや worktree で起動したサーバを使う。間違えたまま成功するため気付けない。  
既定のポートはほかの worktree が使っていることがある。止めずに、専用のポートを指定し、使い回さない設定を足す。

- 配信元は、そのブランチにしかない import 元で確認する。`curl -s "http://localhost:<port>/src/<改修したファイル>" | grep -n '^import'` のように見る。前後のどちらにも現れる語では、間違えていても一致する。
- 継承元の前処理がポートを直に書いていたら、暖機もそのポートへ向ける。暖機を省くと、初回のコンパイルが待ち合わせの timeout を使い切り、要素が出ないという別の症状になる。
- 遷移の直後に非同期の判定を挟むアプリでは、続けて出した遷移が巻き戻される。遷移の後は、URL が一定の時間変わらないことを待ってから次へ進む。

## 対話のツールで探索する

spec を書く前に、対話でブラウザを操作するツールで画面を操作して、spec に書く値を調べる。

- セレクタは、アクセシビリティのツリーの role と名前で取る。spec でも role と名前で書く。スナップショットのたびに変わる参照の番号は持ち込まない。
- 操作ごとに、次の操作に進む前に待つ状態（現れる要素、変わる URL、届く API の応答）を書き留める。API の応答を待つときは、操作の前に待ち始める。操作の後に待ち始めると、先に届いた応答を取り逃がす。
- 撮影のために足す操作（拡大、スクロール）が要るかを、ここで決める。
- 調べた結果は、作業の出力の置き場に、手順書の文、操作、セレクタ、待つ状態を並べた表で残す。表の行は、spec の `step` と `check` に 1 つずつ対応させる。

対話のツールで撮るときは、次に気を付ける。

- コマンドを 1 つずつ打って撮ると、録画が途中で止まることがある。手順を bash のスクリプトにして流す。zsh では、引用符のない変数が単語に分かれず、座標が渡らない。
- 録画を始めると、ブラウザのコンテキストが開き直されることがある。録画を始めた後に、画面を開き直してから操作を始める。
- 画面が変わらない間のフレームが落ち、動画が実時間より縮むことがある。手順をゆっくり見せる必要があるときは、spec で撮る。縮んだ動画を使うときは、縮んでいることを README に書く。
- タブの増減は録画に映らない。ツールが出すタブのタイトルと URL の一覧を一次の証跡にする。タブの一覧を出す操作がフォーカスを移すことがあるので、操作するタブに戻してから値を取る。

## AI のステップを持つテストのツール

- 観点の操作と判定は、確定した操作と `expect` で書く。AI のステップは、観点の前提を作る手順にだけ使い、直後に前提ができたことを確認する。
- 観点の操作を AI のステップに任せない。似た名前のボタンを押し間違えても成功を返し、その操作が記録されて次からも同じ誤りを再生することがある。
- AI に判定させるステップは、回ごとに判定が揺れうる。確定した判定と組にし、AI の判定だけで合否を決めない。
- AI のステップを使ったときは、モデル、呼び出し回数、トークン、所要時間を証跡に写す。

## trace

trace のファイルには、リクエストの URL がそのまま残る。API キーをクエリ文字列に載せるアプリでは、キーが入る。issue と pull request に添付しない。
