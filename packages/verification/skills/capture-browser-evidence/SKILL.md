# capture-browser-evidence

エビデンスは、レビューする人が同じ判断に到達できる状態にする。録画に映らない事象は、テキストのエビデンスと組みで残す。

## 始める前に読むもの

- 利用者の `context/testing/evidence.md`。撮影の手段（ブラウザを操作するツール、録画の設定、撮るコマンド）、撮る環境、ログインとテストデータ、公開してよい範囲を持つ。食い違うときは context に従う。手段が書かれていなければ、利用者に尋ねる。
- 撮る仕組みで間違えやすい点: [references/recording.md](references/recording.md)

## 進め方

1. context から撮影の手段を決め、[references/recording.md](references/recording.md) の該当するセクションを読む。
2. 撮る。条件を切り替えるたびにサーバを立て直し、配信元を確認する。
3. 録画を H.264 の mp4 へ変換する。
4. 出す前のチェックリストを応答に写し、全部を満たすまで 2 か 3 に戻る。
5. README を書き、置き場所に置く。pull request と issue の本文に入れるときは、スキル attach-evidence に従う。

## 手段の選び方

- エビデンスは、観点ごとに書いたブラウザのテストのコード（spec）で撮る。pull request が更新されたときも、同じ spec で撮り直せる。
  - spec で撮るときは、書き方はスキル write-verification-spec に、流し方と確認はスキル run-verification-scenarios に従う。このスキルからは、置き場所と名前、形式の変換、録画に映らないものの扱いを使う。
  - 利用者の context に録画の仕組みがなく、字幕とカーソルを重ねたいときは、`references/` の下の、撮影の手段の名前のディレクトリにある雛形を利用者のリポジトリへ写す。写すかは利用者に尋ねる。
- 対話でブラウザを操作するツールは、spec を書く前の探索に使う。画面の流れ、セレクタ、待つ状態を調べ、spec に移す。
  - 対話のツールでエビデンスを撮るのは、spec を書くほどではない 1 回きりの再現と、自動化できない認証（SSO など）を通る画面だけにする。
- テストのコードが張るネットワークのモックは、テストが起動したブラウザの中でだけ応答を差し替える。ほかの手段で開いたブラウザでは当たらない。
- テストのツールが起動するブラウザのエンジンは、ブラウザのアプリそのものではない。エビデンスには、どの層で測ったかを書く。

## 画面の大きさ

撮るときの viewport は、利用者の context の値にする。書かれていなければ 1920x1200 にする。  
録画のサイズを viewport と揃える。揃えないと縮小され、文字が読めない。対象のテストや設定の既定が違っても、撮るときは上書きする。

## 録画に映らないもの

- タブバー、タブの増減、ネイティブのダイアログ、拡張機能の UI、console、API のレスポンス、`sessionStorage` などの内部状態は映らない。
- 手順の説明は、録画の上端に字幕で重ねる。ページを読み込むたびに実行するスクリプトで重ねれば、対象のアプリの画面にも重ねられる。手順ごとに 1.5 秒ほど止める。
- マウスのカーソルは録画に映らない。位置と押下を描く要素を重ね、色の凡例を字幕と README に出す。
- 検証用のページを自分で作れるなら、判定に使う値を表で描画し、状態が変わるたびに描き直す。
  - イベントは発火の回数を描画する。起きなかったことのエビデンスになる。
- 作れないページでは、ページの中で評価した値をログに残し、録画と並べて読む前提にする。
- 入力のデータを作れるなら、合計から組み合わせが一つに決まる値を置く。9 件の数量を 1、2、4、…、256 にすると、合計 73 は 1 と 8 と 64 の 3 件と決まる。
- 画面の値は、判定のその場でページの中から取る。一度だけ描画するページでは、画面のテキストが変化の前の値のまま残る。ハッシュでの遷移で起きやすい。

## 判定の外で起きたこと

判定の値が正しくても、判定の外で画面が失敗を示していることがある。モックの応答がアプリの成功の形でないと、テストは通ったまま失敗の通知が出る。

- 判定の瞬間の 1 枚だけでなく、録画の全体を 1 秒ごとのコンタクトシートで見る。通知、エラーの表示、想定外のダイアログを探す。コンタクトシートの作り方は、スキル run-verification-scenarios の「確認する」にある。
- 登録、保存、削除を含む観点では、成功の通知が出たことか、失敗の通知が出ていないことも判定に入れる。

## 配信元の間違い

応答があっても、配信元の証明にならない。条件を切り替えるたびにサーバを立て直し、そのブランチにしかない語を配信されたソースで確認する。手順は [references/recording.md](references/recording.md) の「ローカルのサーバの間違い」にある。

## 置き場所と名前

パッケージ verification のスキルが撮るエビデンスの元のファイルは、全部この規則で置く。

置き場所は、`context/project.yml` の `verification.evidence_dir` にする。書かれていなければ `.ai-out/evidence` にする。`context/testing/evidence.md` に指定があれば、そちらに従う。

- `<置き場所>/<検証名>/` の下に、`README.md`、比べる条件（改修の前後、エンジン、権限）ごとのディレクトリ、判定の瞬間の静止画を置く `frames/` を作る。
- `<検証名>` は、エビデンスを入れる先で決める。
  - pull request の本文に入れるときは、その pull request の番号にする。pull request を作る前に撮るときは、issue の番号にする。
  - 検証のシナリオのエビデンスは、`context/testing/evidence.md` の Verification Scenarios にある名前の決まりに従う。
  - どちらでもないときは、検証の内容が分かる英小文字、数字、ハイフンの名前にする。
- 条件のディレクトリは、形式ごとに `mp4/` と `webm/` に分ける。`webm/` は倍率を変えて変換し直すために残す。
  - 字幕とカーソルの雛形で撮るときは、条件のディレクトリを作らず、`<検証名>/` の直下に `mp4/` と `webm/` を置く。条件はファイル名に入る。
- ファイル名は `<条件>-<spec のファイル名>-<連番>-<画面名>-<テストケース名>.mp4` にし、英小文字、数字、ハイフンで書く。issue や pull request の上ではファイル名しか見えない。
  - 比べる条件がないときも、`<条件>` に撮った条件の名前（改修後なら `after`）を入れる。
  - テストケース名は、観点の条件と期待結果から作り、要約しない。手動の操作では、確認した観点を入れる。
  - 連番は spec ごとに 1 から振る。ツールの既定の名前を残さない。

## 形式の変換

ブラウザのツールの録画は WebM（VP8）のことが多く、OS の標準のプレイヤーとホスティングサービスのプレビューで再生できないことがある。

```bash
bash {このスキルのディレクトリ}/scripts/convert-captures.sh <dir>          # <dir>/webm を <dir>/mp4 へ H.264 で変換する
bash {このスキルのディレクトリ}/scripts/convert-captures.sh <dir> -s 1.8   # 尺を 1.8 倍に引き伸ばす
```

- 終了コード 0: 全部の出力が H.264 で、尺があることまで確認した。
- 終了コード 1: 引数の誤り、ffmpeg か ffprobe がない、`.webm` がない、出力が H.264 でない。標準エラーを読んで直す。
- 引き伸ばしはフレームを補間せず、かくつく。遅くするのは撮るときを優先する。
- 判定の瞬間の静止画は、操作の中で撮れるならページのスクリーンショットで撮る。録画はページを開いた直後の何も描いていない間を持たず、動画の時刻と操作の時刻が 1 秒ほどずれるため、時刻で抜くと前後の画面を拾う。
- 操作の中で撮れないときは、変換した mp4 から抜く。`.webm` から位置を指定して 1 枚だけ抜くと、シークがずれて手前のフレームを拾うことがある。

## README

動画だけを置かない。README には、何を示すエビデンスか、ファイル名と検証の内容の対応、画面のどの値で結論が出るかを書く。

- 確認した内容（codec、尺、目視したフレーム）を書く。行っていない確認は、行っていないと書く。
- 撮るあいだに分かった罠と、撮り直すコマンドを書く。個人の絶対パスを埋めない。検証用の HTML、スクリプト、設定も残す。
- 雛形で撮るときは、雛形が撮るたびに README を書き直す。確認した内容、撮るあいだに分かった罠、撮り直すコマンドの 3 つは、README とは別のファイルか、添付する本文に書く。

## 出す前のチェックリスト

```
- [ ] 録画を再生し、判定の瞬間の静止画を開いて見た
- [ ] 録画の全体をコンタクトシートで見て、判定の外に失敗の通知や想定外の表示がない
- [ ] 録画に映らない事象は、テキストのエビデンスと組みで示している
- [ ] 手順の字幕とカーソルが映り、検証の手順にない撮影のための操作には、そうと分かる字幕を付けた
- [ ] 測った層（エンジンかアプリか）を書き、エンジンの結果をアプリの結果として書いていない
- [ ] 操作するタブを間違えて取ったログが入っていない
- [ ] 録画を始めたときに状態が作り直された影響を、読み方に反映した
- [ ] 撮るときの速度と等倍の両方で通る
- [ ] 条件ごとにサーバを立て直し、配信元を確認した
- [ ] API キーを含む URL を出力していない（API キーはクエリ文字列に乗る）
- [ ] 公開してよい範囲の外のデータ（ログインの値、トークン、実在の人のデータ）が映っていない
```

添付が通らないときは、テキストのエビデンスだけで判断できる形に組み替える。
