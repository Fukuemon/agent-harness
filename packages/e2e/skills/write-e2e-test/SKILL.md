# write-e2e-test

E2E のテストのコードを、落ちにくく、直す場所が 1 か所で済む形で書くための判断。  
機械で判定できる書き方は、e2e の kit のテストの書き方の lint の規則が止める。ここには、規則で判定できない判断だけを書く。

## 始める前に読むもの

- `context/project.yml` の `e2e.dir`。E2E のテストのディレクトリで、下の層のディレクトリはこの下に置く。書かれていなければ、利用者に尋ねる。
- 利用者の `context/testing/e2e.md`。テストのツールでの書き方、testid の名前の付け方、固定の待ちを許すファイル、画面 ID の形、流すコマンド、環境が書いてある。食い違うときは、context に従う。
- 同じ画面を触る、既にある spec を 1 本。

## 層

テストのコードは、次の 6 つの層に分ける。ディレクトリの名前は、lint の規則が読むので変えない。

| 層 | 持つもの | 持たないもの |
| --- | --- | --- |
| `specs/` | 何を確認するか。確認（assertion）を書く。要素を拾う関数と、1 から 2 本の spec しか使わない操作。`specs/<dir>/` には、その下の spec だけが共有する値も置く | ほかの `specs/<dir>/` からの import。値のファイルの中の画面の操作 |
| `setup/` | テストデータを作る手順。作る前に同じデータがあるかを確認し、あれば使う。作った結果を確認する | 画面の操作の本体 |
| `screens/` | 3 本以上の spec が使う「画面を開く、モードを変える」。中で待ち切る | 確認、通信の差し替え、複数の画面をまたぐ手順 |
| `widgets/` | 処理の完了が DOM に出ない UI（canvas など）の操作と待ち | 確認、通信の差し替え、画面 ID と URL |
| `selectors/` | testid を付けられない要素の指し方。外部のライブラリが作る DOM と、表示の文言 | 操作、待ち、確認 |
| `fixtures/` | 環境変数の読み取り、作るデータの名前、待つ時間の名前、テストデータの API、アプリの URL の形 | 画面の操作 |

- 依存は上の層から下の層へ張る。間の層は飛ばしてよく、spec から `widgets/` や `selectors/` を直に呼べる。下の層から上の層は呼ばない。
- `fixtures/` と kit は、どの層から使ってもよい。ログインと録画は kit を使い、spec に書き直さない。
- `widgets/` は、使う spec が 1 本でも置く。中を `actions/` と `waits/` に分け、`actions/` から `waits/` の向きにだけ依存する。操作は中で待ち切るので、呼ぶ側は待ちを書かない。
- `widgets/` は画面を知らない。testid の接頭辞は引数で受ける。同じ UI が複数の画面に埋め込まれるためである。

## どこに書くか

特に理由がなければ spec に書く。ほかの層に置くのは、次の問いに当たるときだけにする。

| 問い | はい | いいえ |
| --- | --- | --- |
| テストデータを作るか | `setup/` に書く | 次の問いへ |
| 拾う要素はアプリが描くか | testid を付けて、testid で拾う | `selectors/` に指し方を置き、そこから呼ぶ |
| 操作の完了は要素や文字に出るか | 待ちを書かず、確認の自動の待ちに任せる | kit か `widgets/` の操作を呼ぶ。無ければ、操作と待ちを `widgets/` に足す |
| 同じ「開く、モードを変える」を 3 本目の spec が要るか | `screens/` に移して 3 本から呼ぶ | spec に書く |

- `screens/` に移すかは、3 本目が要った時点で 1 回だけ判断する。数えるのは export ごとにする。1 本の spec だけのために共有の関数を作らない。
- 複数の画面をまたぐ手順は、spec に書く。`screens/` に書くと、ある画面のファイルが別の画面を知る。
- DOM に完了が出る共通の UI（表、日付の選択）は `widgets/` にせず、spec から testid で操作する。
- テスト用のクラス（Page Object）は作らず、ページを引数に取る関数を並べる。共有するのは、3 本以上が使う関数だけにする。

## 名前

spec の置き場とテストの名前は、テストが守る振る舞いで付ける。issue は閉じるが、振る舞いは製品に残るためである。

- `specs/` の下のディレクトリは、機能の名前にする。アクター、検証の観点、issue の番号、変更の向き（新しい挙動、移した後）の名前は使わない。
- ファイルは、機能の中の振る舞いで切る。同じ振る舞いを複数の画面で確認するなら 1 つのファイルにまとめる。
- テストのまとまりは、外側を画面、内側を機能の 2 段にする。アクターの違いは、機能の中のまとまりで表す。
- テストの名前は「{条件}の場合、{期待}であること」にする。観点の ID と規約の ID は、名前にもコメントにも書かない。
- 手動の検証のエビデンスを撮る spec の置き場と名前は、利用者の context にある。決まっていなければ、利用者に尋ねる。
- pull request と issue に添付するエビデンスは、入れる先の `issue-<番号>` か `pr-<番号>` の置き場に撮る。pull request を作る前に撮ったなら issue の番号にし、作った後も使い続ける。改修前と改修後が別の置き場に分かれないためである。

## 待ち方

固定の秒数で待たない。何が終わったかを条件にする。  
完了が要素か文字に出るなら、待ちを書かずに確認の自動の待ちに任せる。出ないときは、次の 6 種類から選ぶ。

| 待ち方 | いつ | 何を待つか |
| --- | --- | --- |
| 読み込み表示の出現と消滅 | 読み込み表示が出る画面を開いた直後 | 表示が出てから消えるまで |
| 取り直しのレスポンス | 表示の条件を切り替えた後 | データを取り直す API のレスポンス |
| 選択の状態 | 状態が変わるボタンを押した後 | ボタンが選択の状態（`aria-pressed="true"` など）になったこと |
| 前後の確認 | 「起きないこと」を確認するとき | 判定の前に描画が終わったことを示す要素を待ち、後に「起きる」側の確認を置く |
| データの到着 | データが要る操作の前 | そのデータを返す API のレスポンス |
| 画面の到達 | 画面を開くとき | 画面が出たことを確認してから、次の準備を待つ |

待ち方を間違えても、エラーにならずに通り過ぎる。

- 読み込み表示が消えるのだけを待つと、読み込みが始まる前の時点で条件を満たす。
- 通信が 2 つある画面で片方だけを待つと、もう一方のデータが届く前に操作へ進む。両方のレスポンスを待つ。
- 値を読んでから比べない。要素をそのまま確認に渡し、自動の待ちを働かせる。リクエストの中身や URL のように、要素で表せない値は、読んでから比べてよい。

## 確認の方法

テストは、誤った実装で落ちなければ役に立たない。

- 「起きないこと」は、変わらないことを繰り返し評価して確認しない。初回の評価で通る。後に起きる別の実際の出来事を待ってから、回数や状態を確認する。
- ラジオは、選び直すと前の選択が外れることまで確認する。複数選択は、選んだ値がリクエストに全部載ることを確認する。
- 既にあるテストから操作の列をコピーするときは、その操作が初期値に対して何をするかを先に確認する。初めから選ばれている項目を押すと、選択を外す動きになる。
- 共通のコンポーネントに渡した testid で入力の値を確認するときは、testid を起点に中の入力の要素に辿る。選択の「空であること」は、文字ではなく値で確認する。

次の場面では、[references/situations.md](references/situations.md) の該当のセクションを読む。

- 新しいタブを開く画面を確認する
- 一定の間隔で取り直す画面や、日付で表示が変わる画面を確認する
- アプリのコンポーネントに testid を付ける

## 規則が止めないこと

lint の規則は、層ごとの確認と通信の差し替え、testid でない要素の指し方とセレクタの文字列での操作、spec の import、`widgets/` の画面 ID と遷移を止める。  
待ち方では、固定の待ち、通信が止まるのを待つこと、spec の中の待つ時間、値を読んでからの比較の一部を止める。options は、利用者の lint の設定で渡す。  
次のものは規則で判定できないので、書くときとレビューで見る。

- 「起きないこと」を、前後の確認なしに確認する。
- 読み込み表示が消えるのだけを待つ。
- 要素の数や表示を読んでから比べる。規則が止めるのは、文字と値の読み取りだけである。
- `screens/` の関数を `specs/<dir>/` の値のファイルで呼ぶ。
- ボタンを並びの位置で指す。名前で指す。
- 確定や削除のダイアログを、文言を確認せずに押す。

## 待つ時間

spec に時間を書かない。全体の時間はテストのツールの設定に、個別の時間は `fixtures/` の名前で置く。  
内側から、確認 < 操作 < 外部の読み込み（ID 基盤のログインなど）< テストの全体の順に長くする。どの層で落ちたかを、失敗の形から見分けられる。  
値は勘で決めない。複数の CI の実行から、成功したテストごとの所要時間を集め、最大の所要に振れの倍率を見込んで決める。確認の時間は、時間切れが起きるまでテストのツールの既定のままにする。

## 書いたら

1. 利用者の `context/testing/e2e.md` にある lint と型のチェックを流す。
2. 書いた spec を 1 本だけ流す。
3. 期待を一時的に逆にして、落ちることを確認してから戻す。落ちなければ、確認の方法を直す。
