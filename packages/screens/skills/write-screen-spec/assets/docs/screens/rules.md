# 画面仕様書の規約

画面仕様書のページ、API との対応、画面のモックの書き方。画面の ID の決め方は [画面仕様書の目次](index.md#画面の-id-の規則) にある。  
このディレクトリの場所は、`context/project.yml` の `screens.dir` に書く。

## 配置先と名前

画面ごとに 1 つのディレクトリを作り、テンプレートの `_template/` をコピーする。

```text
<screens.dir>/
├── _common/                    # 全ての画面のモックが読む CSS と JS。画面のディレクトリにコピーしない
│   ├── mock.css                # 外枠、構成番号の印、ツールバー
│   ├── wireframe.css           # 箱と線の見た目（wf-*）。色と角丸は --wf-* に当てる
│   ├── mock.js                 # デバイスの切り替え、構成番号の印、親のページへの高さの通知
│   ├── interact.js             # 画面の中の操作（モックの間の移動、チェック、開閉）
│   └── embed-mock.js           # 仕様書のページで読み、埋め込んだモックの高さを中身に合わせる
├── _template/                  # テンプレート。サイトに載せない
└── <画面 ID>_<画面の名前>/
    ├── index.md                # 仕様書のページ
    ├── api.md                  # 画面の項目と、画面の型、API の項目の対応
    └── mocks/
        ├── <画面 ID>.css       # この画面のモックだけの見た目
        ├── 01-initial.html     # 状態ごとに 1 枚
        └── 02-<状態>.html
```

- コピーした後に、`mocks/screen-id.css` の名前を `mocks/<画面 ID>.css` に変え、モックの `<link>` も直す。
- ディレクトリの名前は、画面 ID と日本語の画面の名前を `_` でつなぐ（例 `order-list_注文の一覧`）。URL とテストは画面 ID だけを使うので、名前を変えるときはディレクトリの名前だけを変えてよい。
- モックの名前は、2 桁の連番と状態の英語の名前を `-` でつなぐ。連番は、ページに並べる順にする。
- ページを足したら、目次の画面の一覧に足す。文書のサイトにナビゲーションの設定があれば、そこにも足す。

## 仕様書のページ

1 行目は `# <画面 ID> <画面の名前>` にし、その下に画面の用途を 1〜2 文で書く。続けて、URL、使う人、実装の表を置き、`api.md` へリンクする。

セクションは次の順に置く。

| セクション | 書くこと |
| --- | --- |
| 構成 | 状態ごとに 1 つのタブ（`=== "状態の名前"`）を置き、中にモックの iframe、別タブで開くリンク、構成要素の表を置く |
| 要素ごとのセクション（`## <要素名>`） | 構成要素の表の要素ごとに、概要、値のソース、活性条件、表示条件、カタログ、インタラクション |
| 全体動作 | 初期処理、複数の要素にまたがる動き、URL の search params からの復元 |
| 未決 | PRD と実装が食い違うところと、仕様として決まっていないところ |

- 処理と通信は書かない。画面の機能の Design Doc に書く。
- タブは `=== "<状態の名前>"` の行で始め、中身を 4 つの空白で字下げする。タブの名前は状態の名前にする。
- タブの中の最初に、その状態になる条件を 1 文で書く。
- 状態はアンカーを持たないので、本文から状態を指すときはリンクにせず、「「<状態の名前>」の状態」と書く。
- iframe は `<iframe class="mock" title="…" src="mocks/…">` と書く。直後には、`<a class="mock-open" href="mocks/…" target="_blank">別タブで開く</a>` を置く。
  - 高さは書かない。仕様書のページで読む `_common/embed-mock.js` が、中身に合わせる。
  - `<details>` の中には入れない。タブの中は、タブを開いたときに `mock.js` がデバイスと番号を測り直す。
- ページの中の生の HTML は、この iframe と a だけにする。

### 構成要素の表

列は `番号 | 種別 | 要素名 | 仕様` にする。

- 番号は、状態ごとに 1 から欠番なく振る。表の番号の集合と、モックの `data-m` の値の集合を同じにする。同じ番号を複数の要素に付けてよい（一覧の行など）。
- 種別は、画面の上で何を指すかが分かる語にする（ボタン、リンク、テキストボックス、チェックボックス、ラジオボタン、セレクト、ファイルの選択、表、カラム、領域、ラベル、ダイアログ、覆い、メッセージ）。表の列見出しは「カラム」、行の値は「ラベル」、見出しの下の列全体は「領域」と書き分ける。
- 要素名は、利用者が画面の上で呼ぶ名前にする。ダイアログのタイトルやページのタイトルのように文言そのものが仕様のものも、要素にする。
- 仕様の列は、要素ごとのセクションへのリンクにする。
- 要素は、それが見える状態の表にだけ載せる。ほかの状態でしか見えない要素を載せない。

### 要素ごとのセクション

```markdown
## <要素名>

**概要**: 要素の用途と役割

**値のソース**: 利用者に見える値。文言は「」で引く

**活性条件**: 押せる（入力できる）条件。常に押せるなら「常に活性」

**表示条件**: 表示する条件と状態。常に出すなら「常に表示」

**カタログ**: [<コンポーネント> の <ページ>](<カタログの URL>)

### インタラクション

#### 1. <操作>

1. 結果
```

- 4 つの欄（概要、値のソース、活性条件、表示条件）は、デフォルト値（常に活性、常に表示）でも省かない。
- カタログの欄は、コンポーネントのカタログを持つときだけ書く。リンクの先は、画面の文言とデータで要素を見せるページにする。
  - 要素を描くコンポーネントのうち、カタログのページがあり、そのページに要素が出るいちばん小さいものを選ぶ。ページは、仕様書の状態に近いものを選ぶ。
  - 画面のコンポーネントのどのページにも要素が出ないときだけ、共通のコンポーネントのページを選ぶ。どのページにも出なければ欄ごと省く。
  - リンクは、`context/project.yml` の `screens.catalog_url` で始まる URL で書く。
  - 1 つの要素を 2 つ以上のコンポーネントが描くとき、仕様書の 2 つ以上の状態を別のページが描くときは、リンクを「、」でつなぐ。
- インタラクションは、操作を起点に画面が変わるものだけを書く。無ければセクションごと省く。
- 変数名、型、API の名前は書かない。それらとの対応は `api.md` に書く。

## API との対応

`api.md` は、仕様書の要素名ごとに、表示する値、画面のコードが使う型の項目、API の項目（操作と項目）を表にする。画面を作る人と API を変える人が読む。

## 画面のモック

モックは、1 つの状態を 1 枚の HTML で描く。画面の中で完結する操作（ダイアログを開く、タブを切り替える）の結果も、別の状態のモックにする。状態のモックの間は、[画面の中の操作](#画面の中の操作) の `data-go` でつなぐ。

例外として、幅で出し分ける開閉式の要素（幅 768px 未満だけで出すドロワーやメニュー）は、別の状態のモックにしない。各状態のモックに描き、閉じた状態で始め、[画面の中の操作](#画面の中の操作) の `data-panel` で開閉する。

### 構造

```html
<body data-view="desktop">
  <div class="stage">
    <div class="screen">
      <div class="screen-body"><!-- 画面 --></div>
    </div>
    <div class="markers"></div>
  </div>
  <script src="../../_common/mock.js"></script>
  <script src="../../_common/interact.js"></script>
</body>
```

- body の末尾で `../../_common/mock.js`、`../../_common/interact.js` をこの順に読む。ほかの script は書かない。
- head で `../../_common/mock.css`、トークンの CSS、`../../_common/wireframe.css`、`<画面 ID>.css` をこの順に読む。
  - トークンの CSS は、`context/project.yml` の `screens.tokens_css` に書いたファイルを、モックからの相対パスで読む。キーが無ければ読まない。
- `body` の `data-view` は最初に見せるデバイスにする。表示の幅が 600px 未満のとき（スマートフォンで仕様書を読むとき）は、`data-view` によらずモバイルで描く。`mobile`（390px）、`tablet`（768px）、`tablet-wide`（1024px）、`desktop`（1440px）から選ぶ。値は `mock.js` の `VIEWS` にだけ書く。
- サイトのヘッダーとナビゲーションは、その画面の構成要素にするときだけ描く。

### 構成番号と data-testid

- 構成要素の表の要素に `data-m="<番号>"` を付ける。座標は書かない。`mock.js` が要素の左上に番号の印を重ねる。
- 構成番号は、その状態で見える要素にだけ付ける。
- 幅で出し分ける開閉式の要素と、それを開いて初めて見える要素は、その状態で見える要素として扱い、同じ状態の表に載せて `data-m` を付ける。
  - `mock.js` は見えない要素に印を置かないので、印は開いたときに出る。
  - どの印が開くと出るかと、どの幅で出すかを、仕様書の構成のセクションかその状態の説明に、要素の名前で書く。
- テストが指す要素に `data-testid` を付ける。画面の testid は、モックの `data-testid` を元にする。
  - 形は、小文字の英語と数字を `-` でつなぎ、`<画面か部品>-<要素>` にする（例: `order-list-submit`）。
  - 一覧の行のように同じ要素が並ぶものは、末尾に `{…}` を付ける（例: `order-list-row-{注文の ID}`）。`{…}` には、どの値が入ってもよい。
  - 区分のように API の値を末尾に付けるときは、値の `_` をそのまま残す（例: `order-summary-in_progress`）。
  - テストが使う testid は、どれかのモックにある値か、モックの `{…}` の形に当たる値にする。`context/project.yml` に `screens.e2e_dir` があれば、点検がテストのコードの testid をモックと照らす。
- 例外として、全ての画面に共通する状態（[目次の全ての画面に共通する状態](index.md#全ての画面に共通する状態)）はモックを持たず、testid は目次のセクションに書く。点検は画面のディレクトリのモックだけを読むので、テストがその testid を指すときは、共通の状態を描く画面のモックを足す。
- ツールバーの「data-testid」を入れると、番号の印の横に testid を出す。

### 幅と配置

- 幅による切り替えは `@container screen (width < 768px)` のように `.screen` の幅で書く。viewport の寸法の `@media`、`vh` と `vw` は使わない。モックの中では、viewport の幅はデバイスの幅と一致しない。
- スクロールする場所は作らず、画面の高さは中身に合わせる。ただし、実装が横に送る表は、モックでも横に送ってよい。
- ダイアログ、覆い、トーストは、`.screen` の中に `position: absolute` で置く。`position: fixed` は使わない。
- 色、角丸、書体は `wireframe.css` の変数（`--wf-*`）で書く。
  - トークンの CSS を読むときは、`wireframe.css` の `:root` で意味のトークンを `--wf-*` に当てる。足りない色は、意味のトークンを `--wf-*` に当てて足す。
  - 基本のトークンと 16 進の色は、画面の CSS に直に書かない。`wireframe.css` の `:root` で `--wf-*` に当てるときだけ使う。
- 画面だけの見た目は `mocks/<画面 ID>.css` に書く。2 つ以上の画面で使う見た目は `_common/wireframe.css` に移す。

### 禁止

- 外部の読み込み。HTML、CSS、JS に `http` で始まる URL を書かない。フォントはシステムのもの、アイコンはインラインの SVG にする。
- 実在の組織、人、連絡先。ダミーデータで描く。
- ダークモードの切り替え。

### 画面の中の操作

モックの押せる要素には、仕様書のインタラクションのセクションに書いた操作を付ける。  
処理は `_common/interact.js` が持ち、モックは要素の属性で操作を指す。属性は次のとおり。

| 属性 | 押したときの動き | 付ける要素の例 |
| --- | --- | --- |
| `data-go="<モック>"` | 指したモックへ移る | 状態を変えるタブと項目、ダイアログを開くボタン、閉じるボタンと背景、送信のボタン、別の画面へのリンク |
| `data-toggle` | `is-on` を付け外す | チェックボックス、トグル |
| `data-choice="<組の名前>"` | 押した要素に `is-on` を付け、同じ組のほかの要素から外す | ラジオボタン、チップ |
| `data-open="<名前>"`、`data-close="<名前>"` | `data-panel="<名前>"` の要素に `is-open` を付け外し、開くボタンの `aria-expanded` を変える | 幅で出し分けるドロワー、メニュー |
| `data-escape` | Escape キーで押す。見えている要素だけが動く | ダイアログとドロワーの閉じるボタン |

- `data-go` の先は、同じ画面のモックならファイルの名前（`03-detail.html`）、別の画面のモックなら `../../<画面のディレクトリ>/mocks/<モック>.html` と書く。
  - 先は、インタラクションのセクションの結果に最も近い状態のモックにする。詳細のダイアログの閉じるボタンなら、ダイアログを開く前の一覧の状態へ移る。
  - デバイス、構成番号、data-testid、幅に合わせるかの選択は、URL の search params で移った先に引き継ぐ。仕様書のページの iframe の中では、iframe の中で移る。
  - 移った先は、その状態のモックの値で描く。前のモックで変えたチェックと選択は引き継がない。
  - ファイルの選択は、ファイルの選択のダイアログを開かず、ファイルを選んだ後の状態のモックへ移す。
- 次の操作には属性を付けない。
  - API の呼び出し、保存、ダウンロード、ログアウト、ブラウザの確認のダイアログ
  - 当たる状態のモックが無い操作。期間を変える操作、文字の入力、送信中の状態から結果への移り
- 押せる要素には `interact.js` が `tabindex="0"` を付け、Enter と Space でも動かす。背景のように、キーボードで押さなくてよい要素には `tabindex="-1"` を書く。`aria-disabled="true"` の要素は押しても動かない。
- `interact.js` は、role の無い押せる要素に role を付ける。`data-toggle` には `checkbox`、`data-choice` には `radio`、ほかには `button` を付け、`checkbox` と `radio` の `aria-checked` を `is-on` に合わせる。role を書いた要素、`tabindex="-1"` の要素、`button` と `a` と `input` には付けない。
- `interact.js` は、表示を変えた後に `mockRefresh()` を呼び、番号の印を置き直す。
- `data-panel` に `data-panel-modal` も付けると、開いている間は panel の外の要素の印を出さない。デバイスを切り替えると、開いている panel を閉じる。
- panel を開くと、panel の中の最初のフォーカスできる要素へフォーカスを移す。閉じると、見えている開くボタンへフォーカスを戻す。
- 属性で書けない操作が要るときは、モックに script を書かず、`interact.js` に属性を足す。

モックの印の位置は、CSS の `zoom` を標準の形で扱うブラウザで確認する。

## 点検

スキル write-screen-spec の `scripts/check-screens.mjs` が、規約のうち機械的に確認できるものを見る。

- 名前と仕様書: ディレクトリとファイルの名前、仕様書の 1 行目と生の HTML、状態のタブ、iframe と別タブのリンク、構成要素の表の見出し
- 番号: 表の番号とモックの `data-m` の一致、`data-m` の連番
- 操作: `data-go` の先のモックがあるか、`data-open` と `data-close` の名前の `data-panel` があるか、属性の値が空でないか、`data-escape` を操作の属性を持つ要素に付けたか
- モック: 構造と読み込みの順、`data-view`、`data-testid` の形、禁止の記述と幅と配置の規則（外部の URL、`position: fixed`、viewport の単位と寸法の `@media`、ダークモード）
- テンプレートの `<…>` の消し忘れ（`index.md`、`api.md`、モック、画面の CSS）
- カタログ: `screens.catalog_url` があるとき、カタログの欄にリンクがあり、全てがその URL で始まるか
- テスト: `screens.e2e_dir` があり、全ての画面を見るとき、テストのコードの testid がどれかのモックの `data-testid` にあるか

見た目（番号の位置、デバイスごとの崩れ）と操作は、モックを別タブで開き、ツールバーでデバイスを切り替え、押せる要素を押して確認する。
