# write-screen-spec

書き方の規則は、利用者のリポジトリの画面仕様書の規約（`<screens.dir>/rules.md`）が持つ。このスキルは、規約に沿って作業を進める順と、確認の方法だけを持つ。規則をここに写さない。  
`screens.dir` は `context/project.yml` にあり、省くと `docs/screens` になる。

作業の最初に、`<screens.dir>/rules.md` の全文と、`<screens.dir>/index.md` の「画面の ID の規則」を読む。`rules.md` が無ければ、下の「初めて使うとき」を先に行う。規約と食い違うことをこのスキルで見つけたら、規約を直す変更として分けて提案する。

スクリプトは、どれもリポジトリのルートで流す。

## 初めて使うとき

`context/project.yml` に `screens` のキーが無ければ、次の値を利用者に 1 度にまとめて尋ね、`screens` の下に 1 行ずつ書く。

- `dir`: 画面仕様書の置き場。既定は `docs/screens`。
- `tokens_css`: モックが読むトークンの CSS のパス。トークンの CSS が無ければ省く。
- `catalog_url`: コンポーネントのカタログの URL。カタログが無ければ省く。
- `e2e_dir`: testid をモックと照らすテストのコードのディレクトリ。テストが無ければ省く。

`context/project.yml` にほかのパッケージのキーで同じ値（トークンの CSS のパス、カタログの URL、テストのディレクトリ）があれば、尋ねるときに候補として示す。値はほかのキーから読まず、`screens` の下に同じ値を書く。

続けて、雛形を `<screens.dir>` へ写す。

```sh
node {このスキルのディレクトリ}/scripts/copy-screen-templates.mjs [--update]
```

- 終了コード 0: 写し終えた。既にあるファイルは上書きしていない。
- 終了コード 1: 既にある `_common/` の共通の処理が雛形と違う。出た差分を利用者に見せ、取り込むと決まったら `--update` を付けて流し直す。
- 終了コード 2: `screens` の値か引数が誤っている。値を直す。

写した後に、次をそろえる。

- `tokens_css` を書いたら、`<screens.dir>/_common/wireframe.css` の `:root` で、意味のトークンを `--wf-*` に当てる。
- 仕様書のページを描くサイトがあれば、仕様書のページで `<screens.dir>/_common/embed-mock.js` を読み込むよう設定する。サイトが、`source` が `screen-mock` のメッセージを受けるスクリプトを既に読んでいれば足さない。サイトの設定の仕方は、利用者の context か、サイトの設定ファイルを読んで決める。

パッケージを更新した後も、同じスクリプトを流して `_common/` の共通の処理を取り込む。

## 新しい画面を書く

1. 画面 ID と画面の名前を、目次の規則で決める。目次の画面の一覧に行を足す。
2. `<screens.dir>/_template/` を `<screens.dir>/<画面 ID>_<画面の名前>/` にコピーする。`mocks/screen-id.css` を `mocks/<画面 ID>.css` に名前を変え、モックの読み込みも直す。`tokens_css` があれば、モックの head に読み込みを足す。
3. 状態を、規約の「画面のモック」の数え方で決める。PRD と実装から、読み込み中、空、エラー、ダイアログを開いた状態、送信中のうち、この画面が取り得るものを拾う。
   - 幅で出し分ける開閉式の要素（幅 768px 未満だけのドロワー）は状態に数えない。各状態のモックに閉じた状態で描き、規約の「画面の中の操作」のとおり `data-panel` で開閉する。
4. 状態ごとにモックを書く。
   - 実装があれば、画面のコンポーネントを読み、配置、文言、`data-testid` を実装に合わせる。画面のコードの置き場は、利用者の `context/codebase.md` にある。
   - 共通の見た目は `<screens.dir>/_common/wireframe.css` の `wf-*` から探し、無いものだけを書く。配置先は規約の「幅と配置」にある。
   - 構成要素の表に載せる要素に、規約の「構成番号と data-testid」のとおり `data-m` を振る。
   - 開閉式の要素と、開いて初めて見える要素にも `data-m` を振り、開くと出る印を仕様書の状態の説明に書く。
5. 全てのモックを書いた後に、各要素のインタラクションのセクションの操作を、規約の「画面の中の操作」の属性でモックに付ける。
   - 操作ごとに、結果に最も近い状態のモックを `data-go` の先に選ぶ。先が別の画面なら、その画面のモックを指す。
   - 規約が属性を付けないとする操作と、当たる状態のモックが無い操作には付けない。
6. `index.md` を、規約の「仕様書のページ」のセクションの順で書く。
   - 処理と通信は書かない。画面の機能の Design Doc に書く。
   - 要素ごとのセクションの「値のソース」は、画面に出る文言を「」で引く。実装と PRD が食い違うときは、推測で埋めず、未決に書く。
   - カタログの欄は、`catalog_url` があるときだけ書く。ページは規約の「要素ごとのセクション」の選び方で選び、URL はカタログを開いて確認する。
7. `api.md` に、要素ごとの画面の型の項目と、API の項目（操作と項目）を書く。
8. 文書のサイトにナビゲーションの設定があれば、`index.md` を足す。
9. 下の「確認する」を行う。

## 確認する

1. 規約の点検を流し、違反を全て直す。1 画面だけなら、画面のディレクトリを引数に渡す。テストのコードの testid の確認は、引数を省いて全ての画面を見るときだけ動く。

   ```sh
   node {このスキルのディレクトリ}/scripts/check-screens.mjs [<screens.dir>/<画面のディレクトリ>]...
   ```

   - 終了コード 0: 違反なし。リテラルで始まらない testid の引数は照らさず、件数だけを出す。
   - 終了コード 1: 違反の一覧が出る。規約に合わせて直し、流し直す。
   - 終了コード 2: `context/project.yml` の `screens` の値か、`_common/mock.js` の置き場が誤っている。値を直す。
2. 利用者の CONTRIBUTING.md にある文書のチェックを、書いた `index.md` と `api.md` に流す。
3. ブラウザで、仕様書のページと、モックを別タブで開いたものを見る。
   - 仕様書のページでは、全ての状態のタブを開き、モックが描かれることを見る。
   - モックのツールバーの「デバイス」で 4 つのデバイスを切り替え、番号の印が要素の左上にあること、`@container` の切り替えで崩れないことを見る。
   - 主な操作を押し、移った先のモックか表示が変わること、デバイスの選択が保たれること、操作の後も番号の印が要素の上にあることを見る。仕様書のページの iframe の中でも押す。
   - スクリーンショットを撮ったら、画像を開いて中身を見る。描画の前の白い画面を、確認した結果にしない。
   - ブラウザを使えないときは、3 を「未確認」と報告する。
