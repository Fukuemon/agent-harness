# issue の書き方

- 種類は、要求、タスク、不具合の 3 つで、写された form を使う。要求は実現したいこと、タスクは要求を分解した実装の単位、不具合は期待と違う動作である。
- ラベルは、form が付ける `type:*` に加えて、対象のパッケージの `pkg:*` を付ける。
- 題の例は「【実装】リンクのチェックを追加する」で、コミットの要約と同じ動詞を使う。
- 接頭辞は、その issue が扱うプロセスで付ける。要求は【要求】、タスクは【設計】【実装】【検証】のどれか、不具合は【不具合】。
- 要求のあるべき姿は「〜できる」の形で書き、受け入れ条件はそれを確かめる箇条書きにする。現状は、関係する文書やコードへのリンクを添える。
- タスクの背景には、親の要求のどの部分を担い、何ができるようになるかを書く。親へのリンクだけにしない。
- タスクの対応方針は、どう対応するかを文で書く。リンクの一覧だけにしない。根拠になる Design Doc や ADR の節は、文の直後にリンクで示す。
- タスクの完了の条件は、コマンドと期待する結果まで書く。「動く」ではなく、「`node scripts/check-links.js` が切れたリンクを終了コード 1 で報告する」のように書く。
- タスクは親の要求の sub-issue にする。1 つのタスクは、1 つの pull request で閉じられる大きさにする。
