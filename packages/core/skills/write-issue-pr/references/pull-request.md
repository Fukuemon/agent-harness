# pull request の書き方

- 作業を始めた時点で、Draft の pull request を作る。進み具合が外から見える。実装が終わったら Draft を外す。
- 本文の先頭に `Closes #<番号>` を書く。
  - 1 つの issue を複数の pull request に分けたときは、最後の pull request だけに `Closes #<番号>` を書き、ほかは `Refs #<番号>` を書く。途中の pull request のマージで issue が閉じるのを防ぐ。
  - 分けた pull request のタイトルは、issue のタイトルの後に「（n/m 内容）」を付ける。例は「【実装】リンクのチェックを追加する（1/2 スクリプト）」。数が決まっていなければ「（n 内容）」にする。
- 本文は、写されたテンプレートの 8 節で、テンプレートの順に書く。節を足したり、名前を変えたりしない。検証とエビデンスの節は、動作を確かめない変更では消す。ほかの節は消さず、書くことが無ければ「なし」と書く。節がそろっていると、読む人と自動のチェックが、書き忘れと「なし」を見分けられる。概要は 2 文から 3 文で、差分を読む前の地図にする。対応内容は、関心事ごとの箇条書きにし、コミットの分け方と揃える。
  - 1 段目は関心事で、太字の名前に「新規」「変更」「削除」を添え、ファイルが 1 つのディレクトリに集まるならそのパスを続ける。
  - 2 段目はファイルかディレクトリごとに、何をどう変えたかを書く。ファイルの一覧を書き写さない。判断した理由は「背景」に書く。
- 背景は、issue と違う点や、作業中に分かったことだけを書く。issue の繰り返しにしない。
- 確認したことには、実行したコマンドと結果を書く。確かめていないことは「未実施」と理由を書く。
- 検証とエビデンスには、動作を確かめた観点ごとに、確かめ方、結果、エビデンスを 1 行に並べた表を置く。
  - 観点は、外から観測できる結果を条件とともに書いた要件の文にする。確かめ方には、観点を確かめたテストの名前か手順を書く。
  - エビデンスの動画とスクリーンショットは、コメントではなく本文に載せる。レビューする人が、観点を読んだ場所で開ける。コメントは、撮り直したことの通知と、本文が上限を超えたときにだけ使う。
  - 確認したことには、観点に結び付かない自動のチェック（lint、型、テストの全体）を書く。
- 影響には、使う人やほかのリポジトリへの影響と、互換性のない変更の有無を書く。互換性のない変更は、コミットメッセージにも `!` か `BREAKING CHANGE` を付ける。次のバージョンを決める手段が読むためである。
- レビューしてほしい点には、判断が分かれた箇所と、捨てた代替案の理由を書く。
- 扱わなかったことは「残したこと」に書き、issue があれば番号を添える。
- レビューに対応してコミットを足したら、返信と同じときに本文を差分に合わせて直す。対応内容、背景、確認したこと、検証とエビデンス、レビューしてほしい点、残したことのうち、変わった節を書き換える。
  - 本文は、マージする差分の説明である。古いままだと、差分を読む前の地図にならない。
  - 「レビューで直した点」のような追記の節を作らない。経緯はコミットと返信が持つ。
