# pull request の書き方

- 作業を始めた時点で、Draft の pull request を作る。進み具合が外から見える。実装が終わったら Draft を外す。
- 本文の先頭に `Closes #<番号>` を書く。
- 本文は、写された雛形の 7 節で書く。概要は 2 文から 3 文で、差分を読む前の地図にする。対応内容は、関心事ごとの箇条書きにし、コミットの分け方と揃える。
  - 1 段目は関心事で、太字の名前に「新規」「変更」「削除」を添え、ファイルが 1 つのディレクトリに集まるならそのパスを続ける。
  - 2 段目はファイルかディレクトリごとに、何をどう変えたかを書く。ファイルの一覧を書き写さない。判断した理由は「背景」に書く。
- 背景は、issue と違う点や、作業中に分かったことだけを書く。issue の繰り返しにしない。
- 確認したことには、実行したコマンドと結果を書く。確かめていないことは「未実施」と理由を書く。
- 影響には、使う人やほかのリポジトリへの影響と、互換性のない変更の有無を書く。互換性のない変更は、コミットメッセージにも `!` か `BREAKING CHANGE` を付ける。次のバージョンを決める手段が読むためである。
- レビューしてほしい点には、判断が分かれた箇所と、捨てた代替案の理由を書く。
- 扱わなかったことは「残したこと」に書き、issue があれば番号を添える。
- レビューに対応してコミットを足したら、返信と同じときに本文を差分に合わせて直す。対応内容、背景、確認したこと、レビューしてほしい点、残したことのうち、変わった節を書き換える。
  - 本文は、取り込む差分の説明である。古いままだと、差分を読む前の地図にならない。
  - 「レビューで直した点」のような追記の節を作らない。経緯はコミットと返信が持つ。
