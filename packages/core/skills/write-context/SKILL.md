# write-context

対象は、`context/` の 6 種類の文書、`context/domain/<概念>.md`、CONTRIBUTING.md、AGENTS.md である。  
テンプレートの見出しの下の案内は「何を書くか」だけを持つ。決めるときに確かめること、書かないこと、分け方、`status` の意味は、このスキルが持つ。

## 決めて書く手順

1. 種類を 1 つ選ぶ。利用者が指定した種類か、いまの開発プロセスの段階に決まる時期が当たる種類にする。
2. `context/<種類>.md` を開き、`status` を見る。`draft` なら骨組みだけである。`stable` なら「更新する手順」に従う。
3. 決まる時期に当たるかを確かめる。当たらなければ、理由を伝えて止まる。決まっていない事柄を書くと、あとで書き直す文書が増える。
4. 表の「確かめること」を利用者に問い、答えを得る。推測で埋めない。答えが出ない項目は、見出しの下に「未定」と書いて残す。
5. テンプレートの見出しに沿って書く。「書かないこと」に当たる内容は書かず、どのファイルを読めば分かるかをリンクで示す。
6. `status` を `stable` にする。「未定」が 1 つでも残るなら `draft` のままにする。
7. 目次 `context/index.md` を生成し直す。Git のフックに core のチェックを 入れていれば、コミットのときに生成される。

## 種類ごとの決まる時期と確かめること


| 種類        | ファイル                           | 決まる時期                             | 確かめること                                                                               | 書かないこと                                         |
| --------- | ------------------------------ | --------------------------------- | ------------------------------------------------------------------------------------ | ---------------------------------------------- |
| 技術スタック    | `tech-stack.md`                | `requirements` と `design` が終わったとき | 採用したツールと役割。版が書いてあるファイル。パッケージマネージャーが管理しないツールの版の決め方。版を上げるときに動かなくなりやすい箇所。新しいモジュールの作り始め方 | 版そのもの。選んだ理由。理由は ADR が持つ                        |
| コードベースの構造 | `codebase.md`                  | `implementation` に入るとき            | モジュールの境界とその理由。依存してよい向きと、禁止する依存。状態の置き場。新しいコードの置き場と、共有へ移す条件                            | ディレクトリの木。コードから読み取れる構造。全体の構成。構成は Design Doc が持つ |
| コードと文書の規約 | `conventions.md`               | `implementation` に入るとき            | 判断が要る命名。コメントに書くことと書かないこと。文書の書き方のうちこのリポジトリだけの規則。共有の設定の場所。自動チェックから除外しているものと理由                                | lint で検出できる規則。設定の値そのもの                         |
| テスト       | `testing.md`                   | `verification-design` のとき         | 種類ごとに何を保証し、どこに置くか。実行に要る環境変数、ポート、外部のサービス。本物で動かすものと置き換えるもの。変更ごとに足すテストと、リリースの前に通すテスト    | テストの基盤の構成。構成は Design Doc が持つ。個々のテストの内容         |
| 基盤と運用     | `operations.md`                | `integration` と `release` のとき     | 環境の種類と用途と、次の環境へ進む条件。デプロイしてよい条件。正常と判断する観測点。切り戻しの手順と、戻せない変更の扱い。秘密情報を置く場所と置かない場所        | 基盤の構成。構成は基盤の Design Doc が持つ。秘密情報の値             |
| 業務の知識     | `domain.md` と `domain/<概念>.md` | `requirements` のとき                | 用語と、コードの識別子との対応。状態や不変条件を持つ概念。概念ごとの状態と遷移、不変条件、禁止事項                                    | 機能ごとの仕様と画面。仕様は spec と Design Doc が持つ           |


- 決まる時期の識別子は、`context/project.yml` の `process.defaults.processes` と同じである。開発プロセスのパッケージを入れていなければ、利用者にいまの段階を尋ねる。
- どの種類でも書かないことは、コードや設定ファイルから読み取れる事実、選んだ理由、機能ごとの仕様、値そのものの 4 つである。事実の所在を、本文のリンクで示す。
- context は、機能をまたいで成り立つ取り決めと契約と、その所在を持つ。構成と処理の流れは Design Doc が持ち、対象のコードの隣に置く。

## status の意味

- `draft` は、骨組みだけか、「未定」が残る状態である。読む側は内容を当てにしない。目次に印が付く。
- `stable` は、書き終えた状態である。読む側はこの取り決めに従う。
- `deprecated` は、使わない状態である。置き換えた文書へのリンクを本文の先頭に置く。
- 省略したら `stable` と見なす。導入のスキルが置いた骨組みは、すべて `draft` で始まる。

## 1 ファイルに収まらない種類の分け方

- `context/<種類>.md` に一覧を置き、項目ごとに `context/<種類>/<項目>.md` に分ける。モノレポでアプリごとに違う取り決めが例である。
- 分けた文書も frontmatter を持つ。`type` は `context`、`title` と `description` は必須である。目次は下位のディレクトリの文書も載せる。
- 業務の知識は、概念ごとに `context/domain/<概念>.md` を作り、`domain.md` の Concepts からリンクする。節は次の 3 つで、見出しは英語で書く。

```markdown
## States and Transitions
<!-- 状態の一覧と、遷移の条件。遷移を起こす操作 -->

## Invariants
<!-- どの状態でも成り立つ条件 -->

## Prohibitions
<!-- してはいけない操作と、その理由 -->
```

概念を実現する構成と処理の流れは、機能ごとの Design Doc が持つ。概念の文書には書かない。

## 更新する手順

- 取り決めを変える pull request の中で、同じ pull request で context を直す。あとでまとめて直さない。
- 実装と context が食い違ったら、どちらを直すかを先に決める。取り決めが変わったなら context を直し、実装が取り決めから外れたなら実装を直す。
- 文書の体系を入れていれば、説明している設定ファイルを `governs` に、読んで確かめたコミットを `verified_commit` に書く。片方だけは書かない。
- `stable` の文書を大きく書き直すときは、書き直しの間だけ `draft` に戻す。

## CONTRIBUTING.md と AGENTS.md

CONTRIBUTING.md は、変更をリポジトリへ取り込むまでの手順を持つ。規約の本文は持たず、context とスキルへリンクする。


| 節                    | 書くこと                                                                          |
| -------------------- | ----------------------------------------------------------------------------- |
| 開発の準備                | 必要なランタイムとツールの名前、最初に実行するコマンド。版は、版が書いてあるファイルを示す                                 |
| 文書を直すとき              | 文書のチェックの実行方法                                                                  |
| コミットするとき             | コミットの前に動くチェックと、その直し方。分け方とメッセージは、スキル write-commit に委ねる                           |
| ブランチとリリース            | ブランチの構成と取り込み方、バージョンの付け方、次のバージョンを決める手段。保護するブランチの名前は `context/project.yml` と揃える |
| issue と pull request | issue の種類とラベル、pull request との対応。書き方は、スキル write-issue-pr に委ねる                |


AGENTS.md は、常に読み込まれる。目次を読む指示と、禁止事項だけを持つ。次の 3 つをすべて満たす内容だけを足す。

- どの作業でも要る。
- モデルが推測できない。
- スキルの説明、自動チェック、README で代替されていない。
