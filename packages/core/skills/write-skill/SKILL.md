# write-skill

スキルを作るときの、agent-harness に固有の判断。  
frontmatter の形、description の書き方、評価のしかたのような一般論は、公式の文書と、スキルを作るための既存のスキルに任せる。

## どこに書くか

スキルを作る前に、その内容がスキルに向くかを決める。  
手段ごとの違いは、次のとおり。

| 手段 | 守られたかを確かめられるか | コンテキストを使うとき | 向く内容 |
| --- | --- | --- | --- |
| 自動チェック（lint、Git のフック、CI） | 確かめられる | 違反があったときだけ | 機械で判定できる規則 |
| 操作の前に止めるフック | 確かめられる | 拒否したときだけ | 取り返しのつかない操作の拒否 |
| コンテキストを追加するフック | 確かめられない。促したことだけが分かる | 条件に当たったときだけ | その時点でモデルに行動を求めるもの。足したコメントの確認の促し |
| context | 確かめられない | 読まれたときだけ | 機能をまたいで成り立つ取り決めと、その所在 |
| 規約ファイル（AGENTS.md） | 確かめられない | 常に | context の目次を読む指示と、どの作業でも守る禁止事項だけ。ルールの本文は持たない |
| スキル | 確かめられない | 説明は常に。本文は呼ばれたときだけ | 特定の作業のときだけ要る、機械で判定できない判断 |

- 機械で判定できる規則は、自動チェックにする。スキルにも context にも書かない。
- 変わらない指示を、フックで毎回コンテキストに追加しない。関係のない作業でもコンテキストを使い、守られたかも確かめられない。
- そのリポジトリだけの取り決めは、スキルではなく context に書く。スキルは、作業の前に context の該当する節を読む手順を持つ。
- スキルは、使われなくても説明の分だけ毎回のコンテキストを使う。数が増えると、説明が短縮される。既にあるスキルに足せる内容なら、スキルを増やさない。
- 同じことを 2 つのスキルに書かない。入れているスキルやプラグインが同じことを指示していないかを、作る前に確かめる。

## 渡す知識

スキルに書くのは、モデルが知らないそのプロジェクトの知識だけにする。

- 書くもの: そのプロジェクトで選んだ規則とその理由、使うコマンドと置き場、自分たちで変えられない外部の制約、判断の基準。
- 書かないもの: モデルが指示なしで行うこと、一般的な手順、段階を踏んで考えさせる指示。モデルの更新で不要になり、挙動を縛る負債になる。
- コードや設定ファイルから読み取れる事実は、写さない。どのファイルを読めば分かるかを書く。写した事実は、実装とずれても検出できない。
- 最初から網羅しない。モデルが誤った項目、不足に気づいた項目だけを足す。

## 本文の長さとファイルの分け方

- `SKILL.md` は 150 行以内に保つ。
  - 出典: [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- `references/` に分けるのは、呼び出しごとに読む部分が違うときと、150 行に近づいたときに限る。同じ作業で全部を読む規則は、`SKILL.md` の 1 ファイルに置く。
- `references/` のファイルは、`SKILL.md` から直接参照する。`references/` から別のファイルを参照しない。参照が 2 段になると、途中までしか読まれないことがある。
- `assets/` には、利用者のリポジトリへ写すテンプレートを置く。本文の規則は置かない。
- `scripts/` には、手順のうち機械的に決まる処理を置く。本文には、呼び方と、終了コードごとに何をするかだけを書く。処理の中身を本文で説明しない。

## パッケージとして配るスキル

複数のリポジトリへ配るスキルは、次の規則も守る。  
そのリポジトリだけで使うスキルには当てはまらない。

- 名前は `<動詞>-<対象>` にし、対象を具体的に書く。`write-commit`、`write-context`、`setup-agent-harness` が例である。動詞で、どの作業のときに読むスキルかを示す。
  - パッケージマネージャーは、同じ名前のスキルを、後から入れた側で警告なしに上書きする。一般的な語の名前は、ほかの拡張機能と重なることがある。重なる危うさより、名前から作業が分かることを優先する。
- 本文に、利用者によって違う固有の名前を書かない。ホスティングサービス、パッケージマネージャー、コーディングエージェント、利用者のツールと名前が当たる。一般の語で書き、違いの扱いは利用者の context に置く。
- 利用者のリポジトリだけの規則は、本文に書かない。利用者の context のどの節に置くかを決め、スキルは書く前にその節を読む。食い違うときは、context に従う。
- ほかのパッケージのスキルを、名前で呼ばない。そのパッケージが入っていない利用者には、存在しないスキルになる。

## 書き終えたら

- frontmatter の `name` を、ディレクトリ名と揃える。
- 本文を読み直し、「書かないもの」に当たる文を削る。
- description に、どの作業のときに読み込まれるかを書く。書いた作業で実際に読み込まれるかを、コーディングエージェントで確かめる。
