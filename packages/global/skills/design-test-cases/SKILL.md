# design-test-cases

実装の分岐を、仕様としてのテスト観点に変える。テストの実装は、依頼されたときだけ行う。

- 文書は [assets/test-case-design-template.md](assets/test-case-design-template.md) の形で書く。
- 文書の置き場所、テストの方式（実 DB か単体か、mock を使うか）は、リポジトリの AGENTS.md と context に従う。書かれていなければ利用者に尋ねる。
- 呼び出し元も読む。返した結果を後続がどう解釈するかで、観測すべき結果が決まる。

## 実装の事実、要求、推測を分ける

- 実装の事実（コード、SQL、設定、既存のテスト）は、処理の流れとして書く。
- 明示された要求（仕様書、issue、依頼者の指示）だけを期待結果にする。
- 根拠の無い推測は期待結果にせず、未決事項に書く。
- 今の実装を正解とみなすと、既存のバグを固定するテストになる。要求だけを見ると、分岐と合流の回帰を漏らす。両方を読み比べ、食い違いは未決事項に書く。

## 処理の流れと主要な仕様

処理の流れは、呼び出しから結果まで上から下へ読める tree で書く。節はファイルと関数にし、行番号を添える。呼び出し先の一覧で終わらせず、次を書く。

- 分岐へ入る条件と、合流する位置
- 同じ対象を見分けるキー
- 状態や関連を、どの時点の値で評価するか
- 欠損、空、重複、部分的な失敗のときの扱い
- 呼び出し先の結果をそのまま返すか、取り直す、集約する、一意にするか

変更を対象にするときは、tree を `diff` のコードブロックにし、変更の前後を 1 つの tree で見比べられるようにする。

- 変更の前にあって消えた節は行頭を `-`、変更の後で足した節は `+`、変わらない節は空白にする。中身だけが変わった節は、前の節を `-`、後の節を `+` で続けて置く。
- 行番号は変更の後のものにし、どちらの SHA かを tree の前に書く。
- 変えた関数を共有する呼び出し元には `[影響]` を付ける。

リスナ、コールバック、ジョブのように、登録の後で外の入力から呼ばれる処理は、tree では入力がどこで止まるかが読めない。tree に加えて、入力から結果までを mermaid の flowchart で描く。

- 入力の条件（どこで離したか、どの応答が返ったか）で枝を分ける。
- 変更を対象にするときは、変更の前と後を `subgraph` に分け、同じ入力の枝を左右に並べる。`flowchart LR` の中で `before ~~~ after` と見えない線でつなぐと、左右に並ぶ。
- 消えた節、足した節、前後で結果が違う節は、`classDef` で枠の色と線を変えて見分ける。凡例を図の前に書く。
- 変更の前の挙動のうち、コードから読めずライブラリの内部に頼る節は「未確認」と書く。
- 実装の層（エンジン、アダプタ、ドライバ）ごとに流れが違えば、図を層ごとに分ける。

処理の流れの直下に、主要な仕様を 1 つずつ `###` の見出しで置く。見出しは「同じ ID を一意にする」「現在の関連を取り直す」のように、観点へ直につながる文にする。

## 観点とケースの選び方

- 正常系と異常系の 2 つで終わらせない。分岐と仕様の境界ごとに観点を立てる。
- 各観点に、どの実装の誤りを検出するかを書く。書けない観点は採らない。
- 対象外の観点は消さず、理由（不要、別の層で保証、観測できない）を残す。
- 同じ誤りしか検出しないケースは 1 つにまとめる。入力の差は、確かめたい条件だけにする。

次のケースは作らない。

- 順序が保証されない集合で、順序を期待するケース
- 余分な結果を許す部分一致だけで済ませるケース
- 内部の呼び出しの回数だけに頼るケース。外の振る舞いで同じ回帰を検出できないかを先に考える

優先度は次の順を基本にし、影響と変更の箇所で調整する。

1. 今回の変更で直に振る舞いが変わりうる分岐
2. 欠損、重複、状態の境界など、不具合の影響が大きい条件
3. 分岐の合流や現在値の取り直しなど、実装から読み取りにくい仕様
4. 代表的な正常系と、該当なし
5. 頻度が低いか、別の層で保証される条件

## EARS の要件

条件と結果を 1 対 1 にし、クラス名やメソッド名ではなく、外から観測できる結果を書く。

```text
WHEN <イベントか入力の条件> のとき、THEN 対象処理 SHALL <観測できる結果> となる。
WHILE <状態> の間、対象処理 SHALL <観測できる結果> を保つ。
IF <無効、欠損、失敗の条件> ならば、THEN 対象処理 SHALL <安全な結果> となる。
対象処理 SHALL 常に <不変条件> を満たす。
```

- 前提は `WHERE` で絞る。前提が増えすぎたら、ケースを分ける。
- 実装も依頼されたときは、文書のケース名をテスト名と fixture に対応させる。

## 止めるとき

次のときは設計を止め、確かめた事実、対立する選択肢、要る判断だけを示す。

- 実装、文書、既存のテストで仕様が食い違い、どれを選ぶかで期待結果が変わる。
- 観測すべき結果かテストの層を決める情報が無く、絞れない。
- 設計を進めるために、依頼の範囲の外の仕様を決めるか、本番を変える必要がある。
