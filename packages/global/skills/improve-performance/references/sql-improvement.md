# SQL の改善の手順

単一の SQL がボトルネックと分かった後の手順。構文は MySQL 8.0 以降のものを使う。ほかの DB では、同じ役割のコマンドに読み替える。変える前を「現行の SQL」、変える候補を「候補の SQL」と呼ぶ。

## 1. 入力と索引を記録する

- 入力の値（ID など）は、アプリの既存のログから実際の値を抜き出す。単一と複数の両方を用意する。`IN` 句の件数で実行計画が変わることがある。
- マイグレーションの定義だけで索引の有無を決めない。計測に使う DB で、SQL に出るすべての表の `SHOW CREATE TABLE` と `SHOW INDEX` を取る。

## 2. 現行の SQL の実行計画を読む

`EXPLAIN ANALYZE FORMAT=TREE` を実行してもらい、次を見る。

- 探索の起点: 入力の値に当たる行から始まっているか。入力と関係のない表の全走査から始まっていないか。
- loops: 行の多い表を外側にした nested loop や、外側の行ごとに評価される dependent subquery（`<in_optimizer>` の表記）は、1 回が速くても総回数で秒の単位になる。
- actual time: root の値を、実行計画全体の時間として扱う。
- `Temporary table with deduplication` のような重複の排除のコスト

`EXPLAIN ANALYZE` は SQL を実際に実行する。SELECT にだけ使う。actual time と通常の SELECT の実行時間を混ぜて比べない。

## 3. 候補の SQL を設計する

- 入力と関係のない大きな表の全走査から始まる: 起点を入力の側の表に移し、候補のキーを先に絞ってから本体を JOIN する。
- `OR` で結んだ種類の違う条件が dependent subquery になる: 条件ごとに候補のキーを返すサブクエリに分け、`UNION` でまとめてから本体へ JOIN する。
- 全列の `SELECT DISTINCT` が一時表を作る: キーだけの段階で `UNION` により重複を除き、外側の DISTINCT を外す。
- 同じ候補が複数の JOIN やサブクエリから重なって届く: `UNION ALL` ではなく `UNION` で、候補の段階で一意にする。

索引の追加を最初の手段にしない。既存の索引が使われない原因は、探索の向きであることが多い。索引の追加はスキーマを変え、オプティマイザが計画を変える保証もない。足りないときだけ、別の案として立てる。

候補の SQL も、結果の集合（行と列）を現行と完全に一致させる。バインドのパラメータと、空のリストで SQL を発行しないようなアプリ側の分岐を保つ。

## 4. 結果の集合を比べる

現行と候補のそれぞれで、SELECT の列を主キーだけにし、`ORDER BY 主キー` を付けた比較用の SQL を作る。単一と複数の入力で、3 回ずつ一致を確かめる。多ければ出力をファイルに保存して `diff` する。データの更新が並行しうる環境では、同じスナップショットの中で両方を実行する。

```sql
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION WITH CONSISTENT SNAPSHOT;
-- 現行の SQL の ID の一覧
-- 候補の SQL の ID の一覧
ROLLBACK;
```

## 5. 候補の実行計画を読み、3 回ずつ計測する

- 候補の `EXPLAIN ANALYZE FORMAT=TREE` で、入力の値の索引から探索が始まり、本体の JOIN が主キーの lookup になったかを確かめる。
- `EXPLAIN ANALYZE` を外した通常の SELECT を、現行を 3 回、候補を 3 回の順に実行してもらう。本番と同じ全列を取り、比較用の `ORDER BY` を外す。
- 実行時間は、クライアントの表示（`rows in set (... sec)`）か `SHOW PROFILES` から取り、どちらを使ったかを記録する。
- 実行の順を固定する。キャッシュの順の影響が疑わしいときだけ、別のセッションで逆の順の補助の計測を行う。

## 6. 採用を判定する

3 回の個別の値、平均、中央値、現行からの短縮率を記録し、比較用の SQL と本番の形のどちらの値かを明記する。標準の条件は次の 4 つ。数値は改善案の側で調整する。

1. すべての入力のパターンで、結果の集合が完全に一致する。
2. 候補の実行計画が、意図した探索の向きになっている。
3. 3 回の計測の中央値が、現行より 50% 以上短い。
4. 初回の値が大きく悪化していない。

満たさなければ実装へ進まない。索引の追加、JOIN の順の固定、`EXISTS` への分割を別の案として検討する。
