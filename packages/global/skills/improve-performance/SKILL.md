# improve-performance

ログや実行計画で裏付けてから、コードや SQL を変える。

- 1 回のループで扱うボトルネックは 1 つにする。同時に入れると、どの変更で速くなったかを区別できない。
- 記録の置き場とファイルの構成は、リポジトリの AGENTS.md と context に従い、なければ利用者に尋ねる。
- 着手の前に、対象の処理と issue、症状（操作、環境、秒数）、比べる基準の計測値、計測に使う DB とデータ量を確かめる。分からなければ尋ねる。

## 進め方

1 つのボトルネックごとに、次の輪を回す。各手順の判断の基準は、同じ名前の節にある。

```
- [ ] 1. ボトルネックの step を特定する（最大の step が全体の過半を占めるまで計測点を足す）
- [ ] 2. 原因を分析する
- [ ] 3. 改善案を書き、数値の採用の条件を決める
- [ ] 4. 実装の前に現行と改善の形を比べる。条件を満たさなければ、結果を記録して 3 に戻る
- [ ] 5. 実装し、事後の計測を同じ条件で行う
- [ ] 6. 台帳を更新し、次のボトルネックがあれば 1 に戻る
```

輪の途中で「止まって利用者に確かめるとき」に当たったら、先に進まない。

## 利用者とエージェントの分担

DB へのクエリとアプリの操作は、利用者が手で実行する。エージェントは DB に接続しない。

- エージェントは、計測用の SQL ファイルと計測ログの埋め込みを作り、貼られた結果を集計して記録を書く。
- 実行を頼むときは、1 工程ずつ、実行するファイル、確かめたい出力、結果の保存先を示す。複数の工程を 1 ファイルにまとめない。
- 現行と候補の SQL を、1 つの CTE やラッパーのクエリにまとめない。どちらに時間がかかったかを判別できない。

## ボトルネックの step を特定する

次の 3 種類の行を出す計測ログを埋め込む。形式を変えると、集計のしかたを使い回せない。

```text
[perf] start process={処理名}, detail={任意の補足}
[perf] step process={処理名}, step={step名}, elapsedMs={経過ms}
[perf] finish process={処理名}, elapsedMs={経過ms}
```

- step の名前をコードの上の名前と揃え、各層で同じ process の名前を使う。ログだけで呼び出しの階層を復元できる。
- 最初に呼ばれる公開メソッドと直下の呼び出しから始め、最大の step の内側へ段階的に足す。最初から全層に埋め込まない。足す範囲は利用者に示してから足す。
- データアクセスが遅ければ、SQL の実行とオブジェクトへの変換を別の step に分ける。
- 対象の操作を 3 回以上（初回の影響を見るなら 5 回）実行してもらい、試行ごとに 1 ファイルでログを保存する。
- 階層ごとに、試行ごとの値、平均、中央値、親に占める割合を集計する。親から子の合計を引いた値を「計測外の差分」として示す。初回だけ極端に遅ければ、初回を除いた集計も示す。
- 最大の step が全体の過半を占めないなら、粒度が粗い。内側へ計測点を足して再計測する。
- ボトルネックが複数なら、すべてを 1 つの台帳（step、処理、時間の中央値、操作全体に占める割合、状態、改善案）に残し、最大の 1 件だけを進める。

計測コードは機能ではない。改善の本体とコミットを分け、その diff をパッチとして記録に保存する。事前と事後の計測はどちらもパッチを当てて行い、レビューに出す前に revert する。パッチが、事後の計測で同じ計測点を保証する。

## 原因を分析する

- 単一の SQL が遅い（1 回で数百 ms 以上）: [references/sql-improvement.md](references/sql-improvement.md) の手順で実行計画を読む。
- 同じ SQL の繰り返し（N+1）: 呼び出しの回数を集計し、一括の取得に変えられるかを見る。
- 外部 API: 回数と 1 回あたりの時間を分け、並列化、削減、キャッシュを検討する。

## 改善案を書き、実装の前に採用を判定する

案ごとに 1 ファイルに、遅い根拠（ログと実行計画へのリンク）、その形に変える理由と選ばなかった案、数値の採用の条件、切り戻しの方針を書く。確かめていない前提は、本文に混ぜず「未確定の事項」に分ける。

採用の条件は、実装の前に決める。結果を見てから基準を緩める後付けを防ぐためである。現行と改善の形を同じ環境で比べ、条件を満たしたときだけ実装する。満たさなければ、結果を記録して別の案を立てる。見送った案も台帳から消さない。

## 実装と事後の計測

- 実装はボトルネックへの変更だけにし、性能と関係のないリファクタリングを混ぜない。
- 結果が変わらないことを確かめるテストを足す。SQL の変更なら、DB を使うデータアクセス層のテストにする。
- 事後の計測は、同じ計測点、同じ操作、同じ回数で行う。変えた step、それを含む中間の処理、操作全体の 3 段で比べる。改善の対象でない step の値を、効果に数えない。
- 台帳の時間と割合を更新してから、次の対象を選ぶ。

## 計測の原則

- 事前の計測の前に、`ANALYZE TABLE`、索引の追加、DB の再起動、buffer pool のクリアをしない。比べる条件が崩れる。共有の環境では、buffer pool をクリアしない。
- 手元の DB と負荷試験の環境の絶対の時間を比べない。データ量、統計、キャッシュが違う。手元は実行計画と改善の幅に、負荷試験の環境は採用の後の計測に使う。
- 初回だけ遅くても、Query Cache と決めつけない。MySQL 8.0 以降には Query Cache がない。buffer pool、OS のページキャッシュ、同時の負荷、実行計画の違いを候補にする。
- 利用者が貼った生の出力を、そのまま保存する。DB の接続情報を記録に残さない。

## 止まって利用者に確かめるとき

- 比べる基準の計測値がなく、初回の計測のしかたも決まっていない。
- 時間の過半を説明できる step を特定できていない。
- 採用の条件を満たしていないのに、実装へ進もうとしている。
- 結果の集合の一致を確かめないまま、SQL を変えようとしている。
