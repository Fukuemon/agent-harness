# capture-browser-evidence

証跡は、レビュアーが同じ判断に到達できる状態にする。録画に映らない事象は、テキストの証跡と組みで残す。

- Playwright で撮る: [references/playwright.md](references/playwright.md)
- agent-browser で撮る: [references/agent-browser.md](references/agent-browser.md)
- e2e で撮る: [references/e2e.md](references/e2e.md)
- GitHub の issue か pull request へ添付する: [references/github.md](references/github.md)
- GitLab の issue か merge request へ添付する: [references/gitlab.md](references/gitlab.md)

## 進め方

1. ツールを選び、該当する references を読む。
2. 撮る。条件を切り替えるたびにサーバを立て直し、配信元を確かめる。
3. `.webm` を mp4 へ変換する。
4. 出す前のチェックリストを応答に写し、全部を満たすまで 2 か 3 に戻る。
5. README を書き、置き場所に置く。添付するなら、ホスティングサービスの references を 1 つだけ読む。

## ツールの選び方

- agent-browser は CDP で動くため、Chromium 系しか操作できない。1 つのブラウザでの確認、探索的テスト、ログイン済みのセッションを使う操作に使う。
- Playwright は、複数のエンジンの比較、手順の反復、既存の e2e テストを証跡にするときに使う。
- e2e は、観点ごとのテストを書いて撮り、動画、trace、レポートを 1 回でそろえるときに使う。対象のリポジトリの依存には足さない。
- テストのモックを使う画面では、Playwright の外のブラウザではモックが当たらない。agent-browser で撮るときの扱いは references にある。
- Playwright の `firefox` と `webkit` はエンジンで、Firefox や Safari のアプリそのものではない。証跡には、どの層で測ったかを書く。

## 画面の大きさ

撮るときの viewport は 1920x1200 にする。録画のサイズも同じにする。対象のテストや設定の既定が違っても、撮るときは上書きする。

## 録画に映らないもの

- タブバー、タブの増減、ネイティブのダイアログ、拡張機能の UI、console、API のレスポンス、`sessionStorage` などの内部状態は映らない。
- 検証用のページを自分で作れるなら、判定に使う値を表で描画し、状態が変わるたびに描き直す。手順の説明を上部のバナーに出し、手順ごとに 1.5 秒ほど止める。
  - イベントは発火の回数を描画する。起きなかったことの証跡になる。
- 作れないページでは、`evaluate` の戻り値をログに残し、録画と並べて読む前提にする。
- 入力のデータを作れるなら、合計から組み合わせが一つに決まる値を置く。9 件の数量を 1、2、4、…、256 にすると、合計 73 は 1 と 8 と 64 の 3 件と決まる。
- 画面の値は `evaluate` でその場で取る。一度だけ描画するページでは、画面のテキストが変化の前の値のまま残る。ハッシュでの遷移で起きやすい。

## 判定の外で起きたこと

判定の値が正しくても、判定の外で画面が失敗を示していることがある。モックの応答がアプリの成功の形でないと、テストは通ったまま失敗の通知が出る。

- 判定の瞬間の 1 枚だけでなく、録画の全体を 1 秒ごとのコンタクトシートで見る。通知、エラーの表示、想定外のダイアログを探す。

  ```bash
  ffmpeg -i <mp4> -vf "fps=1,scale=480:-1,tile=6x6" -frames:v 1 <sheet>.png
  ```

- 登録、保存、削除を含む観点では、成功の通知が出たことか、失敗の通知が出ていないことも判定に入れる。

## 配信元の間違い

応答があっても、配信元の証明にならない。条件を切り替えるたびにサーバを立て直し、そのブランチにしか無い語を配信されたソースで確かめる。手順は [references/playwright.md](references/playwright.md) にある。

## 置き場所と名前

置き場所は、作業の出力の置き場（global の規約では `.ai-out/`）にする。リポジトリの AGENTS.md と context に指定があれば、そちらに従う。

- `<置き場所>/<検証名>/` の下に、`README.md`、比べる条件（改修の前後、エンジン、権限）ごとのディレクトリ、判定の瞬間の静止画を置く `frames/` を作る。
- 条件のディレクトリは、形式ごとに `mp4/` と `webm/` に分ける。`webm/` は倍率を変えて変換し直すために残す。
- ファイル名は `<条件>-<spec のファイル名>-<連番>-<画面名>-<テストケース名>.mp4` にする。issue や pull request の上ではファイル名しか見えない。
  - テストケース名は要約しない。手動の操作では、確かめた観点を入れる。
  - 連番は spec ごとに 1 から振る。ツールの既定の名前を残さない。

## 形式の変換

Playwright と agent-browser の `.webm`（VP8）は、macOS の QuickTime とプレビュー、ホスティングサービスのプレビューで再生できないことがある。

```bash
bash scripts/convert-captures.sh <dir>          # <dir>/webm を <dir>/mp4 へ H.264 で変換する
bash scripts/convert-captures.sh <dir> -s 1.8   # 尺を 1.8 倍に引き伸ばす
```

- 終了コード 0: 全部の出力が H.264 で、尺があることまで確かめた。
- 終了コード 1: ffmpeg か ffprobe が無い、`.webm` が無い、出力が H.264 でない。標準エラーを読んで直す。
- 引き伸ばしはフレームを補間せず、かくつく。遅くするのは撮るときを優先する。
- 判定の瞬間のフレームは、変換した mp4 から抜く。`.webm` を `-ss` や `-sseof` で 1 枚だけ抜くと、シークがずれて手前のフレームを拾うことがある。

## README

動画だけを置かない。README には、何を示す証跡か、ファイル名と検証の内容の対応、画面のどの値で結論が出るかを書く。

- 確かめた内容（codec、尺、目視したフレーム）を書く。行っていない確認は、行っていないと書く。
- 撮るあいだに分かった罠と、撮り直すコマンドを書く。個人の絶対パスを埋めない。検証用の HTML、スクリプト、設定も残す。

## 出す前のチェックリスト

```
- [ ] 録画を再生し、判定の瞬間のフレームを mp4 から抜いて開いて見た
- [ ] 録画の全体をコンタクトシートで見て、判定の外に失敗の通知や想定外の表示が無い
- [ ] 録画に映らない事象は、テキストの証跡と組みで示している
- [ ] 測った層（エンジンかアプリか）を書き、エンジンの結果をアプリの結果として書いていない
- [ ] 操作するタブを間違えて取ったログが入っていない
- [ ] 録画を始めたときに状態が作り直された影響を、読み方に反映した
- [ ] 撮るときの速度と等倍の両方で通る
- [ ] 条件ごとにサーバを立て直し、配信元を確かめた
- [ ] API キーを含む URL を出力していない（API キーはクエリ文字列に乗る）
```

添付が通らないときは、テキストの証跡だけで判断できる形に組み替える。

## 添付するときの本文

- 証跡そのもの（動画の表と読み方）は、コメントに置く。issue と pull request の本文には、変更の内容と検証の観点の対応を置く。本文の文案は利用者に渡し、利用者が書き換える。
- 証跡のテストのコードと出力は、`<details><summary>` で開閉できるようにして貼る。手元のファイルの置き場所は書かない。
- コメントは機能ごとに分け、各コメントだけで読めるようにする。撮った条件は各コメントに 1 行で置く。
- 改修の前後は、同じ表の同じ行に並べる。
