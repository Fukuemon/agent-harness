# review-changes

指摘も「問題なし」の判断も、変更の head のコードで裏取りしてから出す。  
呼び出し元の条件、モックの型、権限のような差分に写らない前提で、判断が反転する。

- head の取り方、スレッドの読み方、差分行への投稿は、ホスティングサービスの references を 1 つだけ読む。
  - GitHub: [references/github.md](references/github.md)
  - GitLab: [references/gitlab.md](references/gitlab.md)
- worktree の置き場、アプリの起動の手順、コメントの形は、リポジトリの AGENTS.md と context に従い、なければ利用者に尋ねる。

## 進め方

次の順に進める。各手順の判断の基準は、同じ名前の節にある。

1. 読むコードを head に合わせる。
2. 裏取りする。
3. 既出のスレッドと照らし合わせ、出す指摘を絞る。
4. 重要度を付け、コメントの形に書く。
5. 投稿の前のチェックリストを応答に写し、全部を満たしてから投稿する。満たさない項目があれば、その手順に戻る。
6. 投稿し、差分行に紐付いたことを確かめる。

## 読むコードを head に合わせる

- 変更の最新の head SHA を取り、手元の HEAD と一致させてから読む。一致しないと、修正済みの箇所を指摘する。blob link の ref にもこの SHA を使う。
- worktree を作って読む。複数のリポジトリにまたがるときは、スキル create-worktrees を使う。
- `git switch` で今の作業ブランチを離れない。未コミットの変更があると切り替えに失敗し、元の作業にも戻れなくなる。

## 裏取り

- 本文の説明と差分の食い違いは、それ自体を指摘にする。
- `toHaveCount(0)` や「属性がないこと」のような否定形のアサーションは、対象が描画されない条件では常に成立する。描画の条件を親から渡る値まで辿り、対になる肯定の確認を求める。
- 「常に成立する」と書く前に、対象の条件を一時的に反転させ、テストが落ちることを見る。author が実行して反証すると、指摘ごと崩れる。変えたコードは戻す。
- レイアウトや描画は、アプリを起動し、スキル capture-browser-evidence で証跡を残す。静的に読んで結論が出るなら起動しない。
- テストを足す変更と、型チェックや lint に既存のエラーがあるリポジトリでは、[references/verification.md](references/verification.md) を読む。
- 確かめていない命題を指摘に含めるときは「未確認」と書く。

## 既出のスレッドと照らし合わせる

自動レビューと author の対応の記録を、題ではなく、判断した論点で対応付ける。「値がハードコードで実在を確認できない → 許容（実在を確認済み）」は実在の判断で、ハードコードの可否の判断とは限らない。判断の理由の文まで読む。

- 判断が記録されていて、論点も同じ: 再び出さない。判断に事実の誤りがあるときだけ指摘する。
- 判断が記録されていない: `ask` で意図を確かめる。
- 近い判断があるが、論点が違う: 判断済みの論点と別の論点を明記して出す。

## 重要度

- `must`: 誤動作、データの不整合、セキュリティ、回帰を検知できないテスト。直さずにマージすべきでないもの。
- `imo`: 設計と一貫性の提案。既存のパターンとの不一致と、規約に定めのないものは、ここまでにする。
- `nits`: 命名や体裁。
- `ask`: 意図の質問。意図が分からないうちは、`must` と `imo` を出さずに先に訊く。
- 変更の範囲を超える改善の要求を `must` にしない。

## コメントの形

1 つのコメントに、論点とバッジを 1 つずつ入れる。author が片方だけを受け入れられる。

```md
![must](https://img.shields.io/badge/review-must-red.svg)

（1 文目に結論。根拠の `path:line` と、問題になる条件）
```

- バッジの色は、must が red、imo が orange、nits が green、ask が blue。
- `must` と `imo` には、対応の案を付ける。案の書き方はホスティングサービスで表示が違うので、references に従う。
- 別のコメントを参照するときは「具体案は〜の該当行に別途コメントしました」と書く。

## 投稿

- 論点の中心の行に差分行のコメントとして付け、行に紐付いたことを references の方法で確かめる。
- 誤りは削除せずに更新し、先頭に引用で何を誤っていたかを残す。経緯が消えると、author が何に答えたかを追えなくなる。
- approve と merge を実行しない。指摘を直すコミットも作らない。

投稿の前のチェックリスト。

```
- [ ] 手元の HEAD が、変更の最新の head SHA と一致している
- [ ] 既存のスレッドと対応の記録を、判断の理由の文まで読んだ
- [ ] すべての指摘で、差分ではなく実ファイルを開いて確かめた
- [ ] must と imo のそれぞれに、その重要度にした根拠を 1 文で言える
- [ ] 型と lint のエラーが、変更で増えたものか既存のものかを確かめた
```
