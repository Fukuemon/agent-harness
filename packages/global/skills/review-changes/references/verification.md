# 条件付きの裏取り

## テストを足す MR

- セレクタの実在: セレクタを生成する側のコンポーネントを読み、値が prop 由来か、ルート名由来かまで辿る。
- fixture の型: API の型定義と、store の変換の関数の両方を読む。store が別の名前のプロパティを期待していると、実行時にエラーになる。
- テストが成り立つ前提: 表示の条件を決める算出の値、権限、ルートのガードを読む。
- モックの優先順位: fixture 側と spec 側で登録したルートのどちらが優先されるかを確かめる。

## 型チェックと lint に既存のエラーがあるとき

全体の結果だけでは判断できない。MR の本文に clean と書かれていても、実行して確かめる。

1. 型チェックの出力を、変更したファイルで絞る。
2. 残ったエラーがマージ先にもあるかを、`git show origin/<base>:<path>` で確かめる。追加行に紐付かないエラーは既存のもので、指摘にしない。
3. lint は、変更したファイルだけを対象に実行する。
