# organize-issues

issue と task の構造と属性を整える判断。題と本文の書き方は扱わない。ホスティングサービスの API の呼び方は、そのサービスのスキルに従う。

- 始める前に、利用者のリポジトリの issue の規約（context、規約ファイル、ルールのファイル）を読む。食い違うときは規約に従う。規約から外す構造は、外す理由を親の issue の本文に残す。
- 書き換える前に、変える内容を表にして利用者の承認を取る。承認の範囲を越えて変えない。

## 階層

- 要求と設計は、設計の文書を置くリポジトリの issue にする。実装は、実装のリポジトリの task にし、設計の issue の子にする。
- ほかのリポジトリへの依頼（ライブラリの改修など）も、依頼をまとめる issue の子の task にする。
- 前提として要る修正（CI の失敗の修正など）は、ブロックされる issue の子の task にする。
- 検証は task にし、検証する要求の子にする。
- 束ね役の親要求は 1 段にする。期限や完了条件が独立したフェーズに分けるときだけ、2 段を認める。
- ホスティングサービスの親子で表せない段は、親の本文の task list（`- [ ] #子`）と、子の本文の親へのリンクで表す。
- 上位の issue は、下位より先に作る。番号は後から変えられない。関連付けから階層を組むツールは、番号の小さい未完了の issue を上位とみなすことがあり、後から作った親が子の下に出る。
- 親子を変えたら、本文の親の記述と task list も同じに直す。本文に構造の判断が記録されていて、変更がそれと逆向きなら、記録を引用して確かめてから変え、判断の記録に日付と理由を足す。

## 関連付け

- 親子で表せない横のつながりにだけ使う。前提、根本対応、方針の出どころが当たる。
- 親子と同じ 2 件に関連付けを重ねない。
- 束ね役には、直接の構成要素だけをつなぐ。調査の issue から全件へ張るような網の目にしない。
- 関連付けを輪にしない。どの 2 件の間も、関連付けのたどり方が 1 通りになる形を保つ。輪があると、関連付けから階層を組むツールで、同じ issue がたどり方の数だけ重複して並ぶ。
  - 確かめ方：関連付けでつながった issue の群ごとに、関連付けの本数が件数より 1 本少なければ輪は無い。多ければ輪がある。
  - 輪を見つけたら、束ね役から遠い側の関連付けを外す候補にし、外す前に利用者の承認を取る。

## 担当者と日付

- 作った issue と task、着手した issue と task には、担当者を付ける。
- 期日は、利用者が示した予定から取る。予定の無い issue には設定しない。推測で埋めない。
- 開始日は、前の作業が終わって着手できる日にする。issue の作成日、MR の作成日、最初のコミットの日は使わない。前の作業の完了日が決まっていないときは、置いた仮定を利用者に示す。
- 親の開始日と期日は、子の最も早い開始日から最も遅い期日までにする。

## 棚卸しとクローズ

- 棚卸しでは、担当者の無いもの、閉じられるのに開いているもの、長く更新の無いものを分けて示す。
- 閉じる候補は、関係する変更がすべてマージかクローズで、開いた変更が無いものにする。受け入れの検証が済んだかは記録から分からないので、利用者に確かめる。
- 閉じるのは下から順にする。子が開いている親は閉じない。親を閉じたいときは、開いた子の置き場所を利用者に確かめる。
- 長く止まっているチケットは、終了、却下、残すのどれにするかを 1 件ずつ利用者に決めてもらう。
