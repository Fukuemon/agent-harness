# setup-design-system

core の導入のスキル setup-agent-harness を先に実行しておく。`context/project.yml`、`context/codebase.md`、CONTRIBUTING.md は、そのスキルが写す。  
このスキルの雛形は、置き場所が利用者ごとに違うので、`references/` にある。モデルが利用者の決めた場所へ写す。  
既にあるファイルを書き換えるときは、差分を利用者に見せてから書く。

## 1. 尋ねる

次を 1 回にまとめて尋ねる。既にトークンやカタログがあるリポジトリでは、見つけたファイルを候補に示す。

- 元にする公開のデザインシステムと、その基本の段のファイル。依存として入れるパッケージのパスか、リポジトリの中のファイル。
- 意味の段とテーマの段のファイルの場所。テーマの段は、使うスタイルの仕組みの書き方に合わせる。
- 意味の段のトークンの接頭辞。基本の段の名前と重ならない、プロダクトの短い名前にする。
- デザインシステムの文書の場所。トークンとコンポーネントの置き場の隣に置く。
- `design_system.tokens_css`: 静的なファイル（画面仕様書のモック、文書のサイト）が読むトークンの CSS のパス。静的なファイルがなければ省く。
- `design_system.catalog_url`: 公開したカタログの URL。まだ公開していなければ省き、公開したときに書く。

`context/project.yml` に、ほかのパッケージが同じ値を持つキー（トークンの CSS のパス、カタログの URL）があれば、その値を候補に示す。2 つのキーに同じ値を書くので、値を変えるときは両方を直すよう伝える。

## 2. 値と置き場を書く

1. `context/project.yml` に `design_system:` を足す。

```yaml
# デザインシステムが読む
design_system:
  tokens_css: docs/screens/_common/tokens.css
  catalog_url: https://catalog.example.com/
```

2. `context/codebase.md` の Placement Rules に、デザインシステムの文書と 3 つの段のファイルの場所を 1 行ずつ書く。スキル write-design-system が、作業の前にここを読む。
3. 同じ Placement Rules の、画面とコンポーネントのコードの置き場の行に、コードを書く前にデザインシステムの文書を読むことを書く。スキルが読み込まれない作業でも、context から文書に辿り着ける。

## 3. 雛形を写す

| 雛形 | 写す先 | 写した後に直すもの |
| --- | --- | --- |
| [references/design-system.md](references/design-system.md) | 手順 1 で決めた文書の場所 | 題と「知りたいことごとの参照先」の表のパス。ほかのセクションは、スキル write-design-system で書く |
| [references/check-contrast.mjs](references/check-contrast.mjs) | リポジトリのスクリプトの置き場 | 冒頭の `SOURCES`、`PREFIX`、`TEXT_PAIRS`、`NON_TEXT_PAIRS` を、意味の段のトークンに合わせる |
| [references/build-static-tokens.mjs](references/build-static-tokens.mjs) | リポジトリのスクリプトの置き場。`tokens_css` を省いたときは写さない | なし。元の CSS と書き出す先は引数で渡す |
| [references/check-raw-values.mjs](references/check-raw-values.mjs) | リポジトリのスクリプトの置き場 | 冒頭の `TARGETS`（画面とコンポーネントのコードの置き場）、`EXCLUDES`（3 つの段のファイルの置き場）、`BASE_PREFIXES`（基本の段の接頭辞） |

- 雛形はファイルごと写す。中身を読んで書き直さない。直すのは、表の「写した後に直すもの」だけにする。
- 隣の `.test.mjs` は、パッケージのテストなので写さない。
- 3 つのスクリプトは、Node.js の標準のモジュールだけで動く。リポジトリが別のテストの仕組みを使っていても、テストから実行して終了コードを見ればよい。
- 意味の段がまだなければ、文書の骨組みだけを写し、スクリプトは意味の段を作った後に写す。
- テーマの段とカタログの設定は、写す雛形を持たない。スタイルの仕組みとカタログのツールごとの例が、このパッケージのリポジトリの `examples/design-system/` にある。

## 4. 生成とチェックを流す

1. 生成のスクリプトで、`tokens_css` を作る。基本の段を先に、意味の段を後に渡す。リポジトリの中のファイルは `./` で始める。

```sh
node <スクリプトの置き場>/build-static-tokens.mjs --out <tokens_css> <基本の段> ./<意味の段>
node <スクリプトの置き場>/check-contrast.mjs
node <スクリプトの置き場>/check-raw-values.mjs
```

2. コントラストのチェックが失敗したら、出た組を利用者に見せる。値を直すか、組を外すかは利用者が決める。組を外すのは、無効のコンポーネントの文字のように、基準の対象外のものだけにする。
   - 「条件つきのブロック」と出たら、意味の段の変数を `@media` や `:root` 以外のセレクタの中で上書きしている。
     - ダークモードのように画面に表示される値なら、報告に出たブロックを `--root` で渡し、条件ごとに流す。CI にも条件ごとのコマンドを足す。
     - 基本の段の条件つきのブロックは、読み飛ばして数だけを出す。失敗にはならない。
3. 色の値と基本の段の名前のチェックが既にあるコードで失敗したら、出た数を利用者に見せ、直すか、CI に入れるのを後にするかを尋ねる。ロゴのように値が外で決まる行だけは、同じ行のコメントに `design-system-allow` と理由を書いて外す。

## 5. チェックを組み込む

1. CONTRIBUTING.md に「デザインシステムを直すとき」のセクションを足し、手順 4 の 3 つのコマンドと、生成物を同じコミットに入れることを書く。`build-static-tokens.mjs` には `--check` を付けたコマンドも書く。パッケージマネージャーのスクリプトにするときは、リポジトリのロックファイルから決めたパッケージマネージャーで足す。
2. CI のワークフローがあれば、コントラストのチェック、色の値と基本の段の名前のチェック、`build-static-tokens.mjs --check` を足す。どれも失敗にする。コントラストのチェックは依存の基本の段を読むので、依存を入れた後に流す。
3. 足したチェックを 1 度ずつ実行し、結果を利用者に見せる。
4. 写したファイルと直したファイルをコミットするよう促す。以後は利用者のファイルで、パッケージの更新で上書きされない。

## パッケージを更新したとき

写した雛形は上書きしない。このスキルの `references/` と、写したファイルの差分を利用者に見せ、取り込む変更を利用者と決めて手で反映する。
