# write-design-system

トークンの値、ブランドの色、元にする公開のデザインシステムは、利用者のリポジトリが決める。  
このスキルは、トークンの段の分け方、デザインシステムの文書の書き方、画面を作るときの手順、アクセシビリティの基準、カタログの構成の判断だけを持つ。

## 始める前に読むもの

- `context/codebase.md` の Placement Rules。デザインシステムの文書と、3 つの段のファイルの場所が書いてある。書かれていなければ、導入のスキル setup-design-system を先に行う。
- デザインシステムの文書の「知りたいことごとの参照先」の表。値と振る舞いは、表が指すコードから読む。
- `context/project.yml` の `design_system.tokens_css`（静的なファイル用のトークンの CSS）と `design_system.catalog_url`（公開したカタログの URL）。

## トークンの段

トークンを 3 つの段に分ける。画面とコンポーネントは、テーマの段の名前だけを書く。

| 段 | 持つもの | 書かないもの |
| --- | --- | --- |
| 基本 | 元にするデザインシステムの値。色の階調、文字の大きさと行高、角丸、影 | 用途の名前 |
| 意味 | プロダクトの役割の名前（下の種類）。基本の段を参照する | 値。例外は下にある |
| テーマ | スタイルの仕組みに渡す名前。色は意味の段だけを参照する。文字、角丸、影は基本の段を参照し、用途の名前を付ける | 値と、色の基本の段の名前 |

- 基本の段は、元のデザインシステムが配るファイルを依存にし、バージョンを固定する。値を写すと、元の修正を手で追うことになる。
  - バージョンを上げるときは、基本の段の名前と値の差分を読み、コントラストのチェックを流す。
- 意味の段の名前には、プロダクトの接頭辞を付け、基本の段の名前と重ならないようにする。
- 意味の段に値を直に書くのは、基本の段に近い値がないときだけにする。理由を ADR に書き、意味の段のファイルのコメントからリンクする。基本の段の更新に追従しないので、コントラストのチェックの組に必ず入れる。
- 業務の状態の表示には、新しい色のトークンを作らず、意味の段の状態の色に当てる。対応はデザインシステムの文書に書く。業務の語を意味の段に持ち込まないためである。
- テーマの段は、スタイルの仕組みの既定の色、文字の大きさ、角丸、影、ブレークポイントを消す。意味の段を通さない書き方を、画面のコードで書けなくするためである。
- フォーカスの表示は、テーマの段に 1 つのユーティリティとして置く。コンポーネントごとに作らない。
- 余白のように元のデザインシステムがトークンを持たないものは、スタイルの仕組みの既定の段を使ってよい。使う段をデザインシステムの文書に書く。

### 意味のトークンの種類

意味のトークンを足すときは、次のどの種類に当たるかを先に決め、文書の色の表の同じ種類の行に並べる。当たらなければ、名前を作らずに「決まっていない選択」に書く。

- 面: 画面の背景、カードと入力欄、一段沈めた面、重ねる面（ダイアログ、メニュー）と、その後ろを覆う面
- 文字: 本文、補足、反転（色の付いた面の上）、無効
- 枠: 区切りの線、入力欄と押せるものの枠
- 操作: 主の操作、リンクと訪問済みのリンク
  - hover、押下、選択の色も、それぞれ名前を持つ。
- フォーカス: フォーカスの表示の線と、線の外側の縁
- 状態: エラー、注意、成功、情報
  - 文字の色と、同じ系統の薄い面を組にする（`danger` と `danger-surface`）。面の上の文字は、同じ系統の文字の色か `text` にする。
- 区別: グラフの系列、タグの色
  - 状態の色と兼ねない。

### テーマ

ダークモードのように画面全体の色を切り替えるテーマは、意味の段の参照先を条件ごとに替えて作る。基本の段とテーマの段のファイルは、テーマごとに分けない。

- 画面とコンポーネントのコードに、テーマの条件を書かない。意味の段の名前が、条件ごとに別の値を指す。
- テーマを足したら、コントラストのチェックをテーマの条件ごとに流し、CI にも条件ごとのコマンドを足す。
- 元のデザインシステムがそのテーマの階調を持たないときは、意味の段に値を直に書く例外になる。ADR に理由を書く。

### 静的なファイル用のトークンの CSS

画面仕様書のモックや文書のサイトのように、パッケージの CSS を読めない静的なファイルは、`design_system.tokens_css` の CSS を読む。

- この CSS は、基本の段と意味の段から、利用者のリポジトリにある生成のスクリプトで作る。手で直さない。
- 意味の段を直したら、生成し直し、同じコミットに入れる。CI が生成物のずれを見つける。
- 静的なファイルには、テーマの段の名前がない。意味の段の名前を `var()` で使う。

## デザインシステムの文書

使う側の規則はデザインシステムの文書に、保守の判断（段の分け方、値を直に持つ例外、却下した案）は ADR に書く。  
文書の骨組みは、導入のスキル setup-design-system が写す。セクションを足すときも、骨組みの順に並べる。

- 冒頭に「知りたいことごとの参照先」の表を置き、値と振る舞いを書き写さない。写した値は、コードとずれても見つけられない。
- 意味のトークンは、名前と使う場面の表にする。使わない場面が紛らわしいもの（`border` と `border-field`）は、使わない場面も書く。
- 画面を作るときの原則には、1 つずつ確認の方法を書く。確認の方法のない原則は、守られたかが分からない。
  - 機械で判定できる原則はチェックの名前を、できない原則はレビューで見る問いと、良い例と悪い例を書く。
- コンポーネントは、コンポーネントごとのセクションに、使う場面、使わない場面と代わりに使うもの、変種、状態、内容の制約、キーボードの操作を書く。
  - 状態は、デフォルト、hover、押下、フォーカス、選択、無効、エラー、読み込み中のうち、そのコンポーネントが持つものを全部並べる。読み込み中に、同じ操作を 2 回受け付けるかも書く。
  - 内容の制約は、ラベルの書き方（動詞で終えるか）、文字数、アイコンだけのときの名前のように、画面を作る人が決めがちなことだけを書く。
- パターンは、コンポーネントの組み合わせごとに、目的、並べる領域、狭い画面と広い画面での並び方を書く。1 つの画面だけの並びは、パターンにせず、その画面の仕様に書く。
- 文字とレイアウトは、文字のスタイルの名前と使う場面、本文の幅、余白の段、ブレークポイントを書く。値は参照先のコードから読む。
- 元のデザインシステムが使う側に任せる値と、変えないとする要件を、「元にしたデザインシステムとの関係」の表に分けて書く。
  - 任せる値（主の色、余白の段、角丸）には、このプロダクトの選択を書く。
  - 変えない要件（コントラスト、フォーカスの表示、状態の色相と意味の対応）には、確認の方法を書く。
- 元のデザインシステムの指針から外れる使い方は、対象、指針、このプロダクトの使い方、理由の表に書く。表にない外れ方を作らない。
- 文書の出典は、元のデザインシステムのページを、根拠の文の次の行に置く。

## 決まっていない選択

元のデザインシステムにも、デザインシステムの文書にもない選択を、規則として書かない。

- 文書の「決まっていない選択」のセクションに、選択、案、理由を書き、利用者に尋ねる。利用者が決めたら、規則のセクションへ移す。
- 今の画面のコードとスクリーンショットの値は、今の実装を示すだけで、決まった規則の根拠にしない。
- 画面を作る作業は、案を仮に使って進めてよい。仮に使ったことを、作業の報告に書く。

## 画面を作るとき

1. デザインシステムの文書の参照先の表とカタログから、使うパターン、コンポーネント、トークンを探す。
   - 合うものがなければ、近いものと足りない点を利用者に示し、デザインシステムに足すかを尋ねる。画面のコードの中で同じものを作らない。
2. テーマの段のユーティリティと、デザインシステムのコンポーネントだけで書く。要るトークンがなければ、画面のコードに値を書かず、意味の段に足す案を出す。
3. 使ったコンポーネントの状態は、デザインシステムの文書のそのコンポーネントのセクションに並べたもののうち、画面で起きるものを作る。
4. 利用者の `CONTRIBUTING.md` の「デザインシステムを直すとき」にあるチェックを流す。描画した画面は、文書のブレークポイントの表の幅ごとと、テーマの表のテーマごとに見る。
5. 報告には、通ったチェック、通らなかったチェック、レビューで見る原則を分けて書く。
6. 直すのに新しい判断（基準を下げる、トークンを足す、コンポーネントを足す）が要るときは、止まって利用者に尋ねる。基準を下げて通さない。

## アクセシビリティ

WCAG 2.2 の AA を基準にする。基準ごとに、自動で確認する方法を 1 つ決め、デザインシステムの文書の表に書く。  
ターゲットの大きさだけは、AA より厳しい AAA の値を既定にする。利用者が AA の値にしてもよい。

| 項目 | 基準 | 確認の方法 |
| --- | --- | --- |
| 文字のコントラスト | 4.5:1 以上。状態の面の上の文字も含む | カタログの全ての例でアクセシビリティの自動チェックを動かし、違反をテストの失敗にする。意味の段の組はコントラストのチェックでも計算する |
| 文字でないもののコントラスト | 入力欄と押せる枠の境界、フォーカスの表示が 3:1 以上 | 意味の段の組をコントラストのチェックで計算する。描画した画面の自動チェックは枠の色を見ないため |
| フォーカスの見え方 | 全ての操作できる要素で、フォーカスのユーティリティを出す | カタログの例でキーを押し、フォーカスの位置を確認する |
| ターゲットの大きさ | 44×44 CSS px 以上。AA の 2.5.8 の 24×24 より厳しい、AAA の 2.5.5 の値。見た目が小さいものは、見た目の外に押せる領域を広げる | コンポーネントのテストで、ブラウザで描画した大きさを確認する |
| キーボードの操作 | デザインシステムの文書のコンポーネントのセクションのとおりに動く | カタログの例とコンポーネントのテストで、キーを押した結果を確認する |

- `text-disabled` のように無効のコンポーネントだけに使う文字は、WCAG 1.4.3 の対象外なので、組に入れない。
- 意味のトークンを足したら、そのトークンが文字か枠として載る面との組を、コントラストのチェックに足す。
- 描画した大きさとキーの操作は、描画とブラウザのキーの操作がないと確認できない。ブラウザで動くテストにする。

## カタログ

カタログのページを書くとき、直すときは、[references/catalog.md](references/catalog.md) を読む。ページの構成、題の決め方、載せてよいものがある。

## 変えたら

- コントラストのチェックと、生成物のずれのチェックを流す。どちらも利用者の `CONTRIBUTING.md` にコマンドがある。
- 名前を足した、消した、使う場面を変えたトークンとコンポーネントは、デザインシステムの文書の表とカタログのページを同じ変更で直す。
- レビューで同じ指摘が繰り返し出たら、デザインシステムの文書の原則に足す。機械で判定できる指摘は、チェックにする。1 つの画面だけの指摘は、その画面の仕様に書く。
