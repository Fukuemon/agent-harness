# write-design-system

トークンの値、ブランドの色、元にする公開のデザインシステムは、利用者のリポジトリが決める。  
このスキルは、トークンの段の分け方、デザインシステムの文書の書き方、アクセシビリティの基準、カタログの構成の判断だけを持つ。

## 始める前に読むもの

- `context/codebase.md` の Placement Rules。デザインシステムの文書と、3 つの段のファイルの場所が書いてある。書かれていなければ、導入のスキル setup-design-system を先に行う。
- デザインシステムの文書の「知りたいことごとの参照先」の表。値と振る舞いは、表が指すコードから読む。
- `context/project.yml` の `design_system.tokens_css`（静的なファイル用のトークンの CSS）と `design_system.catalog_url`（公開したカタログの URL）。

## トークンの段

トークンを 3 つの段に分ける。画面とコンポーネントは、テーマの段の名前だけを書く。

| 段 | 持つもの | 書かないもの |
| --- | --- | --- |
| 基本 | 元にするデザインシステムの値。色の階調、文字の大きさと行高、角丸、影 | 用途の名前 |
| 意味 | プロダクトの役割の名前（面、文字、枠、状態、区別）。基本の段を参照する | 値。例外は下にある |
| テーマ | スタイルの仕組みに渡す名前。意味の段だけを参照する | 基本の段の名前と値 |

- 基本の段は、元のデザインシステムが配るファイルを依存にし、バージョンを固定する。値を写すと、元の修正を手で追うことになる。
  - バージョンを上げるときは、基本の段の名前と値の差分を読み、コントラストのチェックを流す。
- 意味の段の名前には、プロダクトの接頭辞を付け、基本の段の名前と重ならないようにする。
- 意味の段に値を直に書くのは、基本の段に近い値がないときだけにする。理由を ADR に書き、意味の段のファイルのコメントからリンクする。基本の段の更新に追従しないので、コントラストのチェックの組に必ず入れる。
- 状態の色は、文字の色と同じ系統の薄い面を組にする（`danger` と `danger-surface`）。面の上の文字は、同じ系統の文字の色か `text` にする。
- 業務の状態の表示には、新しい色のトークンを作らず、意味の段の状態の色に当てる。対応はデザインシステムの文書に書く。業務の語を意味の段に持ち込まないためである。
- テーマの段は、スタイルの仕組みの既定の色、文字の大きさ、角丸、影、ブレークポイントを消す。意味の段を通さない書き方を、画面のコードで書けなくするためである。
- フォーカスの表示は、テーマの段に 1 つのユーティリティとして置く。コンポーネントごとに作らない。
- 余白のように元のデザインシステムがトークンを持たないものは、スタイルの仕組みの既定の段を使ってよい。使う段をデザインシステムの文書に書く。

### 静的なファイル用のトークンの CSS

画面仕様書のモックや文書のサイトのように、パッケージの CSS を読めない静的なファイルは、`design_system.tokens_css` の CSS を読む。

- この CSS は、基本の段と意味の段から、利用者のリポジトリにある生成のスクリプトで作る。手で直さない。
- 意味の段を直したら、生成し直し、同じコミットに入れる。CI が生成物のずれを見つける。
- 静的なファイルには、テーマの段の名前がない。意味の段の名前を `var()` で使う。

## デザインシステムの文書

使う側の規則はデザインシステムの文書に、保守の判断（段の分け方、値を直に持つ例外、却下した案）は ADR に書く。  
文書の骨組みは、導入のスキル setup-design-system が写す。セクションを足すときも、骨組みの順に並べる。

- 冒頭に「知りたいことごとの参照先」の表を置き、値と振る舞いを書き写さない。写した値は、コードとずれても見つけられない。
- 意味のトークンは、名前と使う場面の表にする。使わない場面が紛らわしいもの（`border` と `border-field`）は、使わない場面も書く。
- コンポーネントは、使う場面、使わない場面、キーボードの操作の表にする。使わない場面には、代わりに使うものを書く。
- 元のデザインシステムの指針から外れる使い方は、対象、指針、このプロダクトの使い方、理由の表に書く。表にない外れ方を作らない。
- 文書の出典は、元のデザインシステムのページを、根拠の文の次の行に置く。

## アクセシビリティ

WCAG 2.2 の AA を基準にする。基準ごとに、自動で確認する方法を 1 つ決め、デザインシステムの文書の表に書く。

| 項目 | 基準 | 確認の方法 |
| --- | --- | --- |
| 文字のコントラスト | 4.5:1 以上。状態の面の上の文字も含む | カタログの全ての例でアクセシビリティの自動チェックを動かし、違反をテストの失敗にする。意味の段の組はコントラストのチェックでも計算する |
| 文字でないもののコントラスト | 入力欄と押せる枠の境界、フォーカスの表示が 3:1 以上 | 意味の段の組をコントラストのチェックで計算する。描画した画面の自動チェックは枠の色を見ないため |
| フォーカスの見え方 | 全ての操作できる要素で、フォーカスのユーティリティを出す | カタログの例でキーを押し、フォーカスの位置を確認する |
| ターゲットの大きさ | 44×44 CSS px 以上。見た目が小さいものは、見た目の外に押せる領域を広げる | コンポーネントのテストで、ブラウザで描画した大きさを確認する |
| キーボードの操作 | デザインシステムの文書のコンポーネントの表のとおりに動く | カタログの例とコンポーネントのテストで、キーを押した結果を確認する |

- `text-disabled` のように無効のコンポーネントだけに使う文字は、WCAG 1.4.3 の対象外なので、組に入れない。
- 意味のトークンを足したら、そのトークンが文字か枠として載る面との組を、コントラストのチェックに足す。
- 描画した大きさとキーの操作は、描画とブラウザのキーの操作がないと確認できない。ブラウザで動くテストにする。

## カタログ

カタログは、はじめに、トークン、コンポーネント、パターン、画面の 5 つのページに分け、この順にサイドバーに並べる。

| ページ | 書くこと |
| --- | --- |
| はじめに | 原則、アクセシビリティの基準 |
| トークン | 色の階調と意味のトークン、文字、余白、角丸、影 |
| コンポーネント | コンポーネントごとに、使う場面、使わない場面、Do と Don't、状態、キーボードの操作 |
| パターン | コンポーネントを組み合わせた形（入力のダイアログ、絞り込みの一覧） |
| 画面 | 画面のコンポーネント |

- 題は、ファイルの配置先から機械的に決める。例を作るときに分類を判断しない。配置先と題の対応は、デザインシステムの文書の「題の決め方」の表にある。
- コンポーネントの「状態」には、デフォルト、hover、フォーカス、無効、エラー、読み込みのうち、そのコンポーネントが持つものを全部並べる。
- カタログの原稿は、デザインシステムの文書の見本にする。規則の本文はデザインシステムの文書にだけ書き、カタログからリンクする。
- カタログに載せるのは、コンポーネントとダミーのデータだけにする。開ける人の範囲は変わりうるためである。
  - 人と組織の名前はダミーの値にし、実際の画面やデータベースからコピーしない。
  - API を呼ぶ例を作らない。
  - カタログの原稿に、URL、ホスト名、シークレットを書かない。デザインシステムの文書と画面仕様書からカタログへのリンクは、`design_system.catalog_url` で書く。

## 変えたら

- コントラストのチェックと、生成物のずれのチェックを流す。どちらも利用者の `CONTRIBUTING.md` にコマンドがある。
- 名前を足した、消した、使う場面を変えたトークンとコンポーネントは、デザインシステムの文書の表とカタログのページを同じ変更で直す。
