# デザインシステム

## Overview

パッケージ design-system は、画面の見た目を意味のトークンだけで書くための取り決めと、それを使う側と保守する側の文書の型を持つ。全体像は [agent-harness Design Doc](../../design/DesignDoc.md) にある。

## Scope

- 持つもの
  - トークンの段の分け方、意味のトークンの種類、テーマの切り替え方、デザインシステムの文書（使う側の規則）の型
  - 画面を作るときの手順と、決まっていない選択の扱い
  - アクセシビリティの基準と確認の方法の表、カタログのページの構成と題の決め方
  - コントラストのチェックの雛形、静的なファイル用のトークンの CSS を作る生成のスクリプトの雛形
- 持たないもの: トークンの値とブランドの色。元にする公開のデザインシステムの選択。コンポーネントの実装。

## Design

### トークンの段

トークンを 3 つの段に分ける。画面は意味の段だけを使い、基本の段の名前と色の値を書かない。

1. 基本: 元にするデザインシステムの値。
2. 意味: プロダクトの役割の名前（面、文字、枠、操作、フォーカス、状態、区別）。基本の段を指す。
3. テーマ: スタイルの仕組みに渡す名前。意味の段だけを指し、仕組みの既定の色と大きさを消す。

ダークモードのようなテーマは、意味の段の参照先を条件ごとに替えて作り、コントラストのチェックを条件ごとに流す。画面のコードにテーマの条件を書かずに済む。  
意味の段から、静的なファイル（画面仕様書のモック、文書のサイト）が読む CSS を生成する。生成物のずれは CI で確認する。

### 文書

使う側の規則はデザインシステムの文書に、保守の判断は ADR に書く。文書の冒頭に、知りたいことごとの参照先の表を置く。  
文書は、元にしたデザインシステムが使う側に任せる値と変えないとする要件を分けて書き、原則ごとに確認の方法を持つ。コンポーネントは変種、状態、内容の制約まで、パターンは狭い画面と広い画面の並び方まで書く。  
元にしたデザインシステムにも文書にもない選択は、規則にせず「決まっていない選択」に案と理由を書き、利用者が決める。モデルが、今の画面の値をブランドの規則として広げないためである。  
カタログは、はじめに、トークン、コンポーネント、パターン、画面の 5 つのページに分け、題を配置先から決める。カタログに載せるのはダミーのデータだけにする。

### 画面を作るとき

write-design-system は、トークンと文書を書く作業に加えて、画面を作る作業でも読み込まれる。画面を作るコーディングエージェントが、文書にない色やコンポーネントを画面のコードで作るのを防ぐ。

1. デザインシステムの文書とカタログから、パターン、コンポーネント、トークンを探す。合うものがなければ、デザインシステムに足すかを利用者に尋ねる。
2. テーマの段のユーティリティとコンポーネントだけで書き、使ったコンポーネントの状態を全部作る。
3. チェックを流し、描画した画面を狭い画面と広い画面で見る。報告では、通ったチェック、通らなかったチェック、流せなかったチェック、レビューで見る原則を分ける。
4. 同じチェックが 2 回直しても通らないか、新しい判断が要るときは、止まって尋ねる。

### スキル

| スキル | 担う手順 |
| --- | --- |
| write-design-system | トークン、デザインシステムの文書、カタログのページを書くときの判断と、画面を作るときの手順。段の分け方、意味のトークンの種類、テーマ、文書の書き方、決まっていない選択、アクセシビリティの基準と確認の方法。カタログの構成と題は `references/catalog.md` に分け、カタログを書くときだけ読む |
| setup-design-system | 導入。`design_system` のキーと 3 つの段の置き場を尋ねて書き、雛形を写し、CONTRIBUTING.md と CI にチェックを組み込む |

ファイルの置き場は、導入のスキル setup-agent-harness が `assets/` を全部、利用者のリポジトリへ写すことに合わせて決める。

- 3 つの雛形（デザインシステムの文書の骨組み、コントラストのチェック、生成のスクリプト）は、setup-design-system の `references/` に置く。setup-design-system が、利用者の決めた場所へ写す。
  - 3 つとも、どの利用者にも写すが、写す先が利用者ごとに違う。setup-agent-harness は `assets/` を、リポジトリのルートからの同じパスへ写すので、`assets/` に置かない。
  - ADR-0025: [写す先が利用者ごとに違うテンプレートは references/ に置き、キーを尋ねる場所と schema の有無はパッケージが決める](../../adr/0025-templates-keys-and-schemas.md)
- 2 つのスクリプトは Node.js の標準のモジュールだけで書き、隣の `.test.mjs` がこのリポジトリの `pnpm test` で動きを確かめる。利用者のテストの仕組みに依らず、終了コードで結果を返す。
- デザインシステムの文書と 3 つの段のファイルの場所は、キーにせず、利用者の `context/codebase.md` の Placement Rules に書く。読むスクリプトがなく、write-design-system が作業の前に読むだけのためである。
- スタイルの仕組みとカタログのツールに依る例（テーマの段の CSS、カタログの preview の設定、トークンのページ）は、`examples/design-system/` に置く。名前のチェックの外で、ツールの名前を書ける。
- 元にする公開のデザインシステムの例も、`examples/design-system/` に置く。スキルの本文は、特定のデザインシステムを前提にしない。
  - `examples/design-system/dads/` は、デジタル庁デザインシステムのトークンを基本の段にした意味の段と、任せる値と変えない要件の書き方の例を持つ。
  - 出典: [デジタル庁デザインシステム](https://design.digital.go.jp/dads/)

## Interface

- 読むキー: `design_system.tokens_css`（意味の段から生成する CSS のパス）、`design_system.catalog_url`（公開したカタログの URL）。値の形は `schemas/design-system.schema.json` が持ち、隣のテストで確認する。
- 利用者の context: `context/codebase.md` の Placement Rules に、デザインシステムの文書と 3 つの段のファイルの場所。
- 写す雛形: デザインシステムの文書の骨組み、コントラストのチェック、静的なファイル用のトークンの CSS の生成のスクリプト。
