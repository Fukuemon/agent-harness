# issue-pr-writing

form と雛形は `.github/` にある。ここには、節に何を書くかの判断だけを書く。

## 共通

- 題は、接頭辞と、完了したときにどうなっているかの 1 文で書く。pull request の題は、対応する issue の題と同じにする。
- 文書と ADR は、パスではなく GitHub の URL で示す。`https://github.com/Fukuemon/agent-harness/blob/main/<パス>#<節>` の形で、節のアンカーまで付ける。issue と pull request の本文ではパスがリンクにならない。
- 起票の前に、本文を `.ai-out/issues/` か `.ai-out/prs/` にファイルとして置き、利用者の確認を取る。
- コミットのハッシュ、issue と pull request の番号、URL は、コードスパンで囲まない。囲むと GitHub がリンクにしない。
- レビューのコメントと返信も、本文と同じ規則で書く。1 段落は 3 文までにし、理由が複数あれば箇条書きにする。改行のない長い段落は読みにくい。

## issue

- 種類は、要求、タスク、不具合の 3 つで、`.github/ISSUE_TEMPLATE/` の form を使う。要求は実現したいこと、タスクは要求を分解した実装の単位、不具合は期待と違う動作である。
- ラベルは、form が付ける `type:*` に加えて、対象のパッケージの `pkg:*` を付ける。
- 題の例は「【実装】リンクのチェックを追加する」で、コミットの要約と同じ動詞を使う。
- 接頭辞は、その issue が扱うプロセスで付ける。要求は【要求】、タスクは【設計】【実装】【検証】のどれか、不具合は【不具合】。
- 要求のあるべき姿は「〜できる」の形で書き、受け入れ条件はそれを確かめる箇条書きにする。現状は、関係する文書やコードへのリンクを添える。
- タスクの背景には、親の要求のどの部分を担い、何ができるようになるかを書く。親へのリンクだけにしない。
- タスクの対応方針は、どう対応するかを文で書く。リンクの一覧だけにしない。根拠になる Design Doc や ADR の節は、文の直後にリンクで示す。
- タスクの完了の条件は、コマンドと期待する結果まで書く。「動く」ではなく、「`node scripts/check-links.js` が切れたリンクを終了コード 1 で報告する」のように書く。
- タスクは親の要求の sub-issue にする。1 つのタスクは、1 つの pull request で閉じられる大きさにする。

## pull request

- 作業を始めた時点で、Draft の pull request を作る。進み具合が外から見える。実装が終わったら Draft を外す。
- 本文の先頭に `Closes #<番号>` を書く。
- 本文は `.github/pull_request_template.md` の 7 節で書く。概要は 2 文から 3 文で、差分を読む前の地図にする。対応内容は、関心事ごとの箇条書きにし、コミットの分け方と揃える。
  - 1 段目は関心事で、太字の名前に「新規」「変更」「削除」を添え、ファイルが 1 つのディレクトリに集まるならそのパスを続ける。
  - 2 段目はファイルかディレクトリごとに、何をどう変えたかを書く。ファイルの一覧を書き写さない。判断した理由は「背景」に書く。
- 背景は、issue と違う点や、作業中に分かったことだけを書く。issue の繰り返しにしない。
- 確認したことには、実行したコマンドと結果を書く。確かめていないことは「未実施」と理由を書く。
- 影響には、利用者のリポジトリへの影響と、互換性のない変更の有無を書く。互換性のない変更は、コミットメッセージにも `!` か `BREAKING CHANGE` を付ける。release-please がバージョンを決めるためである。
- レビューしてほしい点には、判断が分かれた箇所と、捨てた代替案の理由を書く。
- 扱わなかったことは「残したこと」に書き、issue があれば番号を添える。
