# git-commit

メッセージの形式は commitlint が自動でチェックする。ここには、判断が要ることだけを書く。

## 手順

1. `git status`、`git diff`、`git branch --show-current` で現状を確かめる。
2. 変更を関心事ごとに分ける。1 つのコミットは、単独で取り消せる単位にする。
   - 1 つのファイルに複数の関心事の変更が入っていても、1 つのコミットにまとめない。関心事ごとの途中の版を作り、順にステージして分ける。
3. 分け方、対象のファイル、メッセージを、利用者に 1 度でまとめて見せ、確認を取る。
4. まとまりごとに、対象のファイルだけを `git add` する。`git diff --cached` で確かめてからコミットする。
5. フックが失敗したら、原因を直して、新しいコミットを作る。

## メッセージ

```text
<type>(<scope>): <要約> #<issue の番号>

<なぜ変えたか>
```

- 日本語で書く。
- 要約には、このコミットがリポジトリに加える変更を書く。導入する仕組みの働きを書かない。
  - 悪い例は「textlint で文書の表現をチェックする」。チェックした結果のコミットなのか、仕組みを入れたコミットなのかが分からない。
  - 良い例は「textlint を導入し、文書の表現のチェックを追加する」。
  - 動詞は、追加する、導入する、削除する、変更する、修正する、のように、コミットが行う変更を表すものにする。
- type は、変更の名前ではなく性質で選ぶ。
  - `feat` は機能の追加と変更、`fix` は不具合と誤りの修正、`docs` は文書だけの変更。
  - `refactor` は振る舞いを変えない構造の変更、`chore` はほかに当てはまらない設定や保守。
  - ほかの type は、Conventional Commits の標準に従う。
- scope は任意。影響の範囲が明確になるときだけ付ける。
- issue があるときだけ、要約の末尾に番号を付ける。
- 本文には「なぜ」だけを書く。何を変えたかは、差分で分かる。
  - 誤記の修正や整形のように、理由が自明な変更では本文を省く。
  - 3 行以内に収める。収まらないのは、コミットを分ける合図である。
  - 削除や置き換えのように判断を含む変更では、根拠を添える。参照が 0 件だった検索の結果、合意した決定、エラーの内容などである。

## してはいけない操作

- `git add -A` と `git add .` を使わない。対象のファイルを名前で指定する。
- `--amend` と `--no-verify` を使わない。
- 利用者に頼まれていない `git push` をしない。
- `.env`、認証情報、トークンを含むファイルをコミットしない。見つけたら、コミットの前に利用者へ知らせる。
