# docs-writing

このリポジトリの文書の書き方。機械で検出できる規則は textlint に任せ、ここには判断が要る規則だけを書く。  
文書の種類ごとの節の構成と規則は `references/` にある。対象の文書を書く前に、該当するファイルを開く。

## 先に実行する

```sh
pnpm lint:text
```

- 指摘された語は言い換える。`--fix` は使わない。置き換えの候補は機械的で、文が崩れる。
- 使わない語と言い換えの一覧は `prh.yml` だけに持つ。この文書へ写さない。

## 文書ごとの役割

- **PRD:** 誰のどの課題を、何で解決するか。ツールの名前、書式、配置先などの実現方法は書かない。書き方は `references/prd.md`。
- **Design Doc:** 決定済みの設計だけ。全体像と、機能ごとの設計に分ける。書き方は `references/design-doc.md`。
- **ADR:** 選択肢を比較して決める判断。未決のものは「提案」の状態で置く。書き方は `references/adr.md`。
- **context:** 作業の中で繰り返し参照する規約と事実。技術スタック、コードベースの構造、ツールの扱い。コードから読み取れる構造の説明は書かない。書き方は `references/context.md`。
- **`.ai-out/`:** 公開しない作業メモ。Git で追跡しない。
- **CONTRIBUTING.md:** 変更をリポジトリへ取り込むまでの手順。準備、ブランチ、コミット、pull request、チェック、リリース。規約の本文は書かず、context へリンクする。
- **AGENTS.md:** 常に読み込まれる。次の 3 つをすべて満たす内容だけを書く。
  - どの作業でも要る。
  - モデルが推測できない。
  - スキルの説明、自動チェック、README で代替されていない。

内容は各文書の中で完結させる。

## 文書の分割

1 つの文書に詰め込まない。次のどれかに当てはまったら、別の文書に分ける。

- 対象の読者が違う。
- 読み手に求める行動が違う。
- 独立して理解できる話題になっている。
- 更新の頻度が違う。
- 詳細度が大きく違う。
- 食い違ったときの参照先にすべき場所が違う。
- 1 つの文書の中で、なぜ、何を、どう作るかが並び、流れを追いにくい。

分けた文書は、上位と下位の関係でつなぐ。

- 上位の文書は、背景、目的、制約、全体像を持つ。
- 下位の文書は、上位の文書の構成要素 1 つを対象にし、その判断、設計、仕様を持つ。
- 同じ内容を、上位と下位の両方に書かない。上位からは、下位へのリンクだけを置く。

## 文と段落

- 地の文は短く書く。
- 箇条書きと表のセルは、体言止めか終止形。
  - 条件や否定を含む文は、述語を省かない。
  - 助詞は省かない。
- 1 文ごとに行を分ける。続きの文は、行末の半角スペース 2 つで改行する。
  - 「〜し、〜で、〜」と続けない。
  - 従属する内容は、入れ子の箇条書きにする。
  - 入れ子の字下げは、半角スペース 2 つに統一する。4 つと混ぜると、表示が崩れるレンダラがある。
- 出典と ADR へのリンクは、根拠になる文の直後に置く。節や文書の末尾にまとめない。
  - リンクの先頭に、ADR なら「ADR-0001:」のように番号を、外部の資料なら「出典:」を付ける。読み手が、なぜそのリンクがあるかを迷わないためである。
- 文は、その文だけを読んで意味が取れるように書く。読み手の認知の負荷を下げるためである。
  - 「前述の」「上記の」「この方式」のように、離れた文を指す言い方を避ける。指すものを名前で書く。
  - 他の文書を読まないと意味が決まらない書き方をしない。

## 表

表は、行と列の両方に意味がある比較だけに使う。

- 使う例: 選択肢ごとの強みと弱み、frontmatter のキーの一覧
- 使わない例: 用語の一覧、条件と確認方法の組、リスクと備え。箇条書きか短い文にする。

## 図

- 流れのように、文と表では関係が読み取りにくい内容だけを、図にする。表や箇条書きで足りる内容は、図にしない。
- 図は Mermaid で、文書の中に書く。差分が読め、GitHub がそのまま描画する。
- 図の直前に、図が示す内容を 1 文で書く。図だけに書かれた決定を作らない。
- 図の粒度は、文書の層で決める。C4 モデルの段階に合わせる。段階ごとの割り当ては `references/design-doc.md` にある。
  - 出典: [C4 model](https://c4model.com/)
- GitHub が描画できない記法は使わない。C4 の記法が崩れる場合は、同じ段階の内容を flowchart で描く。
- gitGraph のブランチ名は、引用符で囲む。ハイフンや数字で始まる名前は、囲まないと描画に失敗する。
- 確定していない構成は、図にしない。

## 読みやすさ

エージェントが書く文書は長くなりやすい。  
見た目が整っていても、読み手が検証しきれない文書は workslop になる。

- 足す前に、削れる文がないかを見る。
- 同じ内容を 2 つの文書に書かない。
- スキルの本文は 150 行以内に保つ。詳細は `references/` に分ける。
- 変更の履歴、行った作業、残っている作業を文書に書かない。コミットと issue から読み取れる。
- 実装の進み具合のような、現在の状況を文書に書かない。書いた時点から古くなる。あるかないかはリポジトリの中身から、予定は issue から読み取れる。
- 文書の書き方のルールを、その文書の中に書かない。ルールは、このスキルに書く。
- 見出しは、対象の名前ではなく言いたいことにする。Background のような節では特に守る。
- 用語の一覧は、本当に要る語だけにする。一般的でない語を作らない。
- 用語は、公式の文書の表現に揃える。新しい語を使う前に、公式の文書での使われ方を調べる。
  - 日本語の表記は、Claude Code の日本語の公式文書を基準にする。
  - Claude Code などのツールはコーディングエージェント、拡張機能を取得して配置するツールはパッケージマネージャー、そのツールが読むファイルはマニフェストとロックファイルと書く。
  - フックがモデルへ渡す文章は「コンテキストを追加する」、スキルの本文は「オンデマンドで読み込まれる」と書く。
- 題と見出しは、それだけを読んで何の話か分かるように書く。
  - 「働き方」「置き場」「担当」のような、自分で作った抽象的な語を使わない。
  - スキル、フック、textlint のような実際の名前か、具体例で書く。
  - 誰のどれを指すか分からない言い回しを避ける。「利用者が選ぶ拡張機能」ではなく、「使いたい人が、自分の global に入れる genshijin などのプラグイン」と書く。
