# ADR-0010: 開発のプロセスは種類と決める点だけを定め、選んだ結果は YAML で宣言する

## 状態

承認

## 背景

1 つの要求に対して、要件定義、設計、実装、検証といった作業があり、それぞれにレビューがある。  
作業の種類は、どの開発でもほぼ共通である。  
一方、どの順に、どの時点で行うかは、要求やタスクによって変わる。  
次の 3 つが例である。

- Design Doc と ADR を、設計が確定した時点で直すか、検証がすべて終わった時点で直すか。
- タスクへの分解と、実装の issue の起票を、どの時点で行うか。
- 誤記の修正のような小さな変更で、要件定義や設計を行うかどうか。

開発のプロセスの国際規格である ISO/IEC/IEEE 12207 も、同じ構造を採っている。

- プロセスの種類と、それぞれの成果を定める。要求の定義、設計の定義、実装、統合、検証、移行、妥当性確認などである。
- 特定のライフサイクルのモデルや、開発の方法論は、定めも求めもしない。プロセスは、並行して、繰り返して、入れ子にして適用できる。アジャイルの手法にも適用できる。
- すべてのプロセスを使う必要はない。選んで変更して使うことを、正式な適合の形として認めている。
  - [ISO/IEC/IEEE 12207:2026](https://www.iso.org/standard/90219.html)

スクラムも、作業の種類は定めていない。  
スクラムガイドは、スクラムを意図的に不完全な枠組みとし、その中でさまざまなプロセスや技法を使えると述べている。

- [スクラムガイド](https://scrumguides.org/scrum-guide.html)

## 決定

次の 7 点を決めた。

- プロセスは、次の 7 つとする。それぞれに、目的、成果物、完了の条件を定める。
  - 要件定義、設計、実装、検証の設計、検証の実施、取り込み、リリース。
  - 順序は定めない。繰り返すことも、並行して行うことも、前のプロセスへ戻ることも認める。
  - 標準として定めるのは、この 7 つである。プロセスを足すかどうかは、利用者が決める。
- レビューは、どのプロセスにも付けられる共通の仕組みとして定める。レビュー用の HTML への変換は、設計に限らず、どのプロセスのレビューでも使える。
- 要求やタスクごとに決める点を、次の 4 つとする。それぞれに、選択肢と既定の値を定める。
  - どのプロセスを行うか。
  - Design Doc と ADR へ反映する時点。
  - タスクへの分解と、実装の issue の起票の時点。
  - レビューの要否と範囲。
- 選んだ結果は、YAML で宣言する。
  - プロジェクトの既定は、プロジェクトごとの値のファイルに書く。
  - 要求ごとの選択と、プロセスごとの進み具合は、要求ごとの YAML に書く。spec と同じ場所に置く。
- 要求ごとの YAML と spec は、Git で管理する。issue を閉じる時点で、一緒に削除する。
  - Git で管理すると、複数の人やエージェントが、同じ要求の進み具合を共有できる。CI のチェックも読める。
- agent-harness が持つのは、プロセスの定義、決める点と選択肢、YAML の schema、チェック、プロセスの中で使う手段である。作業を次へ進める制御は持たない。ワークフローのハーネスの導入は任意である。導入した場合は、ハーネスが YAML を読んで、作業を次へ進める。
- タスクの種類ごとの流れは用意しない。タスクの種類の違いは、決める点の組み合わせで表す。

## 検討した選択肢

| 選択肢 | 強み | 弱み |
| --- | --- | --- |
| **採用:** プロセスの種類と決める点だけを定め、選んだ結果を宣言する | 要求やタスクごとの違いを表せる。進め方のモデルを問わない。タスクの種類が増えても、定義が増えない | 要求ごとに、決める点を選ぶ手間が要る |
| 節目と時点を固定する | 定義が単純で、チェックしやすい | 反映の時点や起票の時点が違う要求を表せない。小さな変更にも同じ流れを強いる |
| タスクの種類ごとに流れを用意する | 利用者は、種類を選ぶだけで済む | 種類の数だけ流れが増える。当てはまらない要求が出るたびに、種類を足すことになる |
| 何も定めない | このリポジトリが小さく保たれる | ワークフローのハーネスごとに、プロセスの呼び方と成果物が違ってしまう。ハーネスを差し替えられない |

## 影響

### 良い影響

- ワークフローのハーネスは、同じプロセスの定義と YAML を前提にできる。利用者は、ハーネスを差し替えられる。
- 小さな変更と大きな変更を、同じ仕組みで扱える。
- 要求ごとの進み具合が機械で読める形になり、チェックの対象にできる。

### 悪い影響

- 要求ごとの YAML を、書いて保つ手間が増える。
- 決める点と選択肢を増やしすぎると、規格を丸ごと写したような重い仕組みになる。プロセスは 7 つ、決める点は 4 つに留める。
- 進み具合を宣言として持つため、宣言と実態が食い違う場合がある。
