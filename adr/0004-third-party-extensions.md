# ADR-0004: サードパーティの拡張機能はプロジェクトの単位で宣言し、global は最小に保つ

## 状態

承認

## 背景

サードパーティの拡張機能は、global にもプロジェクトにも入れられる。  
global に入れた拡張機能は、すべてのプロジェクトで読み込まれる。

global に拡張機能を足していくと、次の問題が起きる。

- スキルの名前と説明は常に読み込まれる。数が増えると説明が短縮され、モデルが選びにくくなる。説明どうしが矛盾する場合もある。
  - [Rethinking skills and prompts for GPT-6 Astra](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)
- 関係のないプロジェクトにも作用する。文書だけのリポジトリで、コーディングの方針の拡張機能が働く例がある。
- global の規約とプロジェクトの規約が、同じ点を別々に指示する。文体を丁寧語に固定する global の規約と、常体を求めるプロジェクトの規約が衝突した例がある。
- プロジェクトの作業が、global に入っている拡張機能を暗黙の前提にする。他の開発者や CI では再現できない。
- 同じ拡張機能を global とプロジェクトの両方に入れると、2 つが並んで読み込まれる。

## 決定

次の 2 点を決めた。

- サードパーティの拡張機能は、使うプロジェクトのマニフェストに書く。global には入れないことを既定にする。
- global に置いてよいのは、次の 2 つに限る。
  - チャットでの口調のように、成果物に影響しない個人の好み。 成果物に及ぶ場合は、プロジェクトのルールを優先する。
  - 自分がマニフェストを置けないリポジトリで使う拡張機能。
    - マニフェストと配置先を、そのリポジトリの中だけの無視の設定に入れる方法も試した。スキルだけの拡張機能は配置できたが、導入のたびに Git で管理されている `.gitignore` が書き換えられた。フックを含む拡張機能は、Git で管理されている設定ファイルを変更する。この使い方は勧めない。

配置された拡張機能のファイルは、コミットしない。  
サードパーティの拡張機能の本文を、リポジトリに入れないためである。clone の後に、導入のコマンドを 1 度実行する。

## 検討した選択肢

| 選択肢 | 強み | 弱み |
| --- | --- | --- |
| プロジェクトの単位で宣言し、global は最小に保つ | マニフェストを見れば、そのプロジェクトで働く拡張機能がすべて分かる。関係のない拡張機能が読み込まれない | 複数のプロジェクトに同じ宣言を書く。clone の後に導入が要る |
| global を主にし、プロジェクトには固有のものだけを書く | 宣言が 1 か所で済む。すぐ使える | global が増え続ける。プロジェクトが global を暗黙の前提にする |
| global とプロジェクトの両方を、同じ重みで管理する | 柔軟 | どちらに何があるか分かりにくい。同じ拡張機能が 2 つ並ぶ |
| 配置されたファイルもコミットする | clone の直後から使える。パッケージマネージャーが入っていなくても読める | サードパーティの拡張機能の本文がリポジトリに入る。1 つの拡張機能で数百のファイルが増える場合がある |

## 影響

### 良い影響

- global が小さく保たれ、どのプロジェクトでも読み込まれる量が増えない。
- プロジェクトのマニフェストが、そのプロジェクトの拡張機能の唯一の一覧になる。

### 悪い影響

- 複数のプロジェクトで同じ拡張機能を使う場合、プロジェクトごとに宣言とバージョンの更新が要る。
- パッケージマネージャーを入れていない人は、clone しただけでは拡張機能を使えない。
- global から外す作業が、利用者ごとに 1 度要る。
