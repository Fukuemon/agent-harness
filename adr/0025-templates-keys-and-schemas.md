# ADR-0025: 写す先が利用者ごとに違うテンプレートは references/ に置き、キーを尋ねる場所と schema の有無はパッケージが決める

## Status

承認

## Context

ADR-0023 で、アプリを作るための 5 つの関心をパッケージにし、テンプレートの置き場とキーの渡し方を決めた。  
パッケージを実装してレビューした結果、ADR-0023 の次の 3 つの判断と実装が合わなくなった。この ADR は、この 3 つを置き換える。

- 導入で必ず写すテンプレートは `assets/` に、利用者が選んで写すテンプレートは `references/` に置く。
  - デザインシステムの文書の骨組みと画面仕様書のテンプレートは、どの利用者にも写すが、写す先を利用者に尋ねる。
  - setup-agent-harness は `assets/` を全部、同じパスへ写す。`assets/` に置くと、尋ねた先と違う場所にも写る。
  - setup-agent-harness は既にあるファイルを写さない。利用者がテンプレートを別の置き場へ移した後に導入のスキルを流し直すと、元のパスにまた写る。
- 値は、各パッケージの導入のスキルが利用者に尋ねて書く。
  - 画面仕様書のキーは、画面仕様書を書くスキルとその点検だけが読む。導入のスキルを別に作ると、同じ手順が 2 つのスキルに分かれる。
  - 文書のサイトのキーも、サイトを公開するスキルとその組み立てのスクリプトだけが読む。CI のワークフローのテンプレートは、そのスキルが写す。
  - 検証のエビデンスの置き場のキーは、既定値があり、尋ねなくても動く。
- キーの一覧と schema は、各パッケージの Design Doc と `schemas/` が持つ。
  - 検証と E2E のキーは、スキルの本文だけが読む。core の schema は知らないキーを拒まないので、schema がなくてもチェックは落ちない。
  - デザインシステムは、値の形をこのリポジトリのテストで確かめるために schema を持つ。

## Decision

次の 3 点を決めた。

- テンプレートの置き場は、写し方で分ける。
  - 導入のときに、どの利用者にも同じパスへ写すテンプレートは `assets/` に置く。
  - 利用者が選んで写すテンプレートと、写す先が利用者ごとに違うテンプレートは `references/` の下に置く。
    - 写すのは、パッケージのスキルの手順か、スキルの `scripts/` のスクリプトである。
  - パッケージが直していくコード（モックの共通の JS など）を写すスクリプトは、既にあるファイルとの差分を示し、利用者が選んだときだけ上書きする。
- 導入のスキルを持つかは、パッケージが決める。
  - 導入の作業（依存の追加、CI への組み込み）を、毎回使うスキルの手順と分けたいパッケージは、導入のスキルを持つ。今は design-system と e2e が持つ。
  - 分けないパッケージは、キーを読むスキルの「初めて使うとき」の手順で、キーを尋ねて書き、テンプレートを写す。今は screens と docs-site が当たる。
  - 既定値のあるキーは、尋ねずに既定値を使ってよい。今は verification が当たる。
  - ADR-0023 の、既に値のファイルにあるほかのパッケージの値を尋ねるときの候補に示す決まりは、変えない。
- schema は、キーの値の形をスクリプトかテストで確かめるパッケージだけが `schemas/` に持つ。
  - どちらもないパッケージは、Design Doc の Interface にキーの一覧と意味を書く。

## Considered Options

テンプレートの置き場の選択肢。

| 選択肢 | 強み | 弱み |
| --- | --- | --- |
| **採用:** 写す先が利用者ごとに違うテンプレートも `references/` に置く | 尋ねた先にだけ写る。導入のスキルを流し直しても、元のパスに写らない | 写す手順かスクリプトを、パッケージごとに持つ |
| `assets/` に置き、写した後に利用者が移す | 写す仕組みが setup-agent-harness の 1 つで済む | 流し直すたびに元のパスへ写る。移す手間が利用者に残る |
| setup-agent-harness に、写す先を尋ねる仕組みを足す | 写す仕組みが 1 つで済む | core が、入れていないパッケージの置き場のキーを持つ |

導入のスキルの選択肢。

| 選択肢 | 強み | 弱み |
| --- | --- | --- |
| **採用:** 導入の作業を分けたいパッケージだけが持つ | 導入の作業のないパッケージで、スキルを増やさずに済む | パッケージによって、キーを尋ねる場所が違う |
| どのパッケージも導入のスキルを持つ | 尋ねる場所がそろう | 手順が 2 つのスキルに分かれ、読み込まれるスキルが増える |

schema の選択肢。

| 選択肢 | 強み | 弱み |
| --- | --- | --- |
| **採用:** 値の形をスクリプトかテストで確かめるパッケージだけが持つ | 使われない schema を保守せずに済む | schema のないキーは、書き誤ってもチェックが見つけない |
| どのパッケージも持つ | 値のファイルの形がどのパッケージでも分かる | 読まれない schema を、キーを変えるたびに直す |
| core の schema にまとめる | 1 つのファイルで全部のキーを確かめられる | core が、入れていないパッケージのキーを持つ |

## Consequences

### Positive

- 利用者が置き場を変えても、テンプレートが元のパスに写らない。
- パッケージが直したコードを、利用者が差分を見てから取り込める。
- 読まれない schema を保守せずに済む。

### Negative

- テンプレートを写す手順かスクリプトが、パッケージごとに要る。写し方の規則（既にあるファイルを飛ばす、差分を示す）は、それぞれが持つ。
- schema のないキーは、書き誤ると読まれず、既定値が使われるか、スキルが利用者に尋ね直す。
- キーを尋ねる場所が、導入のスキルと、毎回使うスキルの 2 通りになる。どちらかは各パッケージの Design Doc に書く。
