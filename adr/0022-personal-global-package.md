# ADR-0022: 個人の global の構成をパッケージ global に置き、製品のパッケージと分けて扱う

## Status

承認

## Context

このリポジトリの開発者は、どのリポジトリでも使う規約、スキル、output style を、端末ごとに別の仕組みで配っていた。

- dotfiles が、chezmoi で `~/.claude/CLAUDE.md` と `~/.codex/AGENTS.md` を書き出す。同じ本文を 2 つ持つ。
- 別の端末では、公開しないリポジトリの apm のパッケージから、`apm install -g` で配る。公開できない値を含むためである。

2 つの規約は同じ作法を別々に持ち、片方だけが古くなっていた。規約の大半とスキルの多くは公開できない値を含まない。  
global で使いたいスキルのうち write-prose と write-skill は、このリポジトリの docs と core にある。

[ADR-0004](0004-third-party-extensions.md) は、利用者のプロジェクトへの既定として、サードパーティの拡張機能をプロジェクトの単位で宣言し、global を最小に保つと決めている。

apm 0.32.0 と作業用の HOME で、次を確かめた。

- パッケージの依存に書いた相対のパス（`../docs/skills/write-prose`）は、パッケージを手元のパスで導入すると解決されず、警告もなく配置されない。
- 同じスキルを `Fukuemon/agent-harness/packages/docs/skills/write-prose` と書くと、GitHub から取得して配置される。
- 手元のパスの依存は、ディレクトリの名前で見分けられる。名前が同じ 2 つのパッケージを並べると、後の 1 つだけが配置される。

## Decision

次の 4 点を決めた。

- 個人の global の構成のうち、公開できるものを `packages/global` に置く。規約、output style、スキル、global に入れるサードパーティの拡張機能を持つ。dotfiles と、公開しないパッケージにあった規約を統合し、dotfiles は規約を持たない。
- パッケージ global は、利用者に勧める製品ではない。個人の端末と使うツールを前提に書くためである。
  - ルートのプラグインの一覧に載せない。
  - release-please の対象とパッケージの本文の固有の名前のチェックから外す。
  - ADR-0004 は、利用者のプロジェクトへの既定として変えない。
- 公開できない値を含む規約とスキルは、公開しないリポジトリのパッケージに置く。user scope のマニフェスト `~/.apm/apm.yml` に、2 つのパッケージを手元のパスで並べる。手元のパスなら、編集が `apm install -g` だけで配置先に届く。公開しないパッケージのディレクトリには、`global` と違う名前を付ける。
- ほかのパッケージのスキルは、このリポジトリを指す依存で参照し、ファイルを複製しない。相対のパスは解決されないためである。ref は書かず、`apm update -g` で進める。

`packages/global` を変えたコミットと pull の後は、lefthook が `scripts/apply-global.mjs` を呼んで配置し直す。

## Considered Options

| 選択肢 | 強み | 弱み |
| --- | --- | --- |
| **採用:** このリポジトリの `packages/global` に置き、製品と分けて扱う | write-prose などを同じリポジトリから参照できる。規約とスキルの元のファイルが、公開できるものと公開できないものの 2 か所になる | 製品のリポジトリに個人の構成が入る。製品と分けるための除外の設定が 3 つ要る |
| 個人の構成のための別の公開のリポジトリを作る | ADR-0004 の既定と、同じリポジトリの中で食い違わない | リポジトリが 1 つ増え、CI と文書のチェックを別に用意する |
| 公開しないリポジトリと dotfiles に置いたままにする | 変更が要らない | 同じ規約を 2 か所で保守し続ける。公開できるスキルを、公開しないリポジトリを使えない端末で使えない |

## Consequences

### Positive

- global の規約の元のファイルが、公開できるものについて 1 か所になる。
- どの端末でも、`~/.apm/apm.yml` にパッケージ global を書けば同じ構成を再現できる。

### Negative

- 製品のパッケージとの違い（プラグインの一覧、release-please、固有の名前のチェック）を、新しい仕組みを足すたびに確かめる。
- ほかのパッケージのスキルは、main へ取り込んで `apm update -g` を実行するまで、global に届かない。
- output style は apm が配置しないので、`~/.claude/output-styles/` へ手で写す。
