# ADR-0005: 自動でチェックできるルールは textlint などに任せ、できないルールは 1 つのスキルにまとめる

## Status

承認

## Context

### ルールをモデルに守らせる手段

Claude Code には、ルールをモデルに守らせる手段が 5 つある。Codex CLI にも、同じ名前のフックとスキルがある。

- **規約ファイルに書く。** 
  - CLAUDE.md や AGENTS.md は、セッションの開始時に読み込まれる。
    - 指示は助言にとどまる。公式の文書は、1 ファイル 200 行未満を目安にしている。
    - [How Claude remembers your project](https://code.claude.com/docs/en/memory)
- **フックでコンテキストを追加する。** 
  - セッションの開始やプロンプトの送信のたびにスクリプトが動き、返した文章がモデルのコンテキストに入る。
    - 公式の文書は、この手段を、現在のブランチや直前の操作の結果のような、その時点の状態を伝える用途に勧めている。変わらない指示には規約ファイルを使うよう書いている。
    - 命令の形で書いた文章は、モデルがプロンプトへの攻撃とみなし、コンテキストとして扱わない場合がある、とも書いている。
    - [Hooks reference](https://code.claude.com/docs/en/hooks) — 「Add context for Claude」の節
- **スキルにする。** 
  - 名前と説明だけが常にコンテキストに入り、本文はスキルが呼ばれたときにオンデマンドで読み込まれる。
    - スキルは、使われなくても、1 つごとに毎回のコンテキストを使う。数が多いと、説明が短縮される。
    - [Extend Claude with skills](https://code.claude.com/docs/en/skills)
- **編集の後のフックで、自動でチェックする。** 
  - ファイルの編集の後にスクリプトが必ず動く。公式のガイドは、編集の後の自動整形を例に挙げている。
    - [Automate actions with hooks](https://code.claude.com/docs/en/hooks-guide) — 「Auto-format code after edits」の節
- **操作の前のフックで止める。** 
  - ツールの実行の前にスクリプトが動き、操作を拒否できる。公式のガイドは、保護したファイルの編集の拒否を例に挙げている。
    - 同じガイドの「Block edits to protected files」の節

公式のガイドは、規約ファイルの指示は助言であり、フックは決定的に実行される、と区別している。

- [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)

5 つを比べると、次のようになる。


| 手段                  | 守られたかを確かめられるか | コンテキストを使うとき             |
| ------------------- | ------------- | ----------------------- |
| 規約ファイルに書く           | 確かめられない       | 常に                      |
| フックでコンテキストを追加する     | 確かめられない       | フックが動くたび。関係のない作業でも追加される |
| スキルにする              | 確かめられない       | 説明は常に。本文は呼ばれたときだけ       |
| 編集の後のフックで、自動でチェックする | 確かめられる        | 違反があったときだけ              |
| 操作の前のフックで止める        | 確かめられる        | 拒否したときだけ                |


### 例に挙げる拡張機能

この文書で名前を出す拡張機能は、次のとおりである。

- **genshijin:** モデルの返答を短い日本語にして、トークンを減らすプラグイン。セッションの開始とプロンプトの送信のフックを持つ。プロンプトのたびに、口調の指示をコンテキストに追加する。
  - `.claude-plugin/plugin.json:13-38` / [github](https://github.com/InterfaceX-co-jp/genshijin/blob/968d3c449499fdefc00aff9f1fe9c52c4dfdc7ae/.claude-plugin/plugin.json#L13-L38)
  - `hooks/genshijin-mode-tracker.js:204-212` / [github](https://github.com/InterfaceX-co-jp/genshijin/blob/968d3c449499fdefc00aff9f1fe9c52c4dfdc7ae/hooks/genshijin-mode-tracker.js#L204-L212)
- **ponytail:** 最も単純な解決を選ばせる、コーディング向けのプラグイン。セッションの開始、サブエージェントの開始、プロンプトの送信のフックを持つ。セッションの開始のフックが、方針の全文をコンテキストに追加する。
  - `hooks/claude-codex-hooks.json:1-41` / [github](https://github.com/DietrichGebert/ponytail/blob/e3ba2aa6f1e6f0bc4d69eb09c9f0d0a93af56156/hooks/claude-codex-hooks.json#L1-L41)
- **natural-japanese:** 日本語の文書を読みやすく直すためのプラグイン。フックを持たず、スキルだけである。スキルの手順の中で、付属のスクリプトを使って文章をチェックする。
  - [natural-japanese](https://github.com/coji/natural-japanese)
- **textlint:** 日本語の文章を、ルールに沿って自動でチェックするツール。このリポジトリでは、AI に多い語、使わない用語、常体と丁寧語の混在、1 文の長さをチェックしている。
  - [textlint](https://textlint.org/)

### 起きている問題

文章向けのスキルやプラグインは、1 つで複数のことを指示する。  
口調、使う語、文の長さ、文書の構成、内容の質などである。  
複数を入れると、同じことを別々に指示する。

フックでコンテキストを追加するプラグインは、プロンプトのたびに指示を足すため、他のルールより強く働きやすい。  
口調を丁寧語に固定する genshijin の指示と、常体を求めるこのリポジトリのルールが衝突した例がある。

## Decision

次の 4 点を決めた。

- 機械で判定できるルールは、textlint などの自動チェックに任せる。スキルや AGENTS.md には書かない。
  - 文書を編集した後に textlint を実行するフックも用意する。コマンドを実行し忘れても、チェックされる。
- 機械で判定できないルールは、スキル「docs-writing」の 1 つにまとめる。本文は 150 行以内に保つ。
- フックで毎回コンテキストを追加するプラグインは、agent-harness のパッケージとして作らない。このリポジトリの `apm.yml` にも入れない。
  - 変わらないルールをフックで足すのは、公式の文書が勧める使い方ではない。関係のない作業でもコンテキストを使い、守られたかも確かめられない。
- モデルが指示なしで行うことは、どこにも書かない。不足に気づいた項目だけを足す。

文章のルールは、次のように分ける。


| ルール                                  | どこで持つか                                                      |
| ------------------------------------ | ----------------------------------------------------------- |
| AI に多い語、使わない用語、英字と数字だけの記号による採番       | textlint                                                    |
| 常体と丁寧語を混ぜない                          | textlint                                                    |
| 1 文の長さ                               | textlint                                                    |
| PRD、Design Doc、ADR に何を書くか。節の順。出典の示し方 | スキル「docs-writing」                                           |
| 事実と判断を分ける、異常系を書く、などの一般的な文章術          | 持たない。モデルに任せる                                                |
| チャットでの口調                             | agent-harness は扱わない。使いたい人が、自分の global に genshijin などを入れる    |
| ブログなどの読み物のリズム                        | agent-harness は扱わない。使いたい人が、そのリポジトリに natural-japanese などを入れる |


サードパーティのスキルやプラグインを入れるときは、上の表のどの行を指示するものかを確かめる。  
既に持っている行と重なる場合は、入れない。

コードのコメントのルールは、次のように分ける。

| ルール | どこで持つか |
| --- | --- |
| コメントを足したかどうか。lint や型のチェックを抑制するコメントを足したかどうか | ファイルの編集の後のフック。足されたときだけ、確かめるよう促す文をコンテキストに追加する |
| そのコメントを残してよいかの判断の基準 | スキル「code-comments」 |
| 何を作るか、どこまで作るか | agent-harness は扱わない。使いたい人が、そのプロジェクトに ponytail などを入れる |

- コメントのルールを、AGENTS.md には書かない。文書だけの作業でもコンテキストを使うためである。
- セッションの開始のフックで、毎回コンテキストに追加する形にもしない。ルールが要るのは、コメントを書いた時点だけである。
- 編集の後のフックは、編集を拒否しない。コメントを足したかどうかは機械で判定できるが、残してよいかどうかは判定できないためである。
- 公式の文書は、フックで追加するコンテキストの用途に、直前の操作に応じた条件付きのプロジェクトのルールを挙げている。この使い方は、それに当たる。
  - [Hooks reference](https://code.claude.com/docs/en/hooks) — 「Add context for Claude」の節
- この形は、サブエージェントにも届く。Claude Code では、設定ファイルとプラグインのフックがサブエージェントの中でも動く。スキルはサブエージェントに引き継がれない。
  - [Create custom subagents](https://code.claude.com/docs/en/sub-agents) — 「What loads at startup」の節

## Considered Options


| 選択肢                                 | 強み                                                   | 弱み                                                |
| ----------------------------------- | ---------------------------------------------------- | ------------------------------------------------- |
| **採用:** 自動チェックと 1 つのスキルに分ける                 | 同じことを 2 か所で指示しない。自動チェックのルールは、スキルが入っていない環境や CI でも守られる | スキルやプラグインを入れるたびに、何を指示するものかを確かめる手間が要る              |
| スキルやプラグインごとに、入れるかどうかだけを決める          | 判断が簡単                                                | 1 つのスキルが複数のことを指示するため、重なりに気づけない                    |
| 文章のルールを、フックで毎回コンテキストに追加するプラグインにまとめる | 忘れられにくい                                              | 文章を書かない作業でも追加される。守られたかを確かめられない                    |
| 文章の品質基準を網羅したスキルを 1 つ作る | 内容が網羅的になる | 長い本文を保守することになる。textlint で足りるルールと、モデルが指示なしで行うことを含む |


## Consequences

### Positive

- 同じことを複数のスキルやプラグインが指示する衝突が起きにくい。
- 自動チェックのルールは、モデルが指示を守るかどうかに左右されない。
- 新しいスキルやプラグインを入れるかどうかを、同じ基準で判断できる。文章のほかの領域にも使える。

### Negative

- 一般的な文章術を持たないことで、文書の質が落ちる可能性がある。落ちた項目は、気づいた時点で足す。
- global に genshijin のようなプラグインを入れている人は、このリポジトリのルールと衝突する。どちらを優先するかを AGENTS.md に書く必要がある。
