# ADR-0014: リポジトリの運用の取り決めはパッケージ core に置き、process はプロセスの定義と進み具合だけを持つ

## Status

承認

## Context

開発プロセスのパッケージは、プロセスの定義と、プロセスの中で使う手段の両方を持っていた。  
手段は、コミットとブランチ名の規約のスキル、issue と pull request の雛形、コードのコメントの規約のスキルとフックである。  
一方で、ブランチの運用とリリースの既定は、core の CONTRIBUTING.md のテンプレートにあり、運用の取り決めが 2 つのパッケージに割れていた。

- ブランチの運用、バージョンの付け方、コミットの規約、issue と pull request の規則は、どのプロダクトにも要る。開発プロセスをどの順で踏むかとは別の関心である。
- process を入れない利用者にも、これらの規約は要る。

## Decision

次の 3 点を決めた。

- リポジトリの運用の取り決めは、パッケージ `core` に置く。中身は、ブランチとリリースの既定、コミットの規約のスキル、issue と pull request の規則のスキルと form の雛形、コードのコメントの規約のスキルとフックである。
- `process` は、プロセスの定義、要求ごとの選択、宣言の schema、進み具合のチェックだけを持つ。手段は持たない。
- 次のバージョンを決める手段（release-please か changesets）は、テンプレートに選択肢として示すにとどめる。どちらを使うかは利用者が決める。

## Considered Options

| 選択肢 | 強み | 弱み |
| --- | --- | --- |
| **採用:** 運用の取り決めを `core` に置く | `core` を入れれば運用が揃う。`process` の責務がプロセスの定義に閉じる | `core` が大きくなる |
| 手段を `process` に置いたまま | パッケージの構成を変えない | 運用の取り決めが 2 つのパッケージに割れる。`process` を入れない利用者に規約が届かない |
| 運用の取り決めを 5 つ目のパッケージにする | `core` が小さいまま | どのプロダクトにも要るものを、別に入れる手間が増える。`core` と分ける理由がない |

## Consequences

### Positive

- 利用者は、`core` を入れるだけで、ブランチ、コミット、issue と pull request、コードのコメントの規約を得る。
- `process` は、プロセスの定義と進み具合だけを扱う。ワークフローのハーネスが読むものも、そこに閉じる。

### Negative

- `core` のスキルが 5 つになり、導入のときに配置されるファイルが増える。
- コミットの規約とバージョンの決め方は結びつくが、バージョンを決める手段は利用者が選ぶので、規約と手段の対応は利用者が保つ。
