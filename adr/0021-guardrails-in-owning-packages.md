# ADR-0021: ガードレールは独立したパッケージにせず、規則に関わるパッケージが持つ

## Status

承認。ADR-0013 のうち、guardrails を独立したパッケージとする部分を、この決定が置き換える。

## Context

ガードレールは、取り返しのつかない操作を、実行の前にプログラムで止める仕組みである。  
これまでの設計では、パッケージ guardrails が、止める仕組みと 3 つの規則を持っていた。規則は、保護ブランチ、禁止するコマンド、秘密情報である。

- ガードレールと自動チェックは、PRD の内容の分類では、パッケージではなく内容の種類である。文書のチェックは docs が、コードのコメントのフックは core が、それぞれ自分の関心事について持っている。
- 3 つの規則は、どれもリポジトリの運用に関わる。ブランチ、コマンド、コミットである。ブランチとリリースの既定とコミットの規約は、ADR-0014 で core に置いた。
- 規則は `context/project.yml` の `guardrails` の下に規則ごとのキーで書き、キーがない規則は無効である。パッケージを外さなくても、規則ごとに止められる。
- スクリプトは、実行時にほかのパッケージのファイルを読まない（ADR-0013）。

## Decision

次の 3 点を決めた。

- ガードレールを、独立したパッケージにしない。ガードレールの規則は、その規則が守る関心事を持つパッケージに置く。
- 今の 3 つの規則と、それを止める仕組みは、core に置く。3 つともリポジトリの運用の取り決めを守るものだからである。
- `context/project.yml` のキーの名前 `guardrails` は変えない。キーの名前を変えると、schema の `version` を上げる必要がある。キーの持ち主は core になる。

ほかのパッケージが自分の関心事のガードレールを持つときは、そのパッケージが判定のスクリプトを自前で持つ。core の仕組みを実行時に読み込まない。

## Considered Options

| 選択肢 | 強み | 弱み |
| --- | --- | --- |
| **採用:** 規則に関わるパッケージが持つ。今の 3 つは core | 運用の取り決めと、それを守る規則が 1 つのパッケージに揃う。パッケージが 3 つに減る | ガードレールだけを入れることはできない。規則を止めるには、`project.yml` のキーを消す |
| 独立したパッケージ guardrails を作る | ガードレールだけを入れられ、パッケージごと外せる | 保護ブランチの名前を、core の運用の取り決めと guardrails の両方が扱う。ガードレールを、内容の種類ではなく 1 つの関心事として扱うことになる |
| 止める仕組みを core に置き、ほかのパッケージは規則だけを足す | 仕組みを 1 か所に持てる | 実行時にほかのパッケージのファイルを読む。ADR-0013 と食い違う |

## Consequences

### Positive

- core を入れれば、運用の取り決めと、それを守るガードレールが揃う。
- パッケージの境界が、関心事の境界と一致する。

### Negative

- core が大きくなる。
- 複数のパッケージがガードレールを持つと、判定の仕組みがパッケージごとに重複する。
