# ADR-0017: 文書のチェックのスクリプトは hooks/ に置き、利用者の lefthook と CI はパッケージマネージャーの配置先から呼ぶ

## Status

承認

## Context

パッケージ docs の文書のチェックは、3 つの場所で動く。コーディングエージェントの編集後のフック、利用者の lefthook、利用者の CI である。  
利用者のリポジトリから、パッケージのスクリプトをどう呼ぶかを決める必要があった。

- パッケージマネージャーが利用者のリポジトリへ配置するのは、スキルと `hooks/` だけである。`scripts/` は配置しない。配置先は Git で追跡しない。
- 全体像の Design Doc は、Git のフックを使うパッケージの導入の方法として、lefthook の `remotes` を挙げている。
- lefthook 2.1.6 で確かめると、`remotes` で取り込んだ設定の `run` からは、取り込んだリポジトリのファイルのパスを得る手段がなかった。取り込んだ先のディレクトリ名は、利用者が指定した ref で変わる。
- `remotes` の `scripts` は、取り込んだリポジトリのルートの `.lefthook/<フック名>/` にあるスクリプトを動かせる。取り込んだ側の設定で `source_dir` を変えると、利用者自身の `.lefthook/` のスクリプトが見つからなくなった。

## Decision

次の 3 点を決めた。

- 文書のチェックの 3 つのスクリプト（経緯の混入、リンク、実装とのずれ）と、共通の処理は、docs の `hooks/` に置く。依存するライブラリを持たない。
- 利用者の lefthook と CI は、パッケージマネージャーの配置先（`.claude/hooks/docs/hooks/` か `.codex/hooks/docs/hooks/`）にあるスクリプトを呼ぶ。CI は、チェックの前に `apm install --frozen` を実行する。
- 利用者のリポジトリへの組み込みは、docs の導入のスキル setup-design-docs が行う。配置先を探し、CONTRIBUTING.md、lefthook、CI に呼び方を書く。

## Considered Options

| 選択肢 | 強み | 弱み |
| --- | --- | --- |
| **採用:** パッケージマネージャーの配置先から呼ぶ | 編集後のフックと CLI のバージョンが、ロックファイルの 1 つの ref に揃う。追加の取得の手段が要らない | 配置先のパスがコーディングエージェントの種類で変わる。コーディングエージェントの標準の方法で入れた利用者は、lefthook と CI から呼べない |
| lefthook の `remotes` と、ルートの `.lefthook/` | lefthook の標準の仕組みで、ref でバージョンを固定できる | パッケージの外にファイルが置かれる。パッケージマネージャーとは別に ref を固定し、2 つのバージョンがずれうる。CI にも lefthook が要る |
| スクリプトを利用者のリポジトリへ写す | どの導入の方法でも呼べる | 写したスクリプトが利用者のファイルになり、パッケージの更新が届かない。編集後のフックと処理が二重になる |

## Consequences

### Positive

- 同じ処理を、編集後のフック、lefthook、CI が使う。指摘の基準が場所によって変わらない。
- パッケージを更新すると、`apm install` だけでチェックも新しくなる。

### Negative

- CI は、チェックの前に `apm install --frozen` を実行する必要がある。
- `hooks/` に、フックではない CLI のスクリプトとテストも置かれ、利用者のリポジトリへ配置される。
