# ADR-0023: 検証、E2E、デザインシステム、画面仕様書、文書のサイトを関心ごとのパッケージにし、組み合わせは値のファイルのキーで渡す

## Status

承認

## Context

利用者のリポジトリの 1 つで、アプリを作るための 5 つの取り決めと手段を作り、運用で固めた。検証とエビデンス、E2E のテスト、デザインシステム、画面仕様書、文書のサイトである。  
ほかのリポジトリには写して直すほかなく、撮影の仕組みは既に 3 か所に違うバージョンがある。

- 製品のパッケージは core と docs だけで、5 つの関心はどちらにもない。docs は、画面ごとの UI の設計を持たないと決めている。
- 観点の設計と撮影のスキル（design-test-cases、capture-browser-evidence）は、個人の構成の packages/global にあり、利用者に届かない。
  - ADR-0022: [個人の global の構成をパッケージ global に置き、製品のパッケージと分けて扱う](0022-personal-global-package.md)
- ADR-0014 は、リポジトリの運用の手段を 5 つ目のパッケージにせず core に置いた。どのプロダクトにも要るためである。
  - ADR-0014: [リポジトリの運用の取り決めはパッケージ core に置き、process はプロセスの定義と進み具合だけを持つ](0014-operations-in-core.md)
- core 以外のパッケージは互いに依存せず、スクリプトは他のパッケージのファイルを探さない。
  - ADR-0013: [共通の基盤はパッケージ core に置き、ほかのパッケージはそれを前提にする](0013-core-package.md)
- 5 つの関心は、元のリポジトリでは生成物でつながっている。デザインシステムの意味のトークンから作る CSS を、画面仕様書のモックと文書のサイトが読む。モックの要素の識別子を、E2E のテストが使う。画面仕様書は、カタログの URL を指す。
- パッケージの本文には、利用者によって違うツールの名前を書かない。CI は `packages/*/skills/**/*.md` を `prh-packages.yml` の語と照らす。
- 導入のスキル setup-agent-harness は、配置されたスキルの `assets/` を全部、利用者のリポジトリに写す。
- E2E のテストと録画の kit は、ブラウザのテストのツールに依るコードである。

## Decision

次の 4 点を決めた。

- 5 つのパッケージを足す。core に入れず、利用者が 1 つずつ選んで入れる。画面を持たないプロダクトや、文書のサイトを公開しないプロダクトには要らないためである。

  | パッケージ | 持つもの |
  | --- | --- |
  | `verification` | 観点の設計、検証の spec の書き方、撮影と確認、pull request へのエビデンスの添付 |
  | `e2e` | E2E のテストの書き方、テストと録画の kit のコード、テストの書き方の lint の規則 |
  | `design-system` | トークンの段の分け方、デザインシステムの文書の型、アクセシビリティの基準と確認の方法、カタログの構成 |
  | `screens` | 画面仕様書の型（状態、構成要素、操作できるモック）、モックの共通のファイル、規約の点検 |
  | `docs-site` | 文書、カタログ、図を 1 つのサイトに並べ、公開先へ公開する構成 |

- 組み合わせは、各パッケージが `context/project.yml` に持つ自分のキーで受け取る。パッケージのスクリプトは、ほかのパッケージのキーを読まない。
  - 2 つのパッケージが同じ値を使うとき（トークンの CSS のパス、カタログの URL など）は、それぞれのキーに同じ値を書く。
  - 値は、各パッケージの導入のスキルが利用者に尋ねて書く。既に値のファイルにあるほかのパッケージの値は、尋ねるときの候補に示す。この判断は [ADR-0025](0025-templates-keys-and-schemas.md) で置き換えた。
  - キーの一覧と schema は、各パッケージの Design Doc と `schemas/` が持つ。この判断は [ADR-0025](0025-templates-keys-and-schemas.md) で置き換えた。
- ツールに依るものは、文章の外に置く。
  - `SKILL.md` と `references/` の文章は、一般の語で書く。ツールの具体は、利用者の context（例: `context/testing/`）が持つ。
  - ツールに依る設定、ワークフロー、コードは、kit のコードと、スキルの雛形のファイルに置いてよい。どのツールの雛形かは、ディレクトリの名前で分ける。
  - 導入で必ず写す雛形は `assets/` に、利用者が選んで写す雛形は `references/` の下に置く。setup-agent-harness が `assets/` を全部写すためである。この判断は [ADR-0025](0025-templates-keys-and-schemas.md) で置き換えた。
- 画面仕様書のモックは、静的な HTML を基準にする。コーディングエージェントが書き、トークンの CSS と、パッケージが配るモックの共通の CSS だけを読み、外部の URL を読まない。デザインのツールのファイルは、画面仕様書から参照してよいが、基準にしない。
  - 画面仕様書は、機能の Design Doc が持つ処理と通信を書かず、表示、状態、操作だけを持つ。置き場は `screens` のキーで決め、既定は `docs/screens/` にする。

design-test-cases と capture-browser-evidence は、本文からツールとホスティングサービスの名前を外して `verification` へ移す。2 つは互いを名前で呼ぶので、同じパッケージに置く。packages/global は、移したスキルを依存で参照する。

パッケージごとのバージョンと、kit の npm のレジストリでの公開は、ADR-0024 で決める。

## Considered Options

パッケージの分け方の選択肢。

| 選択肢 | 強み | 弱み |
| --- | --- | --- |
| **採用:** 関心ごとに 5 つに分ける | 要る関心だけを入れられる。変化の速い e2e が、ほかのパッケージの更新を待たない | 製品のパッケージが、core、docs、process を合わせて 8 つになる。生成物でつながる値を、キーで渡す設計が要る |
| verification と、UI（デザインシステム、画面仕様書、文書のサイト）の 2 つにする | 数が増えにくい。トークンの受け渡しがパッケージの中で閉じる | 画面仕様書だけ、文書のサイトだけを使えない |
| docs と core に入れる | パッケージが増えない | core は全員に届くので、画面のないプロダクトにも撮影のスキルが届く。docs の責務が広がる |

組み合わせの渡し方の選択肢。

| 選択肢 | 強み | 弱み |
| --- | --- | --- |
| **採用:** 各パッケージが自分のキーを持ち、導入のスキルが尋ねる | ADR-0013 を変えずに済む。1 つを外しても、ほかのパッケージが動く | 同じ値を 2 つのキーに書く。値を変えるときに両方を直す |
| 共有のキー（例: `ui.tokens_css`）を core の schema に置く | 値を 1 か所に書ける | core が、入れていないパッケージのキーを持つ |
| パッケージ同士の依存を許し、スキルを名前で呼ぶ | 手順を 1 つのスキルにまとめられる | 1 つを外すと、ほかのスキルの手順が切れる |

## Consequences

### Positive

- 利用者は、プロダクトに要る関心だけを入れられる。CLI やライブラリのリポジトリは verification だけを入れられる。
- 撮影の仕組みとスキルの元のファイルが 1 か所になり、直しが利用者の全員に届く。
- 画面仕様書の形と置き場が決まり、機能の Design Doc との分担が明確になる。

### Negative

- 製品のパッケージが、core、docs、process を合わせて 8 つになる。ルートの一覧、release-please の設定、README の表を、足すたびに直す。
- 同じ値を複数のキーに書くので、値の食い違いを導入のスキルとチェックで見つける必要がある。
- ツールに依る雛形を本文の外に置くため、雛形の更新が文章のチェックの対象にならない。雛形のテストで代わりに確かめる。
- packages/global から移したスキルは、main に取り込んで `apm update -g` を実行するまで global に届かない。user scope に残った古い写しは手で消す。
