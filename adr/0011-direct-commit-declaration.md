# ADR-0011: 保護ブランチへの直接コミットは、プロジェクトごとの値での宣言だけで許す

## 状態

承認

## 背景

ガードレールは、保護ブランチへの直接コミットを拒否する。既定は拒否である。  
一方で、直接コミットしてよい場面がある。リポジトリの立ち上げの時期、個人のリポジトリ、文書だけの変更が候補だった。

許す条件は、フックがコミットの時点で判定できる形でなければ働かない。  
候補ごとに、判定できるかどうかは次のとおりである。

- リポジトリの立ち上げの時期は、自動では判定できない。タグがまだない、といった代理の指標はあるが、タグを使わない利用者もいる。
- 個人のリポジトリは、自動では判定できない。remote の所有者と committer を比べる方法は、fork や複数のアカウントでは正しく働かない。
- 文書だけの変更は、ステージしたパスで判定できる。ただし、何が文書かは利用者ごとに違う。AGENTS.md やスキルの本文も文書だが、コーディングエージェントの挙動を変える。

## 決定

次の 3 点を決めた。

- 直接コミットを許すかどうかは、プロジェクトごとの値のファイルで宣言する。自動で検出する条件は持たない。
  - 立ち上げの時期と個人のリポジトリは、どちらも「このプロジェクトは直接コミットを許す」という宣言に帰着する。
  - 文書だけの変更は許さない。文書の境界を引けず、境界の管理が利用者に残る。
- 宣言は、`allow` と `reason` の 2 つのキーで書く。`allow` が `true` のとき、`reason` は必須である。
  - 理由を書かせるのは、宣言を切り忘れたときに、何のために許したかを読めるようにするためである。
- 宣言が有効な間は、フックがコミットのたびに、許す設定が有効であることと理由を表示する。拒否はしない。
  - 切り忘れを、拒否ではなく表示で防ぐ。

値の形は次のとおりである。

```yaml
protected_branches:
  names: [main]
  direct_commit:
    allow: false
    reason: ""
```

## 検討した選択肢

| 選択肢 | 強み | 弱み |
| --- | --- | --- |
| **採用:** 宣言だけ | 判定が予測できる。設定が 2 つのキーで済む | 立ち上げが終わった後に、宣言を切る操作が要る |
| 宣言と、許すパスの glob | 文書だけの変更を表せる | 何が文書かの境界を利用者が管理する。AGENTS.md やスキルの本文を許すと、エージェントの挙動が審査なしで変わる |
| 人とコーディングエージェントで宣言を分ける | 人は直接コミットし、エージェントには変更の依頼を通させる運用ができる | Git のフックからコーディングエージェントのコミットを見分ける手段が未確認。設定が 2 倍になる |
| 立ち上げの時期を、タグの有無で自動で判定する | 宣言が要らない | タグを使わない利用者で、いつまでも許される |

## 影響

### 良い影響

- フックの判定が、値のファイルを読むだけで済む。
- 許している理由が、値のファイルに残る。

### 悪い影響

- 立ち上げの時期が終わったら、利用者が宣言を切る必要がある。切り忘れは、表示でしか気づけない。
- 誤記の修正のような小さな変更でも、宣言がなければ変更の依頼を通す。
