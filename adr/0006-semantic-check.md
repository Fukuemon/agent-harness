# ADR-0006: 意味の判定が要るルールには、任意の追加として Jev を使う

## 状態

提案。採用は、下の「承認の条件」を確かめてから決める。

## 背景

ルールには、機械で判定できるものと、判断が要るものがある。前者は自動チェックで持ち、後者はスキルに書いている。  
スキルに書いたルールは、守られたかを確かめられない。サブエージェントにも引き継がれない。

判断が要るルールの一部は、意味を判定できれば自動チェックへ移せる。次の 2 つが例である。

- 足されたコメントが、コードの言い換えにすぎないかどうか。
- 文書が、水増しや曖昧な記述を含んでいないかどうか。エージェントに書かせた文書は、この形の workslop になりやすい。

Jev は、TypeSafe AI が提供するモデルである。文章を生成せず、型のある問いに確率で答える。  
jev-lint は、Jev をコードと文書のチェックに使うツールである。対象は ast-grep で機械的に選び、問いを自然文で書き、返った確率をしきい値で判定する。Markdown 向けのルールも持つ。

- `README.md:9-11` / [github](https://github.com/uehaj/jev-semgrep/blob/8c78ac7ecb4081cdb2ca40d198d6003aa0e1a506/README.md#L9-L11)
- `README.md:144` / [github](https://github.com/mizchi/jev-lint/blob/4fdca89eb395757047103410bf32bd1bb79b8cb0/README.md#L144)

確かめた制約は、次のとおりである。

- 決定的ではない。jev-lint の README は、自身のリポジトリで測った結果として、指摘の約 5 件に 1 件が誤りだったと書いている。
  - `README.md:96-99` / [github](https://github.com/mizchi/jev-lint/blob/4fdca89eb395757047103410bf32bd1bb79b8cb0/README.md#L96-L99)
- 最も正確なのは英語である。日本語の問いは、しきい値の付近で揺れが大きい。
  - `README.md:69-70` / [github](https://github.com/uehaj/jev-semgrep/blob/8c78ac7ecb4081cdb2ca40d198d6003aa0e1a506/README.md#L69-L70)
- API の鍵が要り、コードや文書の本文を外部のサービスへ送る。
  - `README.md:123` / [github](https://github.com/mizchi/jev-lint/blob/4fdca89eb395757047103410bf32bd1bb79b8cb0/README.md#L123)
- jev-lint は公開されたばかりで、作者は 1 人である。

## 決定

次の 3 点を提案する。

- 意味の判定は、決定的なチェックの後ろに置く、任意の追加にする。
  - 1 段目は決定的なチェックである。コメントが足されたかどうかのように、オフラインで判定できることを扱う。
  - 2 段目が Jev である。1 段目が拾ったものについて、意味を判定する。
  - API の鍵がない環境では、1 段目だけで動く。
- 意味の判定の結果では、編集もコミットも拒否しない。確かめるよう促すだけにする。
- パッケージの必須の部分にはしない。使うかどうかは、利用者が決める。

## 承認の条件

- このリポジトリの日本語の文書とスキルに当て、誤った指摘の割合を確かめる。
- 足されたコメントがコードの言い換えかどうかを、実際の差分で判定させ、誤った指摘の割合を確かめる。
- TypeSafe AI の利用規約と、送った本文の扱いを確かめる。
- 1 回のチェックの費用を、外部へ何も送らない実行で確かめる。
  - `README.md:90-91` / [github](https://github.com/mizchi/jev-lint/blob/4fdca89eb395757047103410bf32bd1bb79b8cb0/README.md#L90-L91)

## 検討した選択肢

| 選択肢 | 強み | 弱み |
| --- | --- | --- |
| **採用:** 決定的なチェックの後ろに、任意の追加として Jev を置く | 判断が要るルールの一部を、チェックへ移せる。サブエージェントにも届く。Jev が使えなくても仕組みが動く | 外部のサービスへ本文を送る。誤った指摘が混じる |
| 意味の判定を使わず、判断が要るルールはスキルだけに書く | 外部への依存がない | 守られたかを確かめられない。サブエージェントに届かない |
| 生成するモデルに、フックの中で判定させる | 既に使っているモデルで足りる | 遅く、費用が高い。同じ入力でも結果が変わりやすい |
| 意味の判定を必須にし、結果でコミットを拒否する | 強く守らせられる | 誤った指摘でコミットが止まる。鍵がない環境で動かない |

## 影響

### 良い影響

- スキルに書くしかなかったルールの一部を、守られたかを確かめられる形にできる。
- 文書の水増しを、書いた時点で指摘できる。

### 悪い影響

- 公開されたばかりのツールと、1 社のサービスに依存する部分ができる。任意の追加に留めることで、影響を抑える。
- 誤った指摘に対応する手間が増える。
- 本文を外部へ送れないリポジトリでは使えない。
