# ADR-0021: ガードレールは考え方として持ち、止める仕組みと値は配らない

## Status

承認。ADR-0011 と、ADR-0013 のうち guardrails を独立したパッケージとする部分を、この決定が置き換える。

## Context

ガードレールは、取り返しのつかない操作を、モデルへの指示ではなく、実行の前にプログラムで止める仕組みである。  
これまでの設計では、パッケージ guardrails が、止める仕組みと 3 つの規則を持つ予定だった。規則は、保護ブランチ、禁止するコマンド、秘密情報である。値は `context/project.yml` の `guardrails` に書き、保護ブランチへの直接コミットは、その値での宣言だけで許す（ADR-0011）。

3 つの規則は、どれも agent-harness の外の仕組みで止められる。

- 禁止するコマンドは、コマンドの文字列だけで判定する。コーディングエージェントの権限の設定（Claude Code の permissions、Codex CLI の rules）が、同じ判定を持つ。
- 保護ブランチは、Git のフックで今いるブランチを確かめれば止められる。利用者の lefthook の数行で足りる。フックを迂回する引数は、コーディングエージェントの権限の設定で止められる。
- 秘密情報は、Git のフックから secretlint を呼べば止められる。

守るブランチの名前、許す場面、除外する形式は、利用者ごとに違う。agent-harness が判定のスクリプトを配っても、中身は利用者の値を読むだけになる。  
agent-harness は、抽象を配り、具体は利用者が作る方針である。境界は、コーディングエージェントの sandbox と権限の設定で、利用者が先に引く。

## Decision

次の 3 点を決めた。

- ガードレールを、パッケージの機能としては持たない。止める仕組みも、規則の値も配らない。取り返しのつかない操作は、利用者が、Git のフックとコーディングエージェントの権限の設定で止める。
- ガードレールは、agent-harness の根本の考え方として持つ。取り返しのつかない操作は、モデルへの指示に頼らず、プログラムで止める。パッケージのフックは、編集もコミットも拒否しない。
- 保護するブランチと、直接コミットを許す場面は、CONTRIBUTING.md のブランチの節に書く。スキルは、そこを読んで判断する。`context/project.yml` から `guardrails` のキーを削除し、schema の `version` を 2 に上げる。

## Considered Options

| 選択肢 | 強み | 弱み |
| --- | --- | --- |
| **採用:** 考え方として持ち、仕組みと値は配らない | 配るものが減る。止める判定を、コーディングエージェントと Git の仕組みに 1 つずつ持てる。ブランチの取り決めが CONTRIBUTING.md の 1 か所にまとまる | 止める設定は、利用者が自分で書く。書かなければ、何も止まらない |
| 規則を core に置く | core を入れれば止まる | コーディングエージェントの権限の設定と同じ判定を、別に持つ。保護ブランチの名前を、CONTRIBUTING.md と `project.yml` の 2 か所に書く |
| 独立したパッケージ guardrails を作る | ガードレールだけを入れられ、パッケージごと外せる | 規則を core に置く形と同じ弱みに加え、パッケージが 1 つ増える |

## Consequences

### Positive

- `context/project.yml` が、機械で読む値だけを持つ。
- コーディングエージェントの仕様の変更で、agent-harness の判定が働かなくなることがない。

### Negative

- 利用者の `context/project.yml` の `version` を 2 に上げ、`guardrails` のキーを消す手間が要る。
- 止める設定が利用者ごとに違い、揃っているかを agent-harness は確かめない。
